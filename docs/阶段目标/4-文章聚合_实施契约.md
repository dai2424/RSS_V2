## 3. 任务契约

| 任务类型 | 阶段 | 幂等键 | 完成方式 | 任务展示目标 |

实现要点（每个类型都要做）：

1. `TaskType` 增加枚举；加入 `WORKER_TASK_TYPES` 与 `LLM_TASK_TYPES`；`TASK_SPECS` 增加规格；worker `execute` 增加分支。
2. 任务 payload 必须含 `{provider_id, model, prompt_id, prompt_version}`（提示词统计与审计依赖它）+ 各阶段输入标识（如 `batch_id`/`project_id`/`outline_version_id`）。

4. 写库前后台校验租约（`ensure_lease` / `lease_of`）；失败写分类错误；重试沿用 worker 阶梯。
5. 新结果表如带 `prompt_version` 列，同步加入 `SQLitePromptRepository.usage()` 的 `results` 计数并在 `PromptUsage` 注释中登记。

## 4. API 契约

通用：所有响应为 Pydantic schema；错误体 `{code, message}`；`DomainError` → 404（`*_not_found`）/409（`ConflictError` 或 `*_exists`）/400（其他）；校验失败 422；分页响应 `{items, total}`；时间均为 UTC 秒。

### 4.1 选题发现与写作项目（P2a）

| 方法 | 路径 | 请求 | 响应 | 状态码 |
| --- | --- | --- | --- | --- |
| POST | `/api/discoveries` | `{window_start?, window_end?, category_id?, source_id?}` | `DiscoveryBatchResponse` | 202（重复请求同码，`reused=true`） |
| GET | `/api/discoveries` | `limit(1–100, 默认 20)`、`offset`、`status?` | `{items: [DiscoveryBatchSummaryResponse], total}` | 200 |
| GET | `/api/discoveries/{batch_id}` | — | `DiscoveryBatchDetailResponse` | 200 / 404 |
| POST | `/api/discoveries/{batch_id}/candidates/{candidate_id}/select` | — | `ProjectResponse` | 201（重复选择 200 + `reused=true`） |
| DELETE | `/api/discoveries/{batch_id}` | — | `{deleted: int}` | 200 / 404 |
| GET | `/api/projects` | `limit`、`offset`、`status?` | `{items: [ProjectSummaryResponse], total}` | 200 |
| GET | `/api/projects/{project_id}` | — | `ProjectDetailResponse` | 200 / 404 |
| GET | `/api/leads` | 增加 `kind?`（默认 `manual`） | 既有 `LeadListResponse` | 200 |

字段约定：

- `DiscoveryBatchResponse`：`id, status, window_start, window_end, category_id, category_name, source_id, source_name, message_count, candidate_count, duplicate_members, out_of_range, dropped_members, dropped_candidates, error_code, error_message, task (TaskResponse | null), reused, created_at, updated_at`。
- `DiscoveryBatchDetailResponse`：`{batch: DiscoveryBatchResponse, candidates: [DiscoveryCandidateResponse]}`。
- `DiscoveryCandidateResponse`：`id, rank, title, summary, event_time, score, reasons: [{kind: 'interesting'|'important', text}], member_count, dropped_members, lead_id, project_id | null, members: [DiscoveryMemberResponse]`。
- `DiscoveryMemberResponse`：`message_id, version_id, version_number, title, source_id, source_name, published_at, url`。
- `ProjectResponse`：`id, title, status, lead_id, candidate_id, created_at, updated_at`；`ProjectDetailResponse` 追加 `members: [DiscoveryMemberResponse]`、`counts: {materials, facts, outlines, articles}`（P2a 阶段后三项为 0；P4 起 `materials`/`facts`/`outlines` 为真实计数，`articles` 待 P5）。

行为：`POST /api/discoveries` 在批次未 `succeeded` 时选择候选 → 400 `discovery_not_ready`；`succeeded` 且候选存在时选择；`writing_projects.candidate_id` 唯一保证幂等。

### 4.3 提纲（P4）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/projects/{id}/outlines` | 生成提纲（`generate_outline`），202 + `TaskResponse`；`force` 可选 |
| GET | `/api/projects/{id}/outlines` | 版本列表（含状态、依据资料包哈希、提示词/模型、丢弃计数） |
| PUT | `/api/projects/{id}/outlines/{oid}` | 人工修改保存（新 `draft` 版本 + `based_on_version`），201 |
| POST | `/api/projects/{id}/outlines/{oid}/confirm` | 显式确认；校验版本状态与项目状态，200；非最新草稿 → 409 `outline_version_stale` |

字段约定：

- `OutlineVersionResponse`：`id, version_number, status, source, title, angle, sections: [OutlineSectionResponse],
  counters: OutlineCountersResponse, material_snapshot_hash, digest_run_id, prompt_version, model, task_id,
  based_on_version, created_at, confirmed_at, is_latest`。
- `OutlineSectionResponse`：`heading, talking_points, fact_ids, evidence_ids, impact_notes`。
- `OutlineCountersResponse`：`out_of_range, unsupported, dropped_sections, dropped_points, without_facts`。
- `OutlineListResponse` / `OutlineResponse`：版本（或 `items`）之外追加项目级 `latest_version_id, confirmed_version_id,
  has_unconfirmed_changes, has_blocking, blocking_count, task_status`。
- `OutlineSaveRequest`：`{title, angle, sections: [OutlineSectionRequest]}`，整份提交、不做局部字段合并。

行为：没有资料整理版本 → 400 `project_status_invalid`；输出不足 2 节 → 400 `outline_validation_failed`（模型侧为任务失败）；
越界事实/引文与指向缺引文事实的引用逐条丢弃并计入 `counters`（不报错）；
**未处理的阻塞缺口只标记（`has_blocking`）不拦生成与确认**，是否拒绝全文生成留给 P5。

## 5. 状态机

- 批次：`queued → running → succeeded | failed`；`failed` 可重试（同批次，新增任务尝试）。
- 项目：`materials_pending → materials_ready → outline_ready → outline_confirmed → article_ready → saved`（只前进；重生成不回退项目状态）。
- 提纲：`draft → confirmed → superseded`；`confirmed` 不可就地编辑，编辑基于任意版本（含已确认/已被取代）另存新 `draft`；
  只有项目内序号最大的版本可确认（旧版 → 409 `outline_version_stale`，已被取代 → 409 `outline_version_superseded`，
  重复确认最新版幂等 200）；确认把旧的 `confirmed` 转 `superseded`。
- 项目状态只前进：确认之后再次编辑产生新 `draft` 时项目仍是 `outline_confirmed`，由
  `has_unconfirmed_changes` 表示"当前确认的不是最新版本"（P5 据此判断要不要重新确认）。
- 文章：`generated(draft)`（生成产物）与 `edited(saved)`（人工保存）；历史版本只读。

## 7. 错误码

| 错误码 | HTTP | 场景 |
| --- | --- | --- |
| `discovery_window_too_large` | 400 | 窗口内消息超过上限 |
| `discovery_window_invalid` | 400 | 起止时间缺失/倒置/超跨度 |
| `discovery_scope_mismatch` | 400 | 来源不属于所选分类 |
| `discovery_batch_not_found` / `discovery_candidate_not_found` / `project_not_found` | 404 | 资源不存在 |
| `discovery_not_ready` | 400 | 批次未完成就选择候选 |
| `project_status_invalid` | 400 | 状态不满足该操作前置条件 |
| `outline_not_confirmed` | 400 | 未确认提纲就生成全文 |
| `outline_validation_failed` | 400 | 提纲不足 2 节（人工保存）；模型侧同一口径记为任务失败 |
| `outline_not_found` | 404 | 提纲版本不存在或不属于该项目 |
| `outline_version_stale` | 409 | 确认/生成时版本已被替换（确认非最新版本） |
| `outline_version_superseded` | 409 | 确认一个已被更新版本取代的旧版本 |
| `article_version_conflict` | 409 | 保存时基础版本过期 |
| `article_reference_invalid` | 400 | 保存稿引用不属于本项目 |
| `article_validation_failed` | 400 | 生成结果未通过引用/结构校验 |
| `search_unconfigured` / `search_format_disabled` / `search_invalid_output` | 400/502 分类 | 检索依赖与结果问题（沿用现有 `ExternalServiceError` 分类与任务错误码） |
| `article_timeout` / `article_http_error` / `article_too_large` / `article_unparsable` / `article_invalid_url` / `ssrf_blocked` / `budget_exhausted` | 资料状态码 | 读取失败与预算跳过分类（写资料行，不抛业务错误）；`unavailable` 状态不给错误码 |

## 12. 已知环境注意事项

- **迁移校验和与行结束符**：校验和是迁移文件**原始字节**的 sha256（`adapters/sqlite/migrations.py`），执行器不做行结束符规范化。仓库没有 `.gitattributes`，`core.autocrlf=true` 来自机器级 gitconfig；主仓库的工作区是**混合**的——截至 0029，29 个迁移文件里 23 个是 CRLF、6 个是 LF（`0001`、`0002`、`0004`–`0007`：这些早期文件在检出后被按 LF 写回过），既有库记录的校验和就是按这个混合状态算的。新 worktree 是干净检出，git 按 autocrlf 把全部 `*.sql` 统一写成 CRLF，上面那 6 个文件的字节因此变化，于是报"迁移文件已被修改"（最先撞到的是 `0001_initial.sql`）。实测：主仓库目录 29/29 与既有库记录一致，worktree 目录正好这 6 个不一致。
  在 worktree 中访问既有库：把 `RSS_MIGRATIONS_DIR`（`settings.py` 的 `migrations_dir`，`env_prefix="RSS_"`）指向**主仓库的 `migrations/` 目录**（见 P1a 文档 2.3）；若这次还要把本 worktree 新增的迁移应用到副本，就按字节复制主仓库目录到临时目录、再把新增文件补进去，指向那个临时目录（P4 的做法见文末 P4 附录）。
  **不要**用 `.gitattributes` 或"执行器先规范化字节再哈希"当根治方案：两者都会改变部分文件的哈希（前者让那 23 个 CRLF 文件在下次检出后变成 LF，后者让这 23 个的哈希值直接变），既有库会立刻不匹配，等于把问题从 worktree 扩大到主仓库。真要根治必须同时设计校验和重录，属独立决策。
- **E2E 端口**：`tests/preview.py` 使用 8877，浏览器用例必须串行；运行目录为 `runtime/e2e`。
- **真实依赖**：模型调用可用（业务库已配置 Provider/模型/Key），真实联网检索依赖用户提供的 SearXNG 实例；未提供前 P3a 只能交接"实现已自测、真实检索未验证"。

**数据表**：`digest_runs`（版本：输入指纹、任务、各类计数、缺口说明）、`material_evidence`
（引文 + 来源资料 + 正文偏移 + 引文指纹）、`project_facts`（run_id + 事实/分析/推测 + 状态 + 冲突说明）、
`fact_evidence`、`project_notes`（gap/conflict/note，`blocking` + `resolved_at`，已处理记录重跑保留）、

**配置**：`materials_digest_max_input_chars`(80000)、`digest_material_chars`(4000)、
`digest_max_facts`(40)、`digest_max_evidence_per_fact`(4)、`article_allow_private_hosts`(false，
仅夹具或内网资料源；默认拒绝内网地址)。

**P3b 分批修正（2026-10-15，真实环境实测后）**：把整份资料包放进一次调用时，真实模型的事实与引文会
写不完（`max_tokens` 截断、JSON 不完整）。现在按 `digest_batch_size`（默认 3 份资料/批）分批调用，
相邻批重叠一份资料，冲突里的"第几条事实"按批内偏移换算成全局序号；输出仍被截断时把这一批对半拆
（最多 2 层）。单次输出上限由 `digest_max_output_tokens`（默认 16384）显式传入。

**同一 URL 一行的去重规则（2026-10-15，真实环境反馈后）**：项目内的资料按规范化 URL 唯一——
`read`/`summary_only` 的行不会被替换（历史依据不被悄然换成最新正文）；`failed`/`unavailable`/
`budget_exhausted` 属于"无证据价值"的弱行，后续读取成功时替换它，避免旧失败记录跨轮堆积。
另外：成员消息**有摘要时不再按链接回读**（回读只用于"连摘要都没有"的短消息），
否则同一链接会存成"订阅原文 + 回读页面"两行。

**版本语义修正（2026-10-16，真实环境反馈后）**：只有**产出结果**的整理尝试才写 `digest_runs` 行。
失败/超时的尝试不写版本（落库中途失败会把半成品版本连同事实/证据/待办一起删掉），
否则界面会把"超时失败"显示成"整理完成但没有产出事实"。项目页的整理状态改为取
**最近一次 `digest_materials` 任务**（失败也显示），不再依赖只在成功时写入的摘要字段。

**真实环境要求：Provider 超时（2026-10-17，真实环境实测后）**：整理任务每批一次模型调用，
实测单次成功调用耗时 38–50 秒、输出 7.5–9.5k token，接近 Provider 默认的 60 秒超时。默认 60 秒
会让整理任务反复超时（`llm_timeout`）并耗尽 3 次重试，因此真实环境把 Provider 的
`timeout_seconds` 调到 180 秒以上（界面「模型配置 → 连接信息 → 超时」，上限 600 秒）；
本机配置同时把 `digest_max_output_tokens` 提到 32768。超时与 Key 冷却的关系见
[决策记录《Key 冷却与任务重试》](../决策记录/2026-10-17-Key冷却与任务重试.md)：
冷却期内的任务按可重试处理（`llm_key_cooling`），不再被误判成"没有可用的模型 API Key"。
已知限制：整理任务重试是**整轮重跑**（从第一批开始），单次任务调用次数多、耗时长（几十份资料
可达数分钟），尚未做逐批续跑；真实环境资料包过大时优先降低 `digest_batch_size`。

**整理输出限量与摘要批（2026-10-17，真实环境实测后）**：43 份资料的选题上，v1 提示词没有条数
上限，模型每批写出 6k–22k token 的事实与缺口（16 批共 23.2 万 token、耗时 22 分钟）；其中两批输入
只有 59/87 token（相当于三条搜索摘要）却写出 1 万与 1.96 万 token，明显在凑数与扩写；同一次整理
产出 108 条缺口说明（53 条阻塞），把真正的缺口淹没。三项修正：

1. 提示词升到 v2（迁移 0028，归档 v1）：单批事实最多 `{{facts_per_batch}}`（默认 8）条、缺口最多
   `{{gaps_per_batch}}`（默认 2）条，引文限定 20–120 字且必须是正文里原样连续的一句，明确"资料
   支撑不了就少写，不要凑数"。
2. 服务端兜底：`DigestLimits.facts_per_batch` / `gaps_per_batch` 在 `normalize_digest` 里截断
   （缺口优先保留 blocking），提示词写不住时也不会失控；`max_facts`（40）仍是全部批次合计上限。
3. 只有搜索摘要的资料（`summary_only`）**合并成一批**：它们单条几十到几百字符，却各自占满一个
   批次名额，还诱发"从极短输入扩写出大量事实"。合并后调用次数只由读到正文的资料决定
   （18 篇正文 + 14 条摘要：10 批，不再是 16 批），摘要也不会被丢掉，仍可作为引文来源。

另外：跨批文本相同的缺口/分歧说明在合并时去重（blocking 取并集、关联事实序号取并集），
避免同一句"缺少官方一手资料"堆成几十条。

**同一选题的实测对比（2026-10-17，隔离副本 + 真实模型，deepseek-v4.1-flash）**：

| 指标 | v1（无上限） | v2（限量 + 摘要批） |
| --- | --- | --- |
| 调用次数 | 16 | 13（含 2 次输出截断拆批） |
| 总耗时 | 22 分钟 | 15.5 分钟 |
| 输出 token 合计 | 232,469 | 137,969 |
| 事实条数 | 40（36 支持 / 4 冲突） | 40（32 支持 / 8 冲突） |
| 缺口说明 | 108 条（53 阻塞） | 23 条（10 阻塞） |

结论与后续：调用次数与输出量都下降，缺口噪声降到约五分之一。但**单次调用的输出仍有 7k–14k
token**，而 8 条事实的 JSON 本身只有 1–2k——差额主要是模型自身的思考 token（该模型按
`output_tokens` 计入思考）。也就是说剩下的耗时主要由"调用次数 × 每次思考开销"决定，
下一步的杠杆是**减少调用次数**（`digest_batch_size` 调到 6：正文 18 篇从 9 批降到 4 批），
而不是继续压 JSON 条数；条数上限已经把单批 JSON 压小了，因此加大批量不会再撞输出上限
（本次实测的一次截断发生在默认 16384 上限下，本机配置的 32768 不会触发）。

## 附：P4 提纲实现与新契约（2026-10-20）

**任务类型**：新增 `generate_outline`（提纲生成，一个写作项目一个任务，服务自完成）；
幂等键 `outline:{project_id}:{material_snapshot_hash}`，`force=true` 表示用户主动重新生成。

**API**：`POST /api/projects/{id}/outlines`（202，`force` 可选）、`GET /api/projects/{id}/outlines`、
`PUT /api/projects/{id}/outlines/{oid}`（201）、`POST /api/projects/{id}/outlines/{oid}/confirm`（200）。
字段与行为见 §4.3。

**一次生成做什么**：取项目最新一次资料整理版本（`digest_run_id` 钉住），把已核对的事实（含分析与推测，
缺引文的事实标注"没有可用引文，不要作为依据"）与未处理的缺口/分歧渲染进提示词 → 模型按 `OutlineDraft`
输出标题、切入点与分节 → 服务端逐条核对引用 → 落一个新 `draft` 版本并推进项目状态到 `outline_ready`。

**引用校验口径（服务端）**：模型（与人工表单）只能给事实 id 与引文 id，服务端按本次资料包核对：
越界的事实/引文 id 丢弃并计 `out_of_range`；指向 `missing`（无可用引文）事实的引用丢弃并计 `unsupported`；
没有小标题的小节与超出上限的小节/要点丢弃并计 `dropped_sections`/`dropped_points`；
保留下来的、一条事实依据都没有的小节计 `without_facts` 并在界面上显著提示。全部计数随版本返回
（`counters`），丢弃必须看得见。归一化后不足 2 节判为无效输出：**不写版本行**，任务失败并记
`outline_validation_failed`——避免界面把"模型没按约定作答"显示成"生成完了但提纲是空的"。

**版本与确认语义**：只追加，历史行不改写。只有项目内序号最大的版本可确认；确认把旧的 `confirmed`
转 `superseded` 并写 `confirmed_at`，项目状态推进到 `outline_confirmed`；重复确认最新版幂等。
人工保存基于任意版本（含已确认/已被取代）另存新 `draft`，只写 `based_on_version`，不改被改的那一版；
确认后编辑产生新 `draft` 时项目状态不回退（只前进），由 `has_unconfirmed_changes` 表示
"当前确认的不是最新版本"。

**阻塞缺口不拦确认**：`has_blocking`/`blocking_count` 随响应返回，界面用显著横幅标记（"可以继续确认，
但按现有资料写主线会有风险"）；是否拒绝生成全文留给 P5 决定。这是本轮的用户决定，与 P3b 附录里
"后续提纲阶段应据此拒绝生成资格"的设想不同，已按此实现。

**任务失败码**：`outline_no_facts`（这次资料整理没有可用事实）、`digest_not_found`（资料包版本已失效）、
`outline_validation_failed`（输出不足 2 节）、`llm_timeout` 等沿用既有分类；失败/超时不写版本行。

**本轮偏差（相对 P1b 契约与决策记录）**：

   落法照抄 `services/digest.py::DigestService.create`：**服务层按幂等键复用 + 普通索引**。

6. **界面位置**：执行清单 P4 第 4 条写的是"前端独立页面编辑"，本轮按用户决定落在写作工作台

**顺带修正**：`GET /api/projects/{id}` 的 `counts` 里 `materials`/`facts` 曾是 P2a 留下的写死值，

### P4 真实环境实测（2026-10-20，隔离副本 + 真实模型）

**环境**：把真实运行库复制到隔离目录（`runtime/p4-real`，只读源库 `VACUUM INTO` 副本），
迁移目录用主仓库的字节再补上本轮 0029（原因见 §12：worktree 检出的字节与既有库记录不一致）；

| 轮次 | 输出上限 | 结果 |
| --- | --- | --- |
| 1 | 8192（原默认） | 失败：`llm_output_truncated`（`stop_reason=max_tokens`，29.4 秒） |
