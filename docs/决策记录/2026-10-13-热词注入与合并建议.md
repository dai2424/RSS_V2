# 决策记录：热词注入与合并建议

> 状态：实施中（2026-10-13，阶段 3 的 M0；实现分 7 个提交，见[阶段目标 3](../阶段目标/3-关键词收敛_AI.md)）
> 背景：阶段 2 做完了"关键词可检索 + 词表可合并"，但词表只是被观察的对象——模型每次加工仍从零发明写法（实测 332 个词里 301 个只出现一次，379 行关键词里 349 行来自旧提示词的降级结果），人工只能事后收拾。本决策把词表变成被使用的对象：加工前注入词表让模型优先复用，人工用常驻词固定必用词，并用模型给出疑似同指组降低人工工作面。

## 结论

1. **注入内容的形状**：提示词新增 `{{vocabulary}}`，内容是**按类型分组、只给写法、不给频次与计数**的词表；另附"近 N 天新增"一段。频次会诱导模型把高频词当成更重要，而注入的目的是复用不是排序；计数还会让同一词表两次渲染产生不同文本，破坏 `llm_calls.input_hash` 的可解释性。
2. **常驻词并入类型分组，不单列一段**：常驻（pin）的语义是"这个词必须一直可见"，因此超出条数上限时也把它放进它所属的类型分组里；再单列一段会让同一个词在提示词里出现两次、白费 token。这是对计划稿 D1 的细化。
3. **条数与窗口可配**：`llm_vocabulary_limit`（默认 150，`0` 表示关闭注入）与 `llm_vocabulary_recent_days`（默认 7）。词表会继续增长，硬编码不可维护；默认值参考现状规模（332 个词）留出增长空间。
4. **注入的是展示写法，不是归一化键**：`KEY_AGGREGATE` 的分组键是规范词（归一化），但注入要给模型看到 `ChatGPT` 而不是 `chatgpt`——模型能直接复用的是写法。判定复用时把写法再归一化一次即可对齐。
5. **词表版本用"注入文本指纹 + 计数"**：`vocabulary_state` 单行表存最近一次注入文本的指纹与计数，指纹变化（新增词、合并、配置变化）则计数 +1，并把当前计数写进 `message_enrichments.vocab_revision`。这样无需在写入与合并路径埋钩子（漏一处就长期漂移），语义正好是"模型看到的词表变了"；这个计数无法从事实数据推导，才允许落字段。
6. **只有加工执行推进版本**：编译预览与提示词试跑只渲染、不写 `vocabulary_state`。否则在界面上点一次预览就会让所有存量结果看起来"早于当前词表版本"。
7. **复用率由服务端硬判定，模型不自报**：模型输出归一化后是否落在本次注入集合里，就是 `reused`；提示词只写"优先使用词表里的写法"，不要求模型返回"复用/新建"字段。自报可以表演性填报，而且多一个字段就多一条容错路径与一份 token。这是对计划稿 D4 的细化。
8. **常驻词与合并联动**：pin 以规范词为键；合并时把成员上的 pin 搬到目标（目标已 pin 则保持），并在 `keyword_merges` 记录 `pinned_json` 与 `target_was_pinned`，撤销时按记录还原。**已知边界**：链式合并按逆序撤销时可能留下一个多余常驻标记（B 的 pin 在两次撤销中都落回 B），界面可手动取消；不为此引入 pin 历史表。
9. **合并建议是请求内的同步调用，不进任务表**：新增任务类型要按 `0009` 的先例整体重建 `tasks` 表来改 CHECK 约束，代价与本阶段收益不匹配。每批 ≤100 词，复用 `LLMFailover.execute(task_id=None, ...)` 的候选调度与 Key 冷却（提示词试跑已验证这条路径），结果落 `keyword_suggestions`，并用 `keyword_suggestion_batches(fingerprint, offset)` 做幂等台账——同一批不重复付费。
10. **建议的提示词规格不进任务分配**：`TaskSpec` 增加 `assignable` 字段，`TaskType.KEYWORD_MERGE_SUGGEST` 这类只用于提示词的任务规格标为不可分配，`TaskSettingService` 不把它渲染进来源/分类的分配界面；worker 的认领集合显式写成"采集 + `LLM_TASK_TYPES`"，因此它永远不会被领取。同时 `PromptService._invoke` 为它加分支，保证提示词页的试跑按钮可用。
11. **采纳建议不新增合并实现**：采纳复用既有 `POST /api/keywords/merge`（含 `dry_run` 影响面预览与撤销），成功后只把建议标记为已采纳并回填 `merge_id`。合并的破坏性与可撤销性已经有一套实现和测试，不复制第二套。
12. **建议组的成员必须落在本批输入内**：模型给出的越界词与幻觉词一律丢弃并记录原因；组指纹（成员集合哈希）唯一，同一组不会被重复建议，已忽略的组不再出现。

## 实测调参（2026-10-14）

首次真实调用直接失败：60 个词的批次把输出预算耗尽（`stop_reason=max_tokens`），JSON 被截断后校验失败。随后在真实库副本上逐项实测，定下以下参数：

| 项 | 取值 | 依据（真实模型 + 真实词表） |
| --- | --- | --- |
| 输出上限 | 32768（被上游拒绝时退回 8192 重试） | 8192 时 40 个词的思考就用掉 10026 输出 token |
| 批次大小 | 默认 20 | 20 词 ≈ 30–40 秒、约 5 千输出 token，落在 Provider 默认 60 秒超时内；60 词会同时逼近上限与超时 |
| 扩展思考 | 保留 | 关掉后快 15 倍、省 25 倍 token，但模型退化成按前缀配对（把「Dots」与「Dots 获得重大升级」当同指），不可接受 |
| 类型标注 | 回查时剥掉 | 模型常把批次行里的「（实体）」一起抄回来，那标注是我们渲染的，不属于写法 |

同一批词表上的实测结果：高频词那批返回 0 组（那里的近似词都是上下位，按规则不该合并），长尾批次返回 1 组且正确（`理想MEGA` 与 `新一代理想MEGA`）。**这个任务吃判断质量、不吃批量**，因此默认批次偏小。

## 影响范围

- 迁移：`0014`（`enrichment_keywords.reused`、种子 `enrich-v3` 提示词）、`0015`（`vocabulary_state`、`message_enrichments.vocab_revision`）、`0016`（`keyword_pins`、`keyword_merges.pinned_json`/`target_was_pinned`）、`0017`（`keyword_suggestions`、`keyword_suggestion_batches`、种子 `keyword_merge_suggest` 提示词）。
- 领域：`PromptVocabulary`、`render_vocabulary()`、`Keyword.reused`、`Enrichment.vocab_revision`、`KeywordEntry.pinned`、`MergeSuggestion`、`TaskType.KEYWORD_MERGE_SUGGEST`、`TaskSpec.assignable`。
- 端口：`KeywordRepository` 增 `prompt_vocabulary`、`note_vocabulary`、`set_pin`、`pins`；`LLMProvider` 增 `suggest_merges`。
- 适配器：新增 `adapters/sqlite/keyword_vocabulary.py`、`adapters/sqlite/keyword_suggestions.py`；`keywords.py` 的写入与重建带上 `reused`；两个协议适配器各加一次结构化调用；`router.py` 转发。
- 服务：`PromptResolver` 承担注入（模板引用 `{{vocabulary}}` 才查词表）；`EnrichmentService` 做复用硬判定；新增 `KeywordSuggestionService`；`PromptService` 的编译与试跑改用真实注入词表。
- 配置：`llm_vocabulary_limit`、`llm_vocabulary_recent_days`（`settings.example.toml` 同步）。
- 前端：词表页拆出筛选组件、增加常驻列与筛选、概览新增指标；新增合并建议区块复用既有合并弹层。

## 重新评估条件

- 注入使单次加工输入 token 明显抬升成本，或前 150 词覆盖率不足（大量该被复用的词落在上限之外）。
- 词表超过约 800 词：评估把建议生成改为后台任务类型（届时才值得付重建 `tasks` 表的代价）。
- 复用率上升但相关消息质量下降（注入把不相关的词硬塞进已有词条）。
- 同一组在合并记录里被反复合并（说明别名没有挡住回潮）。
