# 决策记录：列表分页控件与列表接口的 total

> 状态：已实施（2026-10-10）
> 背景：消息、来源、任务、关键词四个列表页原来只有"上一页 / 下一页 + 第 N 页"。用户要求参照 Element UI 的分页：显示记录总数、可选择每页条数与附近的页码。现状还有两处硬伤：消息与任务的列表接口返回裸数组、没有总数，下一页只能靠"本页不满"来猜；页码与每页条数在四个页面里各写一遍。

## 结论

1. **四个列表接口统一返回 `{items, total}`**：消息与任务补上 `total`，形状与来源、关键词一致（`SourceListResponse` / `KeywordListResponse` / `MessageListResponse` / `TaskListResponse` 都继承新加的泛型 `Page[T]`，schema 名不变）。不用 `X-Total-Count` 响应头：总数不在 OpenAPI 类型里，前端得手工解析，和"类型自动生成"的约定冲突；也不再单开 `/count` 端点：多一次请求，还会出现列表与总数"半新半旧"的不一致。代价是消息与任务的响应形状变了，后端 11 个测试文件与 e2e 打桩同步改成读 `items`。
2. **总数与列表必须同源**：`count_messages` 与 `list_messages` 共用同一个 `_filters` 和同一段 `FROM … JOIN`（三个 LEFT JOIN 都是"每消息一行"的一对一连接，`COUNT(*)` 就是消息条数），任务计数与任务列表共用同一个状态条件。这正是来源、词表已有的做法：过滤条件分两处写，迟早会出现"总数比翻得到的条数少"。
3. **控件形态对齐 Element UI 的 `total, sizes, prev, pager, next, jumper`**：左侧"共 N 条"，右侧每页条数下拉 + 上一页 + 页码列表 + 下一页 + "前往 N 页"。页码列表按 Element UI 的 pager 规则：页数不超过 7 全部列出，否则固定 7 个格子（`1 … cur-1 cur cur+1 … last`，靠近首尾时补足 5 个连续页码），避免翻页时格子数抖动。消息页在真实数据量下会有几十上百页，跳页输入有实际用处，所以保留。
4. **每页条数取 25 / 50 / 100，默认 25**：25 沿用现状，100 是四个列表接口 `limit` 的上限，不需要放宽后端约束。当前页不是按钮而是带 `aria-current="page"` 的记号：点了没有反应的按钮属于"不能工作的控件"。
5. **分页状态和筛选一样放在 URL 上**：`offset` 沿用，新增 `size`。切页 push（浏览器可以后退回上一页），改筛选用 replace 且只删 `offset`——`size` 是显示偏好，不跟着筛选被重置。从列表进详情再返回时（`sessionStorage` 里存的就是当前查询串），每页条数自然也能恢复。
6. **换每页条数保留当前页码并按新页大小重算，超出新的末页时夹紧到最后一页**：第 3 页（每页 25）换成每页 100 后仍然是第 3 页，而不是跳回第一页。页码超出新的末页（例如从每页 25 的第 3 页换成每页 100）夹到最后一页，不停在空页上。
7. **越界的空页不自动跳转**：`total > 0` 但本页为空（删除后停在旧偏移、链接里的 offset 越界）时显示"这一页没有内容"和"回到第一页"，由用户决定。静默改 URL 会让人以为自己点错了。
8. **翻页时保留上一页内容**：四个列表查询加 `placeholderData: keepPreviousData`，符合 Web 界面规范第 5 节"刷新中保留已有数据、避免整页闪烁"；分页条用 `isPlaceholderData` 禁用，而不是 `isFetching`——消息页 5 秒轮询一次，用 `isFetching` 会让控件每 5 秒闪一下禁用。
9. **仍用 OFFSET，不引入游标分页**：排序口径是 `COALESCE(published_at, collected_at) DESC, m.id`（消息）、`created_at DESC, id`（任务）。2026-10-10 在本机 1517 条消息的真实库上只读实测：列表首页 6.6 ms、`OFFSET 500` 25 ms、`COUNT(*)` 4.1 ms、带关键词过滤的计数 4.2 ms——多出来的计数是这个量级，不值得为它改接口形态。深偏移的成本要重新评估时，先看这里：计数与列表共用同一段查询，若实测明显变慢，优先裁剪计数里用不到的 join（只有 `source_id` 或时间条件时不需要译文与加工结果的 join），而不是改分页方式。
10. **不做**：合并记录（10 条）与相关消息（8 条）这类固定窗口的小列表不加分页；它们不是翻页列表，加控件只会增加噪音。

## 影响范围

- 后端：新增 `api/schemas/pagination.py`（`Page[T]`）；`SourceListResponse`、`KeywordListResponse` 改为继承它；新增 `MessageListResponse`、`TaskListResponse`；`MessageRepository.count_messages`、`TaskRepository.count` 端口与 SQLite 实现（消息把过滤条件抽成 `_filters`，列表与计数共用）；`MessageService.count`、`TaskService.count`；`list_messages`、`list_tasks` 返回 `items + total`。
- 前端：新增 `lib/pagination.ts`（每页条数、页码列表、偏移换算）、`lib/usePaginationParams.ts`（URL 读写、`sizeParams`）、`components/Pagination.tsx`；消息、来源、任务、词表四个页面接上，删除各自手写的分页块，`PromptTestPanel` 改读 `items`；`styles.css` 扩展 `.pagination` 一行式布局。
- 测试：后端新增 `tests/integration/test_list_pagination.py`（总数不受分页窗口影响、跟随筛选、offset 越界仍有总数、任务按状态过滤的总数）；11 个测试文件改用 `items`；前端新增 `lib/pagination.test.ts` 与 `components/Pagination.test.tsx`；e2e 打桩与 `drainWorker`、`keywords.spec` 改读 `items`，桌面状态用例补分页条断言。
- 文档：[Web界面规范.md](../项目说明/Web界面规范.md) 第 4 节补分页控件要求。
