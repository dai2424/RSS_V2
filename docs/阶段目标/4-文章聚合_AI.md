## 1. 目标

面向普通科技读者，把订阅内容转化为**有趣、能帮助读者了解行业事件、通读核对并少量修改即可发布的科技博客文章**。用户点击「发现选题」，系统在有限时间范围内发现同一事件的候选，优先推荐有趣或重要的内容；用户选择后，系统读取原文并联网补充资料，提交提纲供用户调整和确认，再生成全文。用户在系统内编辑、保存文章，最后复制或导出到个人博客和公众号编辑器。

| 项目 | 已确认口径 |
| --- | --- |
| 读者与价值 | 普通科技读者；愿意读下去，了解行业发生了什么 |
| 首批文章 | 围绕同一事件整合报道，去重、补齐信息；重要或有趣的单篇报道也可成为选题 |
| 推荐优先级 | 有趣、重要；候选说明推荐理由，报道数量作为材料信息展示 |
| 写作风格 | 自然、有趣的科技博客，解释必要背景和术语；适度分析行业影响 |
| 长度与渠道 | 按事件复杂度决定长度；用于个人博客和公众号文章 |
| 人工节点 | 用户选择选题、确认提纲、通读核对并做少量修改 |
| 成稿要求 | 关键事实有来源，事实、分析与推测明确区分；在系统内可编辑、保存、复制或导出 |

## 2. 核心流程与范围

### 用户主流程

1. **发现选题**：用户点击触发；默认最近 7 天、全部订阅，可设置有限起止时间，并按分类或来源筛选。界面显示实际生效的范围。
2. **选择事件**：候选展示事件概要、发生或报道时间、相关报道、推荐理由。按同一事件聚合，用户选择要写的选题。
3. **准备资料**：读取报道原文，联网补充相关报道、官方一手资料和必要背景，展示资料来源、关键事实、分歧与缺口。
4. **确认提纲**：系统提出切入点和分节提纲，用户可调整并确认。资料存在影响主线的分歧或缺口时先提示处理。
5. **生成文章**：按已确认提纲写成全文，整合材料而非逐条堆叠摘要；正文在关键位置放来源链接，文末附来源列表。
6. **编辑保存**：用户在系统内修改标题、正文并保存；保留生成版本、人工保存版本及其依据。
7. **复制或导出**：将保存后的文章转入个人博客或公众号编辑器，保留文字结构与可阅读的来源信息。

### 包含

- 手动触发的事件发现、候选聚合、推荐理由和选题选择。
- 默认最近 7 天，支持明确的有限时间范围、分类和来源筛选；不提供无时间限制的默认扫描。
- 单篇有趣或重要报道的推荐；短快讯也可参与，不以是否已有关键词作为入选门槛。
- 选题后的原文获取、联网补充相关报道、官方资料与必要背景。
- 资料整理、关键事实的来源追溯、冲突和不足提示。
- 提纲生成、用户调整与显式确认、依据确认提纲生成全文。
- 文章预览、系统内编辑保存、版本保留、复制或导出。
- 主流程的真实状态、失败诊断、重试与恢复。

### 不包含

- 定时推荐、自动运行或自动发布到外部平台。
- 用户只给主题的写作入口、人工选若干消息后直接生成等其他写作路线；已有人工线索功能保留为辅助能力。
- 独立的行业奇闻杂谈栏目、长期主题跟踪、日报或周报。
- 封面、正文配图、自动生成图片或配图建议。
- 多人协作、复杂出版排版和平台发布管理。

## 3. 内容与可信度规则

- **事件边界**：同一事件的发布消息、评测和用户反馈可以共同支持选题；仅共享公司、产品或关键词，不能据此认定是同一事件。独立发布、融资等不同事件要分开。
- **有趣与重要**：推荐理由说明事件的新意、故事性或对行业和普通读者的影响。先做可解释的推荐，不在本次目标中锁定评分公式。
- **资料用途**：外部检索用于补齐已选事件和必要背景。只引用实际获取并使用的资料，搜索结果标题或模型记忆不能冒充已读取的证据。
- **来源支持**：优先使用可核对的官方一手资料；关键事实关联来源和所用证据。引用合法只证明资料在输入集合中，是否支持该事实仍需内容核查。
- **事实与判断**：事实有来源；行业影响分析说明依据；不确定判断使用明确的推测表达。不得编造数据、引语、时间或资料。
- **分歧与缺口**：来源相互矛盾时呈现分歧；关键事实无法确认时标明待核对。未解决的关键缺口会影响成稿通过，不能用流畅文字掩盖。
- **文章表达**：对普通读者解释必要术语和背景，删去重复、补齐关键细节，以完整主线组织文章，避免夸张标题和逐篇摘要拼接。
- **引用展示**：正文必要位置放来源链接，文末列来源标题、发布者及 URL；内部核对能看到实际使用的证据及其版本。

## 4. 约束、前置与已有实现

### 工程与数据约束

- 选题时间取消息发布时间，缺失时回落采集时间；界面标明缺失情况。一次发现固定起止时间和输入版本，避免运行中窗口漂移。存储时间为 UTC 秒，展示遵守项目时区规范。
- 时间窗口限定订阅选题输入；补充的历史背景可早于该窗口，必须保留原始时间，不能写成新近发生的事。
- RSS 证据固定到消息版本；外部资料保留标题、发布者、URL、可用的发布时间、获取时间和实际使用的证据。来源更新后不改写历史文章依据；来源被删除时，保留既有证据或明确标记不可用，不能悄然换成最新正文。
- 已确认提纲、生成稿、人工保存稿分别保留状态与版本；重新生成产生新版本，不覆盖人工修改或旧稿。
- 发现、检索整理、提纲与全文等长任务走任务表 + 独立 worker；每阶段失败可诊断、可重试，不丢失已完成产物。
- 模型调用仅经 LLMProvider，复用提示词库、任务分配、统一调度与调用审计；结构化输出由 Pydantic 校验。检索、网页读取经端口和适配器装配，不在服务或 API 中直接调用具体网络实现。
- 复用现有 React 应用和组件，请求使用生成的 openapi-fetch client。长提纲和正文使用独立页面，遵守加载、空态、错误、未保存修改、键盘和桌面宽度要求。
- 用真实样本确定有限的候选规模、检索与模型调用预算、超时和输入长度限制，写入实施决策并提供可配置项；超限提示或分批，不静默丢材料。
- 数据结构、任务类型和兼容变更只经新编号迁移；资料快照、导出、日志与测试产物写入配置的运行目录，不进入 Git。

## 6. 验收标准

### 6.1 选题发现

- [ ] 点击「发现选题」按默认最近 7 天、全部订阅处理；用户可设置有限起止时间，并按分类、来源筛选，界面显示实际生效条件，固定样本断言窗口边界和组合筛选正确。
- [ ] 同一事件的多篇报道进入一个候选；同一公司不同事件不误合并。候选显示事件概要、时间、相关报道和围绕「有趣」「重要」的推荐理由。
- [ ] 单篇有趣或重要报道可以推荐、选择并走完整写作流程；无关键词短快讯可以成为事件材料。
- [ ] 无候选时如实显示空态和调整范围入口；模型或读取失败显示失败原因，不能伪装成没有选题。

### 6.2 资料与引用

- [ ] 选择选题后实际读取报道原文，并能检索补充官方资料、相关报道和背景；原文或网络失败显示哪份资料不可用及其影响。
- [ ] 关键事实能点回实际使用的资料与证据；RSS 引用固定消息版本，外部引用保存 URL、来源信息、获取时间及证据。未读取资料和越界引用不能进入成稿。
- [ ] 人工逐项核对关键事实是否获来源支持；事实、分析、推测明确区分，来源冲突和关键材料不足有可见提示。
- [ ] 源消息更新后旧稿引用与证据不变；资料不可用时明确提示。重生成保留旧稿和旧依据。

### 6.3 提纲与生成

- [ ] 系统先展示可调整、可保存的提纲，用户显式确认后才生成全文；全文使用确认时的提纲版本，修改提纲后可重新确认。
- [ ] 全文按事件复杂度组织长度，说明事件、必要背景和行业影响，去重并整合互补信息，不堆叠报道摘要或为固定字数凑内容。
- [ ] 正文关键位置有来源链接，文末有来源列表；单篇来源不虚构其他来源或多方共识。

### 6.4 编辑与输出

- [ ] 用户能在系统内修改标题、正文并保存，刷新后内容仍在；清楚区分 AI 生成版本与人工保存版本。
- [ ] 重生成不覆盖人工修改；旧稿可查看。离开未保存编辑时有保护，保存失败保留输入，服务端确认后才显示保存成功。
- [ ] 复制或导出保存后的稿件到个人博客、公众号编辑器，标题、段落、小标题和可阅读的来源信息完整；分别实际验证，无需重排文章主线或正文结构。具体输出格式由这两类验证决定，不能仅以导出文件存在作为通过。

### 6.5 异常、恢复与界面

- [ ] 加载、无候选、获取失败、模型失败、保存失败均可复现且状态真实；失败能重试，已经完成的资料、已确认提纲和已保存文章不丢失。
- [ ] 重复点击不重复创建相同在途任务；worker 重启后可恢复，任务页展示真实阶段、目标、状态、尝试与错误，每次模型调用有审计。
- [ ] 键盘可完成发现、选题、确认提纲、编辑保存与输出；1280、1440、1920、2560px 桌面宽度无页面横向溢出，加载和错误反馈符合 Web 界面规范。

### 6.6 文章质量与验收证据

至少选择 **3 个固定真实事件**，分别覆盖「多源同事件」「单篇有趣报道」「需要背景补充和行业影响分析」，形成至少 3 篇文章。实施前锁定样本、期望事件边界和应覆盖的关键事实，记录来源版本、提示词、模型及人工修改。

每篇均需满足：

- [ ] 普通科技读者能理解发生了什么、为什么值得关注；必要术语有解释，语气自然、有趣，标题与正文一致。
- [ ] 去除重复、补齐关键事实、形成完整主线；关键事实逐项有支持证据，无编造信息或未标记推测。
- [ ] 用户通读核对后，只需少量措辞或个别句子修改即可发布。若需重写主线、大段调整结构、修正关键事实或补关键资料，则该篇未通过；上述至少 3 篇均需通过才算成稿质量达标。

另外用固定 fixture 验证：同主体不同事件分开、冲突和缺料提示、无关键词短快讯、窗口和组合筛选、无结果与失败、重试幂等、消息更新和人工保存版本保留。冲突或缺料样本应正确提示，不能为了通过而强行产出可发布文章。

验收证据包括：领域/仓储/API/任务测试、主流程及重要交互 E2E、桌面与键盘检查、引用核对记录、至少 3 篇原生成稿及人工修改记录、博客和公众号复制或导出结果。自动测试验证结构和状态；内容质量由人工逐篇评审。**当前这些功能与质量项均待验收。**

## 7. 风险、取舍与完成定义

| 风险或取舍 | 影响 | 应对与重新评估条件 |
| --- | --- | --- |
| 自动聚合混淆同主体不同事件，或漏掉短快讯 | 选题失真、材料缺失 | 固定事件样本人工核对；误合并或关键事实漏召回时先修发现流程 |
| 推荐追求吸引力而忽视事实 | 标题夸张、文章失真 | 推荐说明具体理由；关键事实、标题与正文一并核对 |
| 外部资料不可用、冲突或不足 | 无法达到可发布要求 | 显示缺口和分歧，保留已获资料；关键问题未解决的稿件不通过质量验收 |
| 多阶段检索与生成成本、耗时增长 | 流程中断或资源不可控 | 实测并记录阶段耗时与调用量，明确可配预算和超时，失败从阶段恢复 |
| 编辑与重生成覆盖人工成果 | 内容丢失、依据漂移 | 确认提纲和稿件版本保留，重生成另存，保存失败不清输入 |

完成定义：用户可以演示完整主流程；第 6 节行为和质量标准通过；资料引用、人工修改和任务恢复可核对；相关迁移、静态检查、测试、前端及必要 E2E 通过；文档、实现与配置一致；运行产物不污染仓库，并完成 [Git 工作流](../项目说明/Git工作流.md) 的合并与清理。
