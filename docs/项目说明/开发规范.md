# RSS v2 开发规范

> 状态：v0.2 建议版（2026-10-07）
> 定位：与[技术选型.md](技术选型.md)并列的权威文档。选型文档回答“用什么”，本文档回答“怎么写才算合格”。
> 规则标注：**[CI]** 可自动检查；**[评审]** 合并前人工检查；**[约定]** 默认做法，偏离时在提交说明中解释。

本文档的规则服务于第一版最小闭环。技术验证出现新结论时，先更新文档，再更新实现；文档过时与修正文档属于同一项变更。

## 1. v1 教训与 v2 对策

| v1 教训 | v2 对策 |
| --- | --- |
| 数据库迁移、表目录和仓储集中在一个大文件 | 迁移器、数据字典和按领域仓储分开 |
| API 路由、静态托管和任务执行混在一起 | 路由、用例、worker 和静态托管分开 |
| 多份模型 client/config 重复 | 统一 `llm/LLMProvider` |
| Protocol 存在但服务签名绑定具体 SQLite 类 | 端口进入服务构造函数，静态检查验证依赖方向 |
| React、旧看板和服务端页面并存 | 只保留一套 React 应用 |
| 任务表和进程内线程池双轨运行 | 只保留任务表 + worker |
| 数据库和 demo 产物污染 Git 工作树 | 运行目录、测试 fixture 和代码仓库分离 |

## 2. 目录与边界

第一版采用以下目录边界，详细结构见[项目结构.md](项目结构.md)：

```text
src/rss_v2/
  domain/       # 纯领域对象
  ports/        # Protocol 接口
  services/     # 用例和业务规则
  adapters/     # SQLite、RSS、LLM 等具体实现
  api/          # FastAPI 路由
  llm/          # LLMProvider 协议；实现在 adapters/llm
  tasks/        # 任务定义和 worker
  bootstrap.py  # 统一依赖装配
  settings.py   # 配置读取
  main.py       # API/CLI 入口
```

新增顶层目录或包前，先同步更新项目结构文档。[评审]

## 3. 分层与依赖

允许的依赖方向：

```text
api ──▶ services ──▶ ports ◀── adapters
                       ▲           │
                     domain ◀──────┘
```

- `domain/` 只包含领域对象和领域异常，不依赖项目内其它包，不做 IO。
- `ports/` 只依赖 `domain/` 和 `llm/` 的协议面，签名只出现领域对象、标准库类型和 Protocol。
- `services/` 只依赖 `domain/`、`ports/` 和 `llm/` 的协议面，禁止导入具体适配器、`sqlite3` 或模型 SDK。
- `adapters/` 实现端口，可依赖 `domain/`、`ports/` 和第三方库；业务 SQL 只出现在 SQLite 适配器。
- `api/` 只调用服务用例，不直接访问仓储或适配器。
- `bootstrap.py` 是组合根，负责创建具体适配器和服务；API、worker、CLI 与测试都通过它装配依赖。

## 4. 类型检查与抽象

- [CI] `src/` 使用 Pyright strict；服务构造函数必须接收 Protocol，不得写具体适配器类。
- [评审] 禁止无说明的 `# type: ignore`。
- [评审] `cast()` 只有在外部库或边界数据无法表达类型时才使用，并在同一行或附近说明类型安全依据。
- [评审] 新增接口前先确认存在实际用例；不为假想的未来预先创建 Repository。
- [约定] 测试可以在 `conftest.py` 或测试组合根中选择内存实现、SQLite 实现和 fake provider。

## 5. 规模与拆分

以下是生产代码的默认评审阈值，不适用于迁移 SQL、生成代码、fixture、测试数据和构建产物：

| 对象 | 默认阈值 |
| --- | --- |
| 单个 Python/TypeScript 源文件 | 400 行 |
| 单个函数 | 60 行 |
| 单个类 | 300 行 |
| 单个 router 文件 | 12 个端点 |
| 单个仓储类公开方法 | 25 个 |

超过阈值必须在评审中说明原因并决定拆分、保留或调整阈值。禁止为了过线进行没有领域意义的机械拆分，也不允许把“以后再拆”作为默认方案。[评审]

## 6. DRY 与公共层

- 新建模块前先检索现有实现，确认没有可复用代码。[评审]
- 两处相同实现可以暂时保留，但应在提交说明中记录；出现第三处前必须抽取公共层。[约定]
- 禁止复制一个服务目录后只改名称来新增服务。
- LLM client、配置读取、API 类型请求、任务认领和错误分类等共享能力只能有一份实现。
- 抽象只为解决已存在的重复，不为假想需求建立复杂框架。

## 7. LLM 调用

- [CI] 业务服务禁止直接导入模型 SDK、`httpx` 或调用模型端点；所有调用经过 `llm/LLMProvider`。
- [约定] 结构化输出使用 Pydantic schema 校验；禁止在业务层直接处理 provider 原始响应或使用裸 `json.loads` 兜底。
- [CI] 每次模型调用记录到 `llm_calls`，至少包含模型、provider、prompt 版本、输入摘要哈希、耗时、token 用量、状态、错误分类和关联任务。
- [约定] 超时、重试、并发限制、provider 配置和敏感信息脱敏只在 `llm/` 集中处理。
- [约定] 测试使用 fake provider，不依赖真实网络和真实模型。

## 8. 数据库与迁移

- [约定] 迁移是编号递增、永不修改的纯 SQL 文件，执行器独立于 SQLite 仓储。
- [CI] 除迁移执行器和 `adapters/` 外，任何代码出现 `ALTER TABLE`、`CREATE TABLE` 或业务 SQL 都视为违规。
- [约定] `schema_migrations` 记录版本、校验和和执行时间；已执行文件被修改时直接失败。
- [约定] 时间戳统一为 UTC 秒整型；枚举字段写明取值含义；表和字段有中文用途说明。
- [评审] 新建表或字段前先检查现有模型，确认没有复用可能。
- [约定] v1 数据导入是独立、可预览、可重复的命令，不混入结构迁移。

## 9. 配置、路径、错误与日志

- [CI] 生产代码禁止硬编码绝对路径、密钥和环境相关 URL；统一通过 `settings.py` 注入。
- [约定] 开发环境可使用被 gitignore 的 `env/`；生产环境使用仓库外配置或系统环境变量。
- [约定] 产物、日志、数据库和备份写入配置指定的运行目录，不写入代码目录。
- [CI] 禁止裸 `except:` 和静默吞异常；边界层可以捕获顶级异常，但必须记录、分类并返回可诊断结果。
- [约定] 业务异常定义在领域或服务层；适配器异常在端口边界翻译；API 使用统一异常处理器。
- [约定] 采集、LLM 调用和任务状态变化必须有结构化日志。
- [约定] 静默跳过必须在代码附近说明为什么安全可跳过。

## 10. 任务与后台执行

第一版只保留一套机制：

```text
API / CLI 创建任务 → SQLite 任务表 → 独立 worker 领取、续租、执行、重试
```

- 任务必须包含状态、幂等键、尝试次数、租约截止时间、输入版本和错误信息。
- worker 重启后必须能够回收超时任务。
- 任务处理函数必须幂等，并有重复领取测试。[评审]
- Windows 任务计划程序只负责定时创建任务，不承担任务执行状态。
- 禁止 API 进程内线程池与持久化任务表并行承担同一类任务。

## 11. 前端

布局、视觉、交互和页面验收遵守 [Web界面规范.md](Web界面规范.md)。本节只约束代码组织。

- [评审] 只允许一套 React 应用，新增页面必须进入现有应用。
- [CI] API 调用只允许使用生成的 `openapi-fetch` client，禁止手写 fetch/axios 封装。
- [评审] 组件文件默认不超过 200 行；页面拆为路由骨架、数据 hooks 和展示组件。
- [约定] 表单规则使用 Zod schema；服务端状态使用 TanStack Query。
- [约定] 路由级代码分割从第一天启用。

## 12. Git 与仓库卫生

- [约定] 提交信息使用中文，格式为 `类型: 描述`。
- [约定] 一个完整竖切或一个完整修复对应一个提交；同一提交允许包含代码、测试和文档；禁止提交半成品。
- [CI] 禁止入库：数据库、构建产物、日志、缓存、密钥和运行时输出。
- [约定] 测试不得产生代码目录之外的意外修改；测试后的工作树不要求绝对干净，但新增或修改的运行产物必须可识别并清理。

## 13. 检查与完成定义

当前本地检查命令：

```text
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
npm run typecheck
npm run test
npm run build
```

每个竖切完成前确认：

- [ ] 相关领域用例、仓储契约和 API 测试通过；
- [ ] 迁移可在全新数据库上运行；
- [ ] 失败、重试和幂等行为有验证；
- [ ] 前端使用最新 OpenAPI 类型（仅当该竖切包含前端调用时）；
- [ ] 包含界面改动时，完成 Web 界面规范中的状态、窄屏、键盘和视觉验收；
- [ ] 没有超出规范且未说明的规模或依赖方向问题；
- [ ] 文档、注释和配置说明与实现一致。

## 14. 规范变更

发现规范未覆盖的设计问题时，先在本文件或技术选型中记录决策，再实现代码。规范修订、实现和对应测试应在同一竖切中保持一致；不得为了绕过红线而复制实现或关闭检查。
