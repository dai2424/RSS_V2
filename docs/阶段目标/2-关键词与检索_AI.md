> 状态：**第一期已实施（2026-10-09）**，见[决策记录：关键词结构化与检索](../决策记录/2026-10-09-关键词结构化与检索.md)；第二期（热词注入、词表页与合并）待做。
> 更新：2026-10-09，按关键词设计讨论确认"提示词准入 + 结构化关键词 + 归一化词表 + 人工合并 + 热词注入"路线。

## 1. 阶段目标

把内容加工产出的关键词，从"给人看的标签"升级为"给机器用的检索与聚合键"：

    加工产出结构化关键词
    → 字面归一化并入词表
    → 按关键词检索出同一线索的消息
    → 为后续文章生成提供稳定的聚合键

分两期交付，第一期完成后"精确检索"可独立验收：

| 期 | 模块 | 完成后可验收的行为 |
| --- | --- | --- |
| 第一期 | M1–M4、M7 | 按实体/主题精确检索；中文关键词命中英文来源；列表按发布时间而不是入库时间排序；存量可回填 |
| 第二期 | M5、M6 | 关键词跨消息收敛；相似词可在界面合并、可撤销、不回潮 |

## 2. 现状与问题（实测）

以下数据取自本机运行库 `runtime/db/rss_v2.db`（2026-10-09：1798 个版本、15 条加工结果）。

| 问题 | 实测证据 |
| --- | --- |
| 检索打在 JSON 文本上 | `message_enrichments.keywords_json LIKE '%q%'`；搜 `AI` 命中 8/15 条（`OpenAI` 的子串），搜 `%` 或 `_` 命中全部 15 条（通配符未转义） |
| 关键词质量低 | 93 个词里 21 个是泛化动作/抽象词、4 个是正文数值、9 个是音译或字段名，按消息加权占 35%；最差一条 6 个词里 5 个无检索价值 |
| 词表长尾极散 | 90% 的词只出现一次；频次分布只有 `84×1 / 7×2 / 2×3` |
| 同一事件的词对不齐 | 两条同事件消息共享 `懂车帝`、`尊界V800`，但事件词分别是 `刹车踏板支架断裂` 与 `制动踏板支架底座`+`断裂`+`刹车测试` |
| 排序不看发布时间 | 列表按 `m.updated_at`（最近入库）排序；近 7 天采集了 1436 个版本，其发布时间跨度很长，一次批量采集会把历史旧闻顶到最前 |
| 两种时间不可互换 | `published_at` 与 `collected_at` 平均相差 2.6 天、最大 255 天；473 条相差超过 1 天 |
| 覆盖缺口 | 1798 个版本只有 15 条有加工结果（存量不回填），且加工还受"长内容"闸门限制，短快讯永远拿不到关键词 |
| 结果不确定 | 结果按 `(version, prompt_version, model)` 唯一，取"最近成功"；换模型或改提示词会整体换一套词表，检索与聚合随之漂移 |

## 3. 设计基线

1. **关键词是索引标签，不是内容摘要。** 摘要负责让人看懂，关键词负责让机器找到；准入判据只有一句：别人会不会用它来查找这条消息。
2. **模型管"重要度"，系统管"新鲜度"。** 重要度由模型给权重，新鲜度由消息时间算；不让模型输出时效性字段——它是相对查询时刻的量，存进库当天就开始失效。
3. **字面归一化自动做，语义合并人工做。** 归一化只处理大小写、全半角、空白与标点；"这两个词指同一件事"由人工在界面上确认。
4. **合并只处理同指，不处理上下位。** `OpenAI`/`openai`/`Open AI`、`AWS`/`谷歌云` 可合并；`尊界`/`尊界V800`/`尊界汽车` 是三个粒度，合并会抹平检索粒度，`智界V9` 更是另一个主体。
5. **能算的不要存。** 频次、活跃度、新鲜度都从事实数据推，不落成字段。
6. **展示与匹配分离。** 保留模型原始写法用于界面展示，归一化形式只用于匹配；归一化出错时展示层不跟着错。

## 4. 模块划分

### M1 提示词准入改造（零代码，先做）

改的是 `prompt-enrich-*` 的 user 模板；编译校验只要求声明 `title`、`summary`、`keywords`，因此不需要改代码。

要求：

- 条数从"3 至 8 个"改为"最多 6 个、宁少勿多"，并允许空数组（代码与界面已支持空关键词）；
- 明确准入判据、具名实体优先、保留原文写法不译成中文、事件词最多 1 个、同一概念不中英各出一份；
- 不产出泛化的动作、流程与抽象名词，不产出只在正文成立的数值与指标（后者写进 summary）；
- 反面例子不列长清单：把具体词当负面例词会诱导模型产出它们，只写抽象规则；
- 改完 `prompt_version` 变化，历史结果与新结果不可比，所有基线必须重测（见 M7）。

先做纯提示词版本，是为了把"准入判据是否有效"与"结构化改造"分开验证：M1 的实测数据同时是 M2 的目标基线。

交付：新提示词版本（全文见第 5 节），在提示词页创建并启用。

验收：泛化词与噪声在关键词位里的占比从当前 35% 降到 10% 以内（首轮实测后按实际调整目标）。

### M2 结构化关键词契约

- `EnrichmentResult.keywords` 从 `tuple[str, ...]` 改为结构化条目：`text`（展示原文）、`kind`（`entity`/`topic`/`event`）、`canonical`（归一化匹配键）、`weight`（0~1 重要度）；
- `EnrichmentResponse`（`adapters/llm/boundary.py`）同步改为对象数组校验，并加硬约束：`event` 条目最多 1 个、条目上限与提示词一致、`text` 非空；
- 解析容错沿用 `_split_keywords` 的思路：模型用字符串代替对象时按 `topic` 折算，避免一次格式不合规就整条失败；
- 空数组合法，界面显示"无关键词"；
- `message_enrichments.keywords_json` 保留为"模型当时输出"的原始快照；旧行缺少 `kind`/`canonical` 时按 `topic` + 字面归一化补齐一次（在 M4 建关系表时完成）。

### M3 归一化与词表

- 归一化是 `domain/` 的纯函数，只做字面等价：Unicode 形式统一、大小写折叠、全半角统一、压缩空白、剥离首尾标点；不做分词，不做"去公司后缀"这类语义推断；
- 归一化后为空的关键词直接丢弃；
- 新增别名表 `keyword_aliases(alias_norm, canonical_norm, source, created_at)`；`source` 区分 `manual`（人工合并）与 `system`（系统检查）；
- 写入别名时做**路径压缩**：别名永远直接指向最终词，避免 `A→B→C` 链让每次查询都要递归；
- 别名是合并的唯一事实来源：检索、热词注入、频次统计都必须先解析别名。

### M4 存储与检索

- 新增迁移 `0012_keywords.sql`，建关系表：

```sql
CREATE TABLE enrichment_keywords (
    enrichment_id TEXT NOT NULL REFERENCES message_enrichments(id) ON DELETE CASCADE,
    message_version_id TEXT NOT NULL,
    ordinal INTEGER NOT NULL,       -- 模型给出的顺序，即重要度次第
    raw TEXT NOT NULL,              -- 模型原始写法，用于展示
    normalized TEXT NOT NULL,       -- 字面归一化结果，用于匹配
    kind TEXT NOT NULL,             -- entity / topic / event
    weight REAL NOT NULL DEFAULT 0, -- 模型给出的重要度 0~1
    PRIMARY KEY (enrichment_id, ordinal)
);
CREATE INDEX idx_keywords_normalized ON enrichment_keywords(normalized);
CREATE INDEX idx_keywords_version ON enrichment_keywords(message_version_id);
```

- **行数据永不改写**：合并只写 `keyword_aliases`，关键词行保持模型原始输出。解析别名在查询与统计时进行，路径压缩保证每个别名只需一跳；SQL 形态是 `normalized = ? OR normalized IN (该 canonical 的别名集合)`，两段都走索引，不需要递归 CTE。
- 检索端点 `GET /api/messages?keyword=&kind=`：命中口径是归一化并解析别名后的精确匹配，不再用 `LIKE` 打 JSON；
- **修掉 LIKE 通配符**：原文/译文/摘要的兜底检索必须转义 `%` 与 `_`（当前搜 `%` 命中全部）；
- 排序键从 `m.updated_at` 改为 `COALESCE(v.published_at, v.collected_at) DESC`；新增 `since` / `until` 参数；
- 新增 `GET /api/messages/{id}/related`：按共享关键词（解析别名后）的交集排序（实体优先、再按时间邻近），这是无向量版本的"相关消息"，也是文章聚合的雏形；
- 频次统计口径：只统计每个版本**当前生效**的那套加工结果，历史 `(prompt_version, model)` 版本保留审计但不进词表统计，否则旧词会长期占据榜单。

### M5 热词注入与常驻词（第二期）

- 提示词新增占位符 `{{vocabulary}}`；`domain/prompts.py` 的 `TASK_SPECS.variables`、`SAMPLE_VALUES` 与界面占位符提示同步；
- 注入内容按 `kind` 分组，取"频次降序 + 最近出现降序"的前 N（默认 150，可配），另附"近 7 天新增"一段；排序与渲染必须确定性，否则同一输入重跑结果不可比、`llm_calls.input_hash` 也无法解释；
- 注入前先解析别名，被合并掉的写法不再进热词表——这是防止合并回潮的关键一环；
- 常驻词（pin）：人工在词表页标记，永远出现在热词表，解决周期性话题被反复重新发明的问题；
- 提示词要求模型自报每条关键词是"复用词表"还是"新建"，作为收敛度的观测指标；
- 新增 `vocab_revision`（词表每次新增或合并 `+1`）写入 `message_enrichments`；**不进幂等键**（避免一次合并触发全量重跑），另提供"重跑受影响版本"入口。

### M6 词表页与合并（第二期）

- 新增页面 `/settings/keywords`，进入现有 React 应用与导航，遵守 [Web 界面规范](../项目说明/Web界面规范.md)：`.page-wide` 容器、加载/空态/错误态完整、键盘可操作、破坏性操作先说明影响；
- 展示**全量**词表：词、类型、频次、首次与最近出现时间、是否常驻、示例消息。不能只展示时间窗内的词，否则被重新发明的旧写法永远看不见、也合不了；
- 默认按频次降序，只出现 1 次的词折叠在"仅出现一次"分组里（当前占 90%，是噪声主体）；
- 合并：多选 → 指定目标词 → 预览影响面（受影响消息数）→ 执行 → 写别名表；支持撤销；
- 合并后同一条消息内可能出现两个相同关键词（解析后）：按消息去重，保留更具体或权重更高的那条；
- 合并建议：把词表分批交给模型，返回疑似同指组，人工确认后执行，把工作面从几千个词降到几十组；
- 上下位关系不用合并表达，留给后续的 `broader` 分组。

### M7 回填与度量

- 回填：可预览、可限量、可筛选（来源/时间）、幂等，复用现有任务表与独立 worker，不引入第二条执行路径；
- 度量口径固定为四项，作为本阶段的验收指标：
  - 泛化词占比（当前 35%）
  - singleton 占比（当前 90%）
  - 词表复用率（模型自报复用 ÷ 全部关键词；改造前无此数据，从零起算）
  - 词表规模与合并次数
- 基线必须在 M1 完成后重测，不能与旧提示词的数据相比。

## 5. 提示词改造（全文）

`prompt-enrich` 的 user 模板改为：

```text
你是科技资讯编辑。请阅读以下内容，用简体中文产出便于浏览和检索的结果：
title 是精简标题，不超过 40 字，保留关键主体，不添加原文没有的信息；
summary 是 1 至 3 句摘要，说明发生了什么；
keywords 是供检索用的索引标签，最多 6 个，宁少勿多；没有值得检索的词就返回空数组。

判断一个词该不该收，只有一条标准：别人会不会用它来查找这条消息。
- 优先具名实体：公司、产品、模型、人物、机构、地点、法规、专有技术名。保留原文写法，不要译成中文。
- 其次是有信息量的主题词：能概括话题的领域词。
- 不要泛化的动作、流程和抽象名词，它们在多个行业通用，检索不出任何东西；不要产出只在正文里才成立的数值和指标，那些写进 summary。
- 一条消息最多 1 个事件词，用一句话概括，不要把一个事件拆成多个碎片。
- 同一概念只用一种写法，不要中英文各出一份。

必须只返回 JSON 对象，字段严格为 title、summary、keywords（字符串数组），不要 Markdown 包裹。
标题：{{title}}
摘要：{{summary}}
正文：{{content}}
```

M2 落地时，`keywords` 的字段说明改为对象数组（`text`/`kind`/`canonical`/`weight`），并在模板里声明 `kind` 的取值含义；M5 落地时增加 `{{vocabulary}}` 段落与"复用还是新建"的自报字段。

## 6. 时效性（跨模块约束）

- 时效性不进关键词 schema：它是相对查询时刻的量，不让模型输出 `fresh`/`evergreen` 之类的枚举；
- 时间语义：`published_at`（发布）与 `collected_at`（采集）不可互换，前者回答"消息多新"，后者回答"什么时候拿到的"，排序与筛选用 `COALESCE(published_at, collected_at)`；
- 注入提示词的必须是**消息自身时间**（`published_at ?? collected_at`）与"采集于"，不是服务器当前时间：加工任务排队执行，回填 1798 条存量时若注入"现在"，模型会写出"今日发布"而那条实际是 255 天前；
- 时间衰减排序（`score × exp(-Δt/τ)`，τ 按 kind 分档）与线索活跃度（`first_seen_at`/`last_seen_at`、近 24h/7d 计数、聚合窗口、新鲜度门槛）属于文章生成阶段；本文只保证这些指标能从 `enrichment_keywords` join 消息时间直接算出，不提前加字段。

## 8. 本阶段不做

- 文章生成与发布：跨多条消息的聚合任务，需要新的输入范围与结果模型（见[决策记录：提示词库与任务分配](../决策记录/2026-10-09-提示词库与任务分配.md)的扩展缝）；
- 向量检索与语义去重；
- 上下位词表与 `broader` 分组；
- 时效性排序界面与衰减参数调参；
- FTS5：先在真实数据量下验证关系表 + 索引是否够用。

## 9. 风险与待定

1. **关键词变少会降低召回。** 宁少勿多必须与 M5 热词注入配套：靠共用同一个词表提升聚合召回，而不是靠每条多产词。只砍词不加词表约束，聚合效果会更差。
2. **热词注入降低多样性。** 热词表被某个领域占满时，模型可能把不相关的新词硬塞进已有词条；提示词明确"只在确实指同一事物时复用"，并用复用率度量。
3. **合并可能回潮。** 别名不参与热词注入时，模型会再次产出被合并掉的写法；M5 的别名解析是唯一防线。
4. **合并是破坏性的。** 别名表 + 撤销保证可回退；不提供就地覆写（默认不做），因为覆写不可逆且丢失模型的原始输出。
