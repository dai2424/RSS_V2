# 决策记录：关键词结构化与检索

> 状态：已实施（2026-10-09，阶段 2 第一期）
> 背景：关键词此前是"给列表看的标签"——3 至 8 个自由字符串，存在 `message_enrichments.keywords_json` 里，检索用 `LIKE` 打在这个 JSON 文本上。实测结果是：搜 `AI` 会命中 `OpenAI`，搜 `%` 命中全部；15 条消息产出 93 个词，90% 只出现一次，其中 35% 是 `发布公告`、`检测`、`重置` 这类泛化词；同一事件的两条消息事件词各写各的，无法聚到一起。列表还按"最近入库"排序，一次批量采集就把历史旧闻顶到最前。

## 结论

1. **关键词从字符串数组改为对象**：`{text, kind}`，`kind` 取 `entity` / `topic` / `event`。上限从 8 降到 6，与提示词一致。`text` 保留模型原始写法只用于展示；匹配键 `normalized` 由领域纯函数从 `text` 算出，检索、去重、统计只用它——归一化必然有算错的时候，展示层不能跟着错。
2. **归一化只做字面等价**：Unicode NFKC（全角折半角）→ 大小写折叠 → 去掉所有空白 → 剥离首尾标点。不做分词，不做"去公司后缀"（`尊界汽车` → `尊界` 是语义判断，属于第二期的人工合并）。去掉空白让 `AI 助手` 与 `AI助手` 落在同一个匹配键上；内部标点保留，避免把 `GPT-6.1` 与 `GPT6.1` 合并。
3. **准入判据写进提示词，而不是只给数量配额**：旧提示词只说"3 至 8 个检索关键词"，模型凑不满就用泛化词填。新提示词给一句判据——"别人会不会用它来查找这条消息"，优先具名实体并保留原文写法，不产出泛化动作词与只在正文成立的数值，事件词最多一个，允许返回空数组。
4. **新增关系表 `enrichment_keywords`（迁移 0012）**：每行一个匹配键（`raw` 展示、`normalized` 匹配、`kind` 类型、`ordinal` 重要度次第）。检索、相关消息、统计都走这张表，不再碰 JSON。**行数据永不改写**：合并将写别名表而不是覆写行，为第二期的人工合并留出可撤销的余地。
5. **索引与快照分离**：`keywords_json` 保留为模型当时的输出快照（审计与重建索引用），关系表是唯一的检索面。写入在同一个事务里完成，不允许出现半更新状态；同一匹配键在一次写入中只保留第一次出现，避免 `OpenAI`/`openai` 这类重复写法让频次与相关度重复计数。
6. **检索语义**：`GET /api/messages?keyword=` 按匹配键**精确或前缀**命中，`kind` 可收窄。用前缀而不是包含匹配，是为了让"尊界"命中"尊界v800"（同一主体的不同粒度），同时让 `AI` 不再命中 `OpenAI`。全文兜底参数 `q` 的关键词部分改为查关系表，原文、译文、加工标题与摘要仍用 `LIKE`，但**补上了通配符转义**（旧实现搜 `%` 或 `_` 命中全部）。
7. **排序按发布时间**：`ORDER BY COALESCE(published_at, collected_at) DESC, m.id`，新增 `since` / `until`（UTC 秒，同一口径）。发布与采集两种时间不可互换：实测两者平均相差 2.6 天、最大 255 天，用采集时间判断"新鲜"会把回溯补录的历史旧闻当成新消息。
8. **相关消息（无向量的线索检索）**：`GET /api/messages/{id}/related` 按共享匹配键找其他消息，计分实体 4 分、主题 2 分、事件 1 分，同分按发布时间新近。只比较每条消息最新版本里"当前生效"的加工结果，避免历史提示词版本的关键词继续参与匹配。这是文章生成阶段聚类键的雏形。
9. **存量处理分两步，都不调用模型以外的路径**：
   - `POST /api/keywords/rebuild`：按已存的 `keywords_json` 重建关系表（老行是字符串数组，按主题词折算），本地操作、可重复执行；
   - `POST /api/keywords/backfill?dry_run=`：为没有成功加工结果的消息入队，先预览条数再执行，复用单条入队的提示词解析、Key 选择与幂等键，缺提示词或缺 Key 只跳过并回报原因。**回填不套用自动入队的长度阈值**：回填是人工触发、可预览、可限量的动作，目的是补齐存量；自动入队才需要靠阈值控制日常成本。
10. **提示词 v2 由迁移种子化**：归档该任务类型下所有启用版本后插入新版本，版本号取 `MAX(version)+1`（用户若已自建过 enrich 版本不会撞 `UNIQUE(prompt_key, version)`）。被归档的版本仍在提示词列表中，可随时重新启用；历史结果的 `prompt_version` 保持可回溯，幂等键不受影响。

## 与计划的偏差

阶段计划（[2-关键词与检索_AI.md](../阶段目标/2-关键词与检索_AI.md)）把别名表放在第一期，实施时调整了三处，理由如下：

1. **别名表与人工合并推迟到第二期**：本期没有任何代码会写入别名，"只有表没有产出方"的结构是死代码（开发规范第 4 节：不为假想的未来预先创建 Repository）。合并与词表页一起在第二期落地，届时 `normalized` 行数据仍然不需要改写，所以不会返工。
2. **不引入 `weight` 字段**：重要性用模型给出的数组顺序（`ordinal`）表达即可，不必让模型再给一个无法验证的 0~1 数值。
3. **M1 的过渡提示词不再单列**：结构化输出本身就要求提示词同时改掉准入判据，两版合成一个 v2 更省一次版本噪声；代价是"单独验证准入判据效果"的对照测量没做，基线口径改为改造前后对比（35% 泛化词、90% singleton 是改造前的数）。

## 影响范围

- 领域：新增 `domain/keywords.py`（`Keyword`、`KeywordKind`、`normalize_keyword`、`normalize_keyword_list`、`RelatedMessage`、`KEYWORD_LIMIT`）；`EnrichmentResult.keywords` 与 `Enrichment.keywords` 类型改为 `tuple[Keyword, ...]`。
- 端口：`MessageRepository.list_messages` 增加 `keyword`/`kind`/`since`/`until`；新增 `KeywordRepository`（重建索引、相关消息、回填候选）。
- 适配器：新增 `adapters/sqlite/keywords.py`（关键词 SQL、编解码、索引写入、相关消息与候选查询的唯一入口）；`messages.py` 与 `enrichments.py` 复用它的共享件，`messages.py` 因此保持在规模阈值内；`adapters/llm/boundary.py` 的 `EnrichmentResponse` 改为结构化校验，未知 `kind` 与纯字符串都折算为主题词。
- 服务：新增 `services/keywords.py`（`KeywordService`、`BackfillResult`）；`MessageService.list` 透传新参数。
- API：`GET /api/messages` 新增查询参数，新增 `GET /api/messages/{id}/related`、`POST /api/keywords/rebuild`、`POST /api/keywords/backfill`；`EnrichmentResponse.keywords` 改为对象数组。
- 数据：迁移 0012（`enrichment_keywords` + 结构化提示词种子）。历史行不迁移，由 `rebuild` 补齐。
- 前端：关键词徽标展示 `text` 并用提示说明 `kind`；消息详情新增"相关消息"区块；`Badge` 支持透传 HTML 属性以便挂提示。
- 已知的存量问题：`domain/models.py` 在本次改动前已超过 400 行阈值（474 行），本次只改了两处类型与一行导入，未继续放大；拆分留待后续单独评审。
