# 决策记录：提示词的就地编辑与删除

> 状态：已实施（2026-10-09）
> 背景：提示词入库后界面只有"读 + 基于此版本新建 + 归档"。用户反馈缺三件事：不能新建一个全新提示词、不能改已有版本的文本、不能用不到时删掉它。但版本串 `{prompt_key}-v{version}` 是审计与幂等键的锚点，一旦被引用就不能再改或删，所以这三件事必须先定义"什么算被使用"。

## 结论

1. **判定口径只有一处实现**：`PromptService.usage(prompt_id)` 调用 `PromptRepository.usage`，一次查四类引用并返回 `PromptUsage`。

   | 引用 | 查询 | 为什么算 |
   | --- | --- | --- |
   | 模型调用 | `llm_calls.prompt_version = ? OR prompt_version = ? \|\| '+prompt-test'` | 审计里已经写着这个版本串 |
   | 结果记录 | `translations.prompt_version`、`message_enrichments.prompt_version` | 译文与加工结果按版本串回溯提示词 |
   | 排队/历史任务 | `json_extract(tasks.payload_json,'$.prompt_id') = ?` | 任务快照指向这条记录，排队中的任务还会读它 |
   | 来源/分类分配 | `task_settings.prompt_id = ?` | 分配指向这条记录，删掉会让来源失去提示词 |

2. **版本串必须精确匹配**，不能用 `LIKE '%版本串%'`：`translation-v1` 会误命中 `translation-v10`，把 v10 的调用算到 v1 头上。集成测试为此专门建了 v1 与 v10 两个版本，只让 v10 被调用，断言 v1 仍可编辑。

3. **试跑算"已使用"**：试跑会往 `llm_calls` 写 `{版本串}+prompt-test`。按第 1 条口径它属于审计引用，因此**试跑过的草稿不能再就地编辑**。这是有意的——审计里已存在该版本串，改文本会让这条记录指向不存在的文本；界面在试跑按钮旁用文字说明这一后果。

4. **就地编辑**：`PATCH /api/llm/prompts/{id}` 改 `name` / `system_template` / `user_template` / `note`，不动状态、业务键与版本号，因此版本串保持稳定。前置校验两条：先 `compile_prompt`（不通过抛 `prompt_invalid`），再判 `usage.used`（已引用抛 `prompt_used`，提示另存新版本）。`name` 留空时回落到 `prompt_key`。

5. **真删除**：`DELETE /api/llm/prompts/{id}` 返回 204，只对"从未被引用"且"不是当前启用版本"的记录生效。被引用抛 `prompt_used`（引导归档）；启用中抛 `prompt_active`（先启用另一个版本）。启用中即"该任务类型的唯一启用版本"——迁移 0010 的唯一索引保证每类任务最多一个启用版本，删掉它会让未绑定提示词的来源拿不到提示词。

6. **`used` 是派生值而不是存储字段**：`PromptUsage` 只存四项计数，`used` 由它们推导，避免出现"计数非零却标记未使用"的矛盾状态。

7. **界面比后端更保守**：就地编辑按钮只对**草稿且未被引用**的版本开放（后端允许未被引用的归档版本也改），删除按钮在"被引用或正在启用"时禁用。禁用原因用文字写在操作区下方（"已被 N 次模型调用、N 条结果引用…只能另存为新版本或归档"），不靠颜色或图标表达。

8. **新建提示词用页面内表单，不用弹层**：Web 界面规范 §4/§6 明确要求提示词这类长正文在页面内编辑、编译错误留在页面内。因此"新建提示词"在提示词页展开一块表单（任务类型下拉 + 业务键 + 名称 + 模板 + 编译预览），而不是计划书原写的 Dialog；业务键在界面提示规则（小写字母、数字、短横线，`^[a-z0-9][a-z0-9-]{0,40}$`）。

9. **删除确认说明对象与影响**：确认弹层写出要删的版本串、名称、状态，以及"没有被任何调用、结果、任务或来源分类引用"和"不可恢复，想保留历史可改用归档"。

## 追加：入库之前的任务快照继续可执行（2026-10-09）

现场反馈：一批内容加工任务全部失败，报"任务快照的提示词已不存在，请重新创建任务"，
而内置提示词 `enrich-v1` 明明还在。查库发现这些任务的 `payload_json` 里**只有
`prompt_version`、没有 `prompt_id`**——它们是**提示词入库之前**的代码（旧进程）写下的快照，
提示词当时还硬编码在适配器里，所以快照里没有 id。新代码按 id 取版本，取不到就判失败，
于是这批任务既跑不了、`重试任务` 也救不回来。

升级不该让排队中的任务变成死信，因此补一条兼容路径：

1. **按版本串找回**：`PromptResolver.snapshot(prompt_id, version_string)` 先按 id 取，
   取不到再用 `prompt_version` 经 `PromptRepository.by_version_string` 取同一条记录；
   两者都对不上才仍报 `prompt_missing`——不猜、不回退到"当前启用版本"。
2. **版本串从右侧拆分**：`Prompt.split_version_string` 用 `rpartition("-v")`，因为业务键
   本身允许短横线与数字（`news-v2` 的 v3 是 `news-v2-v3`，从左拆会切错）。
3. **这种引用也算"被使用"**：`PromptRepository.usage` 的 tasks 统计同时覆盖
   `payload_json.prompt_id = ?` 与"没有 prompt_id 但 prompt_version = ?"两种形状。
   否则一个只被旧形状任务引用的版本会被判成"未使用"而允许删除，删掉同样让任务变成死信。
4. **不改任务快照**：兼容是读取侧的，不给历史任务回写 payload——回写等于篡改当时的执行依据。

三个集成用例固定这条口径：旧形状快照能跑通并写出与版本串一致的结果；既无 id 又无版本串时
仍然明确失败；只有旧形状引用的版本不能被编辑或删除。

## 影响范围

- 领域：新增 `PromptUsage`（`used` 为派生属性）。
- 端口：`PromptRepository` 增加 `usage`、`update_content`、`delete`（7 → 10 个方法）。
- 适配器：`adapters/sqlite/prompts.py` 实现三者；`update_content` 只写内容与 `updated_at`。
- 服务：`PromptService` 增加 `usage`、`update`、`delete`；新建/就地编辑/试跑共用 `_compile_or_fail`，编译校验不再有三份重复。
- API：新增 `GET /api/llm/prompts/{id}/usage`、`PATCH /api/llm/prompts/{id}`、`DELETE /api/llm/prompts/{id}`（204），端点数 8 → 11；新增 `PromptUpdateRequest`、`PromptUsageResponse` 与 `prompt_usage_response`。
- 前端：`usePrompts` 增加 `usePromptUsage`、`update`、`remove`（新建全新提示词复用既有 `create`，同一 POST 不另写一份）；`PromptEditor` 扩成 create / edit / version 三种模式，编译结果面板拆到 `PromptCompilePreview`；新增 `PromptDeleteDialog`；详情页操作区改为 启用 / 归档 / 编辑 / 另存为新版本 / 删除 并展示使用情况。
- 数据：无迁移（不动表结构）。

## 明确不做

- 不做提示词导入导出、版本对比（diff）、按来源批量改提示词。
- 不放开"已被引用"版本的就地编辑或删除——那会破坏审计与幂等键的可回溯性。
- 不新增任务类型（文章生成与调研仍是后续独立工作）。
