# 阶段目标 1：RSS 订阅与英文内容中文化（AI 需求拆分）

> 状态：AI 整理稿 v0.2（本阶段实现已完成；历史自动化验收见文末）
> 更新：2026-10-08，按用户要求取消手机与窄屏验收，桌面验收结果单独记录。
> 来源：[1-RSS订阅_人工.md](1-RSS订阅_人工.md)
> 文档关系：`1-RSS订阅_人工.md` 是用户原始目标和优先级；本文负责模块化、补充验收条件和实现边界。两者冲突时，以人工文档为准。

## 1. 阶段目标

建立一条可维护的 RSS 来源管理与英文内容中文化闭环：

    维护来源
    → 检查来源健康
    → 采集并保存原文
    → 对英文内容生成中文版本
    → 记录任务、模型和失败原因

第一版先验证来源管理、采集、版本和翻译任务；不实现图谱、影响分析和文章发布。

## 2. 模块划分

### M1 来源注册与分类

用户可以在 Web 界面：

- 新增 RSS 来源；
- 编辑名称、URL、平台、语言和行业分类；
- 启用或停用来源；
- 删除来源（连同已采集的消息、版本、译文、健康记录、采集结果与相关任务）；不可恢复，前端必须说明对象与影响后确认；
- 查看来源 ID、创建时间和更新时间；
- 测试来源地址和解析结果。

约束：

- 每个来源有稳定 ID；
- URL 必须是可解析的 HTTP(S) 地址；
- 行业分类不能为空；
- 停用只影响后续采集，不删除历史消息；
- 删除是破坏性操作，与停用语义分开：删除后未完成的采集运行移除该来源并按剩余任务收敛状态，v1 导入映射同步清理以便重新导入；
- URL、名称和分类的校验错误必须在表单附近说明。

### M2 来源元数据与健康

保存 RSS 返回的可复用元数据：

- feed 标题和链接；
- feed 描述；
- 声明语言；
- 作者或组织信息；
- 更新时间；
- 平台和来源类型；
- 时间偏移配置；
- 扩展字段 JSON。

保存最近健康结果：

- 检查时间；
- HTTP 状态；
- 请求耗时；
- 解析是否成功；
- 获取条目数；
- 最近成功时间；
- 错误分类和可读错误信息。

健康信息不能覆盖来源基本配置，也不能因为一次失败自动停用来源。

### M3 RSS 采集与消息版本

采集器统一输出：

- 来源 ID；
- 外部条目标识；
- 标题；
- 正文或摘要；
- 原文 URL；
- 发布时间；
- 采集时间；
- 语言；
- 内容哈希。

行为要求：

- 使用 `source_id + external_id` 做第一重幂等；
- 使用规范化 URL 和内容哈希做第二重判断；
- 同一内容重复采集不生成新消息；
- 内容变化时保存新的消息版本；
- 单个来源失败不阻塞其它来源；
- 每次采集记录新增、更新、跳过和失败数量。

### M4 英文内容中文化

翻译仅针对被识别为英文的消息版本：

    英文消息版本
    → 语言判断
    → 创建翻译任务
    → LLMProvider 生成中文版本
    → 校验并保存译文

要求：

- 原文永远保留，译文不能覆盖原文；
- 译文与具体原文版本关联；
- 中文消息默认不重复翻译；
- 相同消息版本和翻译配置重复执行不重复调用模型；
- 翻译失败可重试，并保留失败原因；
- 译文标记为机器生成，可区分未翻译、翻译中、已完成和失败；
- 保存 provider、模型、prompt 版本、耗时、token 用量和任务 ID；
- 用户可以在详情页切换原文和译文。

业务层只能调用 `LLMProvider`，不能直接依赖模型 SDK 或 HTTP 客户端。

### M5 Provider 与 API Key 池

第一版支持多个模型服务配置，但不在业务代码中硬编码密钥：

- provider 名称；
- 兼容 API 地址；
- 模型名称；
- 优先级；
- 启用状态；
- 超时和重试策略引用；
- API Key 引用名；
- 最近成功和失败状态。

调度规则：

1. 只从启用的 provider 中选择；
2. 按优先级从高到低尝试；
3. 429、超时和 5xx 进入短暂冷却；
4. 格式错误记录失败，但不能无限重试；
5. 当前 provider 不可用时允许切换到下一个 provider；
6. 前端只显示 Key 掩码或引用名，不能返回原始 Key。

原始 Key 第一版放在仓库外的环境变量或系统配置中；Web 界面只管理 provider 的非敏感配置和启停状态。默认模型可以配置为 `deepseek-v4.1-flash`，不能写死在业务代码中。

### M6 任务与审计

翻译使用统一任务机制：

    创建翻译任务
    → worker 领取
    → 执行翻译
    → 保存译文或错误
    → 更新任务状态

任务至少有：类型、幂等键、状态、尝试次数、租约时间、输入版本、输出版本、错误分类和创建时间。

模型调用写入 `llm_calls`，默认保存元数据和输入摘要哈希，不保存未经脱敏的完整 prompt 或 API Key。

### M7 Web 页面

第一版页面：

1. **来源列表**：搜索、分类筛选、启停状态、最近健康状态；
2. **来源编辑**：基本配置、语言、行业分类、时间偏移；Provider 通过全局模型配置页的优先级与启停选择；
3. **来源详情**：元数据、健康记录、最近采集结果；
4. **消息列表与详情**：来源筛选、搜索、原文、译文、版本、翻译状态和错误信息；
5. **任务状态**：采集与翻译任务的排队、运行、完成、失败和重试；
6. **模型配置**：Provider 新增、编辑、启停，Key 引用及优先级管理。

页面遵守 [Web界面规范.md](../项目说明/Web界面规范.md)：

- 仅面向电脑浏览器，最低支持 1280px 内容区宽度，以 1440px 为设计基准，验收覆盖 1280、1440、1920px；

- 有加载、空态、错误和提交中状态；
- 失败时保留用户输入；
- 状态同时显示文字，不能只依靠颜色；
- 详情页可以直接打开并返回列表后保留筛选状态；
- API Key 永远不以明文出现在页面、日志或错误提示中。

## 3. 最小接口

第一版 API 至少包含：

    GET    /api/categories
    POST   /api/categories
    GET    /api/sources
    POST   /api/sources
    PATCH  /api/sources/{source_id}
    DELETE /api/sources/{source_id}
    POST   /api/sources/{source_id}/test
    GET    /api/sources/{source_id}/health
    POST   /api/collection/runs
    GET    /api/messages
    GET    /api/messages/{message_id}
    POST   /api/messages/{message_id}/translate
    GET    /api/tasks/{task_id}
    GET    /api/tasks
    POST   /api/tasks/{task_id}/retry
    GET    /api/llm/providers
    POST   /api/llm/providers
    PATCH  /api/llm/providers/{provider_id}
    POST   /api/llm/providers/{provider_id}/keys
    PATCH  /api/llm/providers/{provider_id}/keys/{key_id}

API 返回结构由 Pydantic 模型定义，并通过 OpenAPI 生成前端类型。

实现和验证记录见 [1-RSS订阅_实现_AI.md](1-RSS订阅_实现_AI.md)。

## 4. 验收标准

### 来源管理

- [x] 用户可以新增、编辑、启用和停用来源；
- [x] 用户可以删除来源；删除前说明对象与影响（含消息条数），相关消息与任务一并清理；
- [x] 来源可按行业分类和启停状态筛选；
- [x] 停用来源后历史消息仍可查询；
- [x] RSS feed 元数据和最近健康结果可查看；
- [x] 错误 URL 和解析失败有明确反馈。

### 采集与版本

- [x] 同一 fixture 重复采集不会产生重复消息；
- [x] 内容变化会产生新版本，旧版本仍可查看；
- [x] 一个来源失败不会影响其它来源；
- [x] 采集运行统计可查询。

### 中文化

- [x] 英文消息可以创建翻译任务；
- [x] 原文和译文同时保留；
- [x] 同一消息版本不会重复调用模型；
- [x] fake provider 可以完成离线测试；
- [x] provider 失败后可以重试或切换；
- [x] 译文详情能看到模型、版本和任务状态。

### 安全与可维护性

- [x] 原始 API Key 不进入 Git、数据库、日志和 API 响应；
- [x] worker 重启后未完成任务可以恢复；
- [x] 测试不写入项目根目录的数据库或 demo 文件；
- [x] 前后端使用生成的 API 类型；
- [ ] 页面在 1280px、1440px 和 1920px 桌面宽度下可完成主流程，Provider/Key 配置在 1280px 可操作。

历史记录：2026-10-07 已完成 1440px、768px 和 390px 主流程验收。768px、390px 自 2026-10-08 起退出当前验收范围，历史结果不作为桌面标准已通过的依据。

## 5. 本阶段不做

- 图谱、实体和跨行业影响分析；
- 文章生成、发布和导出；
- Telegram、X 等非 RSS 特殊来源适配；
- 向量检索和语义去重；
- 多用户、角色权限和复杂组织管理；
- 分布式任务队列；
- 手机及低于 1280px 窗口的专门适配；
- 让前端直接读取或管理原始 API Key。
