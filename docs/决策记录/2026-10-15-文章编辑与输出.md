## 1. 背景与问题

产品要求"用户在系统内修改标题、正文并保存，刷新后内容仍在；复制或导出到个人博客和公众号编辑器；保留 AI 生成版本与人工保存版本及其依据"。当前项目没有编辑器，也没有渲染 Markdown 的前端依赖；公众号编辑器对 HTML 的过滤规则不可控，复杂的富文本编辑器框架（TipTap/ProseMirror）会带来样式与依赖成本。需要冻结首版的最小可用方案与冲突规则。

## 2. 候选方案与决定

| 决策点 | 方案 | 决定 |
| --- | --- | --- |
| 编辑器 | A. 引入 TipTap 等富文本；B. 分节纯文本编辑（标题 + 小标题 + 段落，Markdown 语法）+ 服务端预览 | **B**。正文以结构化 `body_json` 保存，编辑界面按节渲染文本域；不引入编辑器框架，避免样式与依赖成本；Markdown 行内语法（`**强调**`、方括号加圆括号的链接写法）在预览中渲染。 |
| 预览渲染 | A. 前端渲染 Markdown（新增依赖）；B. 服务端渲染受控 HTML，前端只展示 | **B**。与"不把任意外部 HTML 注入页面"一致：服务端用白名单清洗后返回，前端只在预览容器内展示，链接协议只允许 http/https。 |
| 保存模型 | A. 覆盖保存当前稿；B. 每次保存追加 `edited` 版本，记录基础版本 | **B**。产品要求保留人工保存版本与依据；覆盖会丢历史。 |
| 冲突处理 | A. 后写覆盖；B. 基于基础版本检查，冲突返回 409 并由用户选择 | **B**。禁止静默覆盖人工成果。 |
| 复制/导出 | A. 只导出文件；B. 复制（Markdown / 纯文本 / HTML 片段）+ 附件流导出 | **B**。博客用 Markdown，公众号用"纯文本 + 小标题"或内联样式 HTML 片段；导出由 API 以附件流返回，默认不落服务器文件。 |

## 3. 决定内容

### 3.1 正文数据模型

- 保存稿的权威结构是 `article_versions.body_json`：`{sections:[{heading, paragraphs:[str]}], citations:[...], source_list:[...]}`；同时冗余保存 `body_markdown`（便于导出与复制）与 `title`、`lead`。
- 渲染规则（服务端，Markdown 子集）：`#`/`##`/`###` 标题、段落、`-`/`1.` 列表、`>` 引用、`**粗体**`、`*斜体*`、方括号加圆括号的链接写法、行内 `code`、水平线；**不支持原始 HTML**（一律转义），链接协议只允许 http/https。
- 文末来源列表由 `source_list_json` 生成，格式：`标题 — 发布者 — URL`，正文中的引用标记保留可点击链接。

### 3.2 保存与版本

- 保存请求：`PUT /api/projects/{project_id}/articles/{article_id}`，body `{title, lead, sections, base_article_version_id}`。
- 服务端校验：`base_article_version_id` 必须是该项目当前最新的 `saved` 版本（或 `generated` 版本）；不匹配 → 409 `article_version_conflict`，返回服务端最新版本供用户对比（不自动合并）。
- 保存成功：新增 `article_versions` 行（`kind='edited'`、`status='saved'`），`saved_at` 落库，项目状态转 `saved`；响应返回新版本（前端以服务端返回为准显示"已保存"）。
- 保存失败：前端保留当前输入，不解锁离开保护，不显示成功提示。
- 引用校验：人工改动后若引用的 `fact_id/evidence_id/material_id` 不存在于项目 → 400 `article_reference_invalid`；若删除了不再需要的引用，记录到新版本行的 `recheck_fact_ids_json`（标"需重新核对"），不沿用旧稿的核对结论。

### 3.3 预览与状态展示

- 预览接口：`GET /api/projects/{project_id}/articles/{article_id}/preview` 返回 `{html, source_count, citations:[{marker, fact_id, supported}], pending_notes:[...]}`；`supported` 来自事实状态，`pending_notes` 来自未解决的分歧/缺口。
- 界面必须把"AI 生成稿 / 人工保存稿 / 生成中 / 待核对"分开显示，不用同一个徽标混用；历史版本可查看（只读），旧版本不提供"最新版本"类操作。
- 未保存离开保护沿用项目现有 `UnsavedChanges` 组件；刷新后能恢复服务端已保存内容（编辑中的未保存内容不做草稿持久化，提示用户）。

### 3.4 复制与导出

- 复制（前端）：`Markdown`（按 `body_markdown`）、`纯文本`（标题 + 小标题 + 段落，无 Markdown 标记）、`HTML 片段`（服务端渲染并清洗后的片段，内联样式保持最简：标题加粗、段落 `<p>`，不做颜色与字体）。
- 导出（API 附件流）：`GET /api/projects/{project_id}/articles/{article_id}/export?format=md|txt|html`；`Content-Disposition: attachment; filename="{清洗后的标题}-v{版本号}-{YYYYMMDD}.{md|txt|html}"`；标题清洗（去掉路径分隔符与控制字符、截断 60 字符）；默认不写服务器文件，若后续确需落盘，目录由配置项 `export_dir` 决定并位于运行目录内。
- 复制/导出内容必须来自**指定的已保存版本**，不得混入未保存修改或旧生成稿；版本选择由界面显式给出（默认最新 `saved` 版本）。
- 平台验证（P6b）：在用户提供的博客编辑器与公众号编辑器分别粘贴/导入，记录工具、方式、结构（标题、小标题、段落、列表、链接、来源列表）与截图；只做预览与本地保存，不点击发布或群发。未获得平台访问时，交接可复现的输出文件与本地结构检查，并明确标注该平台实测未完成。

## 4. 影响

- 新增 `services/articles.py` 的编辑/保存/预览/导出逻辑与 `api/routers/articles.py`；渲染与清洗集中在服务层的 `render` 模块，前端不引入 Markdown 依赖。
- 导出文件名清洗与受控 HTML 清洗是安全相关代码，需要单元测试（危险协议、控制字符、超长标题、中文标点、`javascript:` 链接、`<script>` 转义）。
- 未保存保护、冲突 409、历史只读是 P6a 的定向 E2E 覆盖点。
