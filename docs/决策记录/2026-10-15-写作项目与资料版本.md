## 1. 背景与问题

从"选中一个事件"到"保存一篇文章"要跨越五个阶段（资料、事实核对、提纲、全文、人工编辑），每阶段都有产物与输入版本。若不确定领域关系与版本规则，各任务会各自造表、各自定义"最新版"，导致重生成覆盖人工成果、来源更新改写历史依据。本记录冻结对象、表归属、版本与快照语义，以及任务、预算与校验原则。

## 2. 领域关系（自上而下）

```text
发现批次 discovery_batch            ← 一次"发现选题"的输入范围与输入快照
  └─ 候选 discovery_candidate       ← 同一事件的成员集合 + 推荐理由
       └─ 事件成员集合 lead (kind=discovery) + lead_messages(固定 message_version_id)
            └─ 写作项目 writing_project        ← 用户选定后的写作上下文（唯一入口）
                 ├─ 资料 project_material       ← 原文/外部资料快照（RSS 固定消息版本）
                 │    └─ 证据 material_evidence ← 实际使用的引文片段
                 ├─ 事实 project_fact           ← fact/analysis/speculation + 支持状态
                 │    └─ 事实—证据 fact_evidence
                 ├─ 提示 project_note           ← 分歧、缺口、待核对
                 ├─ 提纲版本 outline_version    ← draft/confirmed/superseded
                 └─ 文章版本 article_version    ← generated/edited，另存不覆盖
```

- **复用 `leads` 作为事件成员集合的唯一容器**：候选与写作项目都用 `lead_id` 指向消息版本集合，成员固定加入时的 `message_version_id`，不新建"事件成员表"。
- `leads` 增列 `kind TEXT NOT NULL DEFAULT 'manual' CHECK (kind IN ('manual','discovery'))`；人工线索页与既有 API 默认 `kind='manual'`（行为不变），发现线索默认不出现在人工线索列表。
- `LeadService.create` 的消息门槛由"≥2"放宽为"≥1"，零条仍报 `lead_needs_members`；去重、20 条上限与无效版本校验保留（`create` 与 `add_messages` 口径一致）。

## 4. 版本、快照与状态

### 4.1 写作项目状态

`status ∈ {materials_pending, materials_ready, outline_ready, outline_confirmed, article_ready, saved}`，只前进不回退，转换由对应阶段的服务在租约内更新：

| 转换 | 触发 |
| --- | --- |
| `(新建) → materials_pending` | 用户选定候选 |
| `→ materials_ready` | P3a 资料任务完成（含部分失败，失败项在资料上标记） |
| `→ outline_ready` | P4 提纲生成（有新 `draft` 版本） |
| `→ outline_confirmed` | 用户显式确认某个提纲版本 |
| `→ article_ready` | P5 生成成功（新 `generated` 版本） |
| `→ saved` | P6a 首次人工保存（新 `edited` 版本） |

### 4.2 版本与快照规则

- **RSS 证据固定到消息版本**：资料行的 `message_version_id` 一旦写入不再变；消息后续更新不改变已有资料与文章依据（B09）。
- **外部资料保存获取现场**：`url/final_url/title/publisher/published_at/fetched_at/content_text/content_hash/byte_size` 全部入库；来源删除时资料行保留，`status` 改为 `unavailable` 并保留原文快照。
- **提纲确认不可变**：`confirmed` 版本不可编辑；修改产生新的 `draft`（`based_on_version` 指向被改版本）并需要重新确认；确认时若已有更新的 `confirmed` 版本，旧版本转 `superseded`。
- **文章另存不覆盖**：重生成写新的 `generated` 行；人工保存写新的 `edited` 行并记录 `base_article_version_id`；删除来源、更新提纲都不改写历史行。
- **同快照重试不产生重复产物**：各阶段结果以内容快照哈希 + 版本号做唯一约束（提纲：`(project_id, material_snapshot_hash, prompt_version, model)`；文章：`(outline_version_id, material_snapshot_hash, prompt_version, model)`），命中已有结果时任务直接完成并复用，不重复调用模型。
- **用户主动重生成**总是产生新版本（幂等键带请求时间戳/序号），不受上面唯一约束限制。

### 4.3 人工编辑与核对状态

- 人工稿不继承"已核对"结论：保存 `edited` 版本时，受影响的事实/引用标记 `needs_recheck`（在 `project_facts.status` 之外，由 P6a 记录在文章行上：`recheck_fact_ids_json`）。
- 人工删除引用或新增事实时，只校验引用关系是否存在（引用必须是本项目已读资料/证据），不据此声称内容真实。

## 5. 阶段任务契约

| 阶段 | 任务类型 | 幂等键 | 完成方式 |
| --- | --- | --- | --- |
| 事件发现（P2a） | `discover_events` | `discover:{scope_hash}:{input_fingerprint}` | 服务自完成（写批次与候选） |
| 资料准备（P3a） | `prepare_materials` | `materials:{project_id}:{lead_snapshot_hash}` | 服务自完成（写资料与证据） |
| 提纲生成（P4） | `generate_outline` | `outline:{project_id}:{material_snapshot_hash}` | 服务自完成（写提纲版本） |
| 全文生成（P5） | `generate_article` | `article:{project_id}:{outline_version_id}:{material_snapshot_hash}` | 服务自完成（写文章版本） |

共同规则：

- 四个类型都进 `WORKER_TASK_TYPES` 与 `LLM_TASK_TYPES`（都走模型），任务 payload 记录 `{provider_id, model, prompt_id, prompt_version}` 快照与阶段输入标识；模型调用一律经 `LLMFailover.execute` 并写 `llm_calls`。
- 每个阶段写库前在同一事务内校验租约（`ensure_lease`）；崩溃后由 `reclaim_expired` 回收，晚到结果被拒绝（B07）。
- 失败分类沿用现有阶梯：`ExternalServiceError`（超时/网络/限流/服务端错误）按冷却重试、最多 3 次尝试；领域错误不重试；失败写 `error_code/error_message`，界面可诊断、可手动重试。
- 任务列表需能显示目标（批次标题 / 项目标题）与阶段参数摘要；`api/routers/tasks.py` 的 `task_type` 过滤正则同步扩展；提示词统计（`PromptUsage.results`）在新增结果表带 `prompt_version` 时同步计入。
- 模型统一经 `LLMProvider`：阶段 4 的四个新类型使用新增的通用结构化方法 `structured(provider, model, secret, prompt, prompt_version, schema, max_output_tokens=...)`，在 `ProtocolRouter` 与两个协议适配器各实现一次，复用 `boundary` 的 JSON 提取、错误分类与脱敏；现有四个方法不动。理由：适配器里已经有四个同构实现，再加四个会变成"第三份以上同构实现"，按开发规范应先抽公共层。

## 6. 生成 schema 与校验原则

新建 `domain/generation.py` 放各阶段结构化输出 schema（Pydantic，可被服务与适配器同时引用，不违反分层）。所有 schema 只使用 ID 引用，服务端负责解析与校验归属。

### 6.1 资料整理（P3b 使用，P3a 不产生）

```text
MaterialDigest{ facts:[{statement, kind, evidence_ids:[...], conflict_note?}],
                gaps:[{text, blocking: bool}],    # blocking=true 表示影响主线
                conflicts:[{text, fact_indexes:[...]}] }
```

### 6.2 提纲（P4）

```text
OutlineDraft{ title, angle,
              sections:[{ heading, talking_points:[str], fact_ids:[...],
                          evidence_ids:[...], impact_notes:[str] }] }
```

校验：`sections` ≥2；每个 `fact_id` 必须属于本项目；`status='missing'` 的事实不能出现在 `talking_points` 的依据里（必须先在 `project_notes` 里解决或标为待核对）；`evidence_ids` 必须属于本项目已读资料的证据；提纲保存时记录 `material_snapshot_hash`（资料包哈希），确认的版本把该哈希与 `project_id` 一起冻结。

### 6.3 全文（P5）

```text
ArticleDraft{ title, lead,
              sections:[{ heading, paragraphs:[str] }],
              citations:[{ marker, fact_id, evidence_ids:[...] }],
              source_list:[{ material_id, title, publisher, url }] }
```

校验原则：

1. `citations` 里的 `fact_id`/`evidence_ids` 必须属于本项目且来自本次输入的资料快照；`source_list.url` 必须等于某个已读资料的 `final_url`（或 `url`），不接受模型自造 URL。
2. 正文中出现的引用标记必须都能在 `citations` 中找到；`citations` 中未被正文使用的条目丢弃并计数（记入生成元信息，不静默）。
3. 关键事实必须带引用；模型输出的 `analysis`/`speculation` 必须带显式类型与依据（`kind` 沿用 `fact/analysis/speculation`），推测文本不得使用确定性表述（校验规则：`speculation` 段落必须包含不确定词表之一，否则该段落降级为 `analysis` 并记录）。
4. 任一必填校验失败 → 该次生成失败（`llm_invalid_output` 或 `article_validation_failed`），不保存"部分合格"的稿件；越界引用一律丢弃并计数，绝不"删掉引用保留结论"。
5. 单来源事件（`source_list` 只有一条）时，正文与分析不得暗示多方共识（提示词约束 + 人工核对项，机器只校验来源数量并写入元信息）。

## 7. 预算（初始值与可配置项）

能实测的标注实测值，其余标"暂定"，实现时写入 `settings.py` 与 `config/settings.example.toml`。

| 项 | 值 | 状态 | 说明 |
| --- | --- | --- | --- |
| 默认窗口天数 `discovery_window_days` | 7 | 产品口径 | 可配 |
| 窗口最大跨度 `discovery_max_window_days` | 90 | 暂定 | 超过返回 400 |
| 窗口内消息上限 `discovery_max_window_messages` | 400 | 实测参考：7 天窗口当前 89 条 | 超限提示缩小范围 |
| 分批条数 `discovery_batch_size` | 40 | 暂定 | 40 条 × 约 1.5k 字符 ≈ 60k 字符输入 |
| 单批输入字符上限 `discovery_batch_chars` | 60000 | 暂定 | 超出时逐条截断摘要并记录 |
| 候选成员上限 `discovery_max_members` | 20 | 沿用线索上限 | 超出截断并展示 |
| 候选总数上限 `discovery_max_candidates` | 30 | 暂定 | 超出按排序保留并展示丢弃数 |
| 每项目搜索查询数 `materials_max_queries` | 3 | 暂定 | 中文、英文、官方站点各一 |
| 每条查询结果数 `search_result_limit` | 8 | 暂定 | SearXNG 返回上限 |
| 每项目读取资料数 `materials_max_reads` | 12 | 暂定 | 含 RSS 原文 |
| 单次读取体积 `article_max_bytes` | 2 MB | 暂定 | 超过记 `article_too_large` |
| 资料/事实阶段模型调用 | 1 次整理 + ≤3 次重试 | 暂定 | 输入 ≤80k 字符 |
| 提纲阶段模型调用 | 1 次 + ≤3 次重试 | 暂定 | 输入 ≤80k 字符 |
| 全文阶段模型调用 | 1 次 + ≤3 次重试 | 暂定 | 输出上限按模型能力取 8k–32k tokens |
| 各阶段单次模型超时 | 沿用 Provider 配置 | 现状 | 需实测是否足够（S03 类长文） |
| 阶段耗时观测 | 记录在任务与 `llm_calls` | 现状 | P5/P7 实测后回填 |

超预算时的行为：搜索结果不足或读取失败只记录缺口，不静默减少；模型调用重试耗尽 → 任务失败并保留已完成产物（资料、提纲、旧稿都不丢）。
