# 决策记录：关键词别名与人工合并

> 状态：已实施（2026-10-09，关键词管理模块第 1 步；统计口径与页面见同竖切后续提交）
> 背景：阶段 2 第一期让关键词有了匹配键与关系表，但同一个概念的不同写法（`AWS` 与 `谷歌云`）在检索、统计与相关消息里仍然是两个词。计划把别名表放在第一期，实施时因为"没有写入方就是死代码"推迟到了这里。

## 结论

1. **合并只处理同指，不处理上下位**：`AWS` / `谷歌云`、`OpenAI` / `Open AI` 可以合并；`尊界` 与 `尊界V800` 不行——那会抹平检索粒度，属于分组（`broader`）而不是合并该管的事。界面文案要明确写出这条边界。
2. **别名一律压平**（迁移 0013 `keyword_aliases`）：`canonical_norm` 永远指向最终规范词，所以解析永远只有一跳，不需要递归 CTE，统计里一次 `LEFT JOIN` 即可。规范词键的唯一表达式是 `COALESCE(a.canonical_norm, k.normalized)`，定义在 `adapters/sqlite/keyword_sql.py` 的 `RESOLVED_KEY`，检索、相关消息与统计共用。
3. **合并可撤销，且支持链式**：`keyword_aliases` 除记录当前指向外，还记录被改写前的 `previous_canonical` 与 `previous_merge_id`；撤销时按原值回填、把本次新建的别名删掉，并给 `keyword_merges` 打上 `undone_at`（不删记录，保留审计）。因此 `A→B` 之后再把 `B` 并入 `C`，可以按逆序逐次解开而不产生漂移。
4. **合并记录里的成员是快照**：`members_json` 保存合并当时的写法列表，只用于展示、不参与查询。这样后续链式合并把别名改指之后，历史记录仍然说清"当时并入了哪些写法"。
5. **检索与相关消息同步接入别名**（这一步不做，合并等于没做）：
   - `GET /api/messages?keyword=` 先把输入解析到规范词，再按规范词键精确或前缀匹配——搜被合并掉的写法会命中它并入的词条；
   - 相关消息的"共享"判定改为比较规范词键，并且同一消息里解析后重复的词只算一次；
   - 相关消息的共享词按**正在看的那条消息**的写法展示，否则合并后同一个概念会在界面上显示成两个不同的词。
6. **合并目标必须是词表里已有的词**：不能凭空造词，否则新词没有频次来源。目标若是别名会先解析到规范词；被合并词与目标相同、或目标不在词表里都明确报错（`keyword_target_unknown` / `keyword_merge_empty`）。合并前提供 `dry_run` 影响面预览（合并后词频、受影响消息数、全部写法），预览与执行共用同一份计算。
7. **新增三个端点**：`GET /api/keywords/merges`、`POST /api/keywords/merge`、`POST /api/keywords/merges/{id}/undo`。

## 影响范围

- 迁移 0013：`keyword_merges`、`keyword_aliases` 与规范词索引。
- 领域：`MergePreview`、`MergeRecord`。
- 端口：`KeywordRepository` 增 `resolve_key`、`merge_preview`、`merge`、`undo_merge`、`merges`。
- 适配器：新增 `adapters/sqlite/keyword_sql.py`（共享 SQL 片段，避免两个模块互相导入形成环）与 `adapters/sqlite/keyword_aliases.py`（别名、合并、撤销、历史）；`keywords.py` 与 `messages.py` 改为引用共享片段，相关消息改用规范词键比较。
- 服务：`KeywordService` 增 `merge_preview`、`merge`、`undo_merge`、`merges`，写结构化日志；输入键统一归一化并解析到规范词。
- 测试夹具：抽出 `tests/integration/keyword_support.py`（造 RSS、配模型、跑 worker、假 provider），检索与合并两个测试文件共用——这是第三份同构实现的抽取点。
