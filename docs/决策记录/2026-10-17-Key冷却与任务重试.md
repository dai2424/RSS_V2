# 决策记录：Key 冷却属于临时状态，模型任务据此重试

> 状态：已接受（修正既有行为；阶段 4 真实环境验证中发现）
> 日期：2026-10-17
> 参与者：lyx（真实环境反馈）、实现 Agent
> 影响范围：`services/llm_failover.py` 的候选与 Key 选择、入队前的可用性检查、模型任务的错误分类；阶段 1 起的全部模型任务类型。
> 依据：[Provider 协议可选](2026-10-09-Provider协议可选.md)、[任务与后台执行](../通用工程规约/任务与后台执行.md)、[技术与架构](../通用工程规约/技术与架构.md)。

## 1. 背景与问题

真实环境（阶段 4 资料准备与整理）出现一串互相牵连的失败：整理任务超时（`llm_timeout`）后，Key 按冷却规则被打上冷却时间；紧接着被 worker 领取的下一个模型任务在冷却期内找不到可用 Key，抛出 `llm_key_not_configured`（"没有可用的模型 API Key"）。该分类属于 `DomainError`，worker 按"配置错误"处理，**尝试 1 次就判为失败**，任务页显示成"没有可用的模型 API Key"，看起来像密钥没配，实际只是 60 秒的冷却窗口。

三个问题叠在一起：

1. **临时状态被报成配置缺失**：冷却由本进程的另一个任务造成，等待即可恢复，却按不可重试错误结束任务。
2. **入队前的检查同样混淆**：`first_available()` 把"冷却中"的 Key 视为不可用，报"没有启用且具有可用 Key 的模型"，与"没配 Key""没启用模型"共用一句话。
3. **同一段检查复制了六份**：翻译、加工、关键词建议、选题发现、资料准备、资料整理各写一遍"取候选、为空就抛错"。

## 2. 决定

1. **Key 冷却一律按可重试处理**：`LLMFailover.execute` 在"候选存在、Key 行存在但全在冷却中"时抛出 `ExternalServiceError("llm_key_cooling", "模型 Key 都在冷却中，稍后自动重试")`。worker 对模型任务类的临时错误按既有规则退避重试（`max(60, llm_retry_cooldown_seconds)`），任务保持排队而不是失败。
2. **"没配 Key"与"冷却中"分开报**：新增 `LLMFailover.require_available()` 供入队前检查，区分三种情况——没有启用模型（`llm_not_configured`）、Key 全在冷却中（`llm_key_cooling`）、没有可用 Key（`llm_key_not_configured`，未配置或已停用）。六个调用点统一改走它，不再各写一份。
3. **只区分冷却，不改冷却策略**：冷却时长、`COOLDOWN_CODES`（`rate_limited` / `llm_timeout` / `llm_server_error`）与"配置类错误不冷却"的规则都不变；本次只修正冷却期的任务语义与报错分类。
4. **连接测试保持原状**：`translation_service.probe` 的 Key 过滤已经区分"未冷却"，其错误文案本就写明冷却，不随本次改动调整。

## 3. 理由

- 冷却表达的是"这个 Key 暂时不可用"，不是"这个 Key 不存在"；把它归成不可重试错误会让一次超时连带杀死后续任务，掩盖真实原因（超时）。
- 重试上限仍是 3 次，冷却结束后自动恢复；真的没有 Key 或模型时，报错分类与文案保持可读，不会因为改成可重试而掩盖配置问题。
- 入队前的检查保留（避免创建必然失败的任务），但分类要能指导用户动作：等一会儿、还是去补 Key。

## 4. 影响

- 行为变化：冷却期内入队返回 `400 llm_key_cooling`（文案"模型 Key 都在冷却中，请稍后重试"），任务页在冷却期领取到的任务显示为排队重试。
- 关键词回填的原因文案：完全没配 Provider 时由"没有启用且具有可用 Key 的模型"改为"没有启用的模型"。
- 测试：`tests/integration/test_recovery.py` 新增"冷却中的 Key 使任务排队重试"与"入队区分冷却与缺 Key"两个用例；`test_keywords.py` 的原因断言随文案更新。
