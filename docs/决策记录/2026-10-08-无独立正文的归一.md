# 决策记录：无独立正文的消息版本归一

> 状态：已实施（2026-10-08）
> 背景：RSS 条目只有 `<description>`（Atom 的 `<summary>`）而没有 `<content:encoded>` 时，采集器把摘要复制进正文。详情页于是把同一段文字按"摘要"和"正文"展示两次，用户无法分辨哪些消息真的有正文。

## 结论

1. **正文为空表示"来源没有提供独立正文"**：`feedparser_client` 不再用摘要兜底正文，`content` 留空字符串；只在来源真的给出 `content:encoded` 时才填充。v1 导入沿用同一口径。
2. **内容指纹口径保持不变**：指纹仍是"标题 + 摘要 + 有效正文"的 SHA-256，其中有效正文在没有独立正文时取摘要（`domain.values.message_content_hash`，`content=None` 表示无独立正文）。这样"来源后来补上正文"会改变指纹，而"采集器不再复制摘要"不会。
3. **迁移 0008 只清空正文、不重算指纹**：`UPDATE message_versions SET content='' WHERE content = summary AND content <> ''`。因为存量行的 `content` 恰好等于 `summary`，清空前后指纹逐字节相同，升级后重新采集同一来源不会被判定为内容变化（`_store_item` 跳过的判据就是指纹相等），不会产生假新版本。
4. **展示必须诚实**：详情页不再渲染空的"正文"块，并在只有描述时说明"该来源未提供独立正文"。列表只展示摘要，不重复正文。
5. **翻译提示词不变**：空正文照常传给模型，不修改 prompt 文本，避免 prompt 版本变更导致新译文与既有译文口径不一致。

## 影响范围

- 领域：新增 `domain.values.message_content_hash`，`feedparser_client` 与 `v1_messages` 共用它（此前是两处重复的 sha256 写法）。
- 数据：迁移 0008 是纯数据迁移，没有结构变更，因此不重建表；`find_by_hash` 去重与版本跳过判定都不受影响。
- 兼容性：旧的 `content == summary` 行升级后 `content` 为空；指纹未变，任务是幂等的，已完成的译文与加工结果仍绑定同一版本。
- 后续约束：任何用正文判断"内容变化"的逻辑都必须使用 `message_content_hash`，不能直接对比 `content` 字符串。
