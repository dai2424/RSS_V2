# 开发规范

本文件约束业务代码如何组织、依赖和验证。技术名称、命令和框架专用规则写入项目自己的技术附录。

## 1. 规则和文档

- [必须] 规范、实现和测试必须保持一致；发现规范未覆盖的设计问题时，先补充决策记录再实现。
- [评审] 每个新增顶层目录、公共接口和基础设施依赖都要说明职责与边界。
- [约定] 规则标注 `[CI]`、`[评审]`、`[约定]` 或 `[可选]`，避免把人工判断伪装成自动检查。

## 2. 分层与依赖

推荐的依赖方向如下：

```text
入口层 ──▶ 应用层 ──▶ 端口 / 接口 ◀── 适配器层
                         ▲             │
                         └── 领域层 ◀──┘
```

- [必须] 领域层只包含领域对象、规则和领域异常，不做网络、文件、进程或存储 IO。
- [必须] 应用层只依赖领域层、标准库和抽象接口，不导入具体存储、网络客户端或第三方 SDK。
- [必须] 适配器层实现端口，负责把外部协议、存储行或第三方错误翻译为项目内部类型。
- [必须] 入口层只负责参数解析、身份边界、用例调用和结果转换，不直接访问适配器。
- [必须] 具体实现只在组合根创建；入口、任务、命令行和测试通过组合根获取依赖。
- [评审] 禁止反向依赖和跨层绕过；必要的例外必须写明原因与替代方案。

## 3. 接口与类型

- [必须] 应用服务的构造参数使用抽象接口，不绑定具体实现类。
- [评审] 新增接口前先确认有两个以上实现、测试替身或明确的替换边界；不为假想需求预建接口。
- [CI] 启用项目语言支持的严格类型检查，并把业务代码纳入检查范围。
- [评审] 类型忽略必须说明原因、影响范围和删除条件。
- [评审] 类型断言只能用于边界库或运行时已验证的数据，并在附近记录安全依据。
- [约定] 外部输入先转换成内部类型，再进入应用层；内部代码不传播未校验的字典或原始响应。

## 4. 错误、日志和可诊断性

- [必须] 业务异常定义在领域或应用边界；适配器异常在端口边界翻译；入口层使用统一错误响应。
- [必须] 禁止裸异常捕获、静默吞错和无上下文重新抛出。
- [必须] 捕获顶级异常时必须记录、分类并返回可诊断但不泄露敏感信息的结果。
- [约定] 日志包含事件名、级别、关联标识和必要上下文；不把密钥、完整凭据或敏感正文写入日志。
- [约定] 可安全跳过的数据必须在代码附近说明跳过原因，不用空的 `except` 隐藏坏数据。

## 5. DRY 与规模

- [评审] 新建模块前先检索已有实现。
- [约定] 两处相同实现可以暂时保留，但要在提交说明中记录；出现第三处前抽取公共层。
- [必须] 不复制目录后只改名称来制造新模块；公共能力只能有一份权威实现。
- [约定] 以下是默认评审阈值，项目可在技术附录中调整：

| 对象 | 默认阈值 |
| --- | ---: |
| 单个生产源文件 | 400 行 |
| 单个函数或方法 | 60 行 |
| 单个类 | 300 行 |
| 单个入口模块的公开操作 | 12 个 |
| 单个存储适配器的公开方法 | 25 个 |

- [评审] 超过阈值时必须说明拆分、保留或调整阈值的理由；不做无领域意义的机械拆分。

## 6. 注释和命名

- [约定] 公共模块、类和函数说明职责、参数、返回值和副作用。
- [约定] 时间戳注明单位和时区；枚举字段列出所有取值及含义。
- [评审] 注释解释非直观逻辑的原因，不重复代码表面语义；代码变化后同步更新过时注释。
- [必须] 命名表达业务概念或技术职责，避免用 `misc`、`helper2` 等无语义名称堆放代码。
