# 技术与架构

本文件用于记录项目为什么选择某种技术和结构，以及什么时候应该重新评估。它不指定具体产品或框架。

## 1. 选型原则

- [必须] 先验证最小可行闭环，再为未来规模保留必要的替换接口。
- [约定] 优先使用当前运行环境已经能可靠承担的能力，外部基础设施必须有明确收益。
- [必须] 业务层只依赖领域对象和端口；存储、网络、消息、文件和第三方 SDK 放在适配器边界后。
- [必须] 运行环境、依赖版本、迁移、构建和测试应可重复。
- [约定] 没有验证的数据和结论标记为“待验证”，不写成既定事实。

## 2. 技术状态

| 状态 | 含义 | 必须记录 |
| --- | --- | --- |
| 已锁定 | 当前阶段直接使用 | 版本、使用范围和替换边界 |
| 待验证 | 先做小实验或基准测试 | 验证问题、样本、通过条件和截止时间 |
| 暂缓 | 当前阶段不引入 | 暂缓原因、重新评估条件和替代方案 |

当验证结果改变结论时，先更新本文件和相关决策记录，再修改实现。

## 3. 模块边界

推荐按职责划分以下模块，可按项目调整名称：

- `domain/`：纯领域对象和规则。
- `ports/`：供应用层依赖的抽象接口。
- `services/` 或 `application/`：用例编排和业务策略。
- `adapters/`：存储、网络、文件、消息和第三方服务实现。
- `interfaces/` 或 `api/`：HTTP、命令行、事件等入口。
- `tasks/`：后台任务定义与 worker（采用任务机制时启用）。
- `bootstrap/`：唯一的具体依赖组合根。

- [必须] 每个模块有单一主要职责和明确输入输出。
- [评审] 跨模块访问必须通过端口、用例或明确的公共读模型完成。
- [必须] 适配器不得反向驱动领域对象的结构；外部模型先转换为内部模型。

## 4. 外部依赖

- [必须] 每种外部能力只保留一个项目内边界；业务代码不得散落调用供应商客户端。
- [约定] 外部请求、超时、重试、错误分类、脱敏和审计集中在适配器或基础设施层。
- [必须] 测试使用 fake、stub 或录制的固定样例，不依赖真实网络或真实服务状态。
- [评审] 新增外部依赖前说明收益、运行成本、故障模式、退出方案和数据迁移影响。

## 5. 反过度设计

- [必须] 不为尚未出现的用例预建复杂框架、通用总线或多层代理。
- [约定] 先用简单实现验证行为；当重复、性能、隔离或可靠性达到记录的触发条件时再抽象。
- [评审] 每个新引入的基础设施都要有删除或替换条件，避免技术债变成永久依赖。
