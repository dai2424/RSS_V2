# 决策记录：结构化输出的容错与失败定位

> 状态：已实施（2026-10-10）
> 背景：线上出现三条内容加工任务反复失败，报错都是"模型返回的结构无法校验：keywords.0（string_type）"，而模型返回的片段明明已经是 `{"text":"ChatGPT","k…`。查下来是两件事：一是**报错位置没有信息量**，二是**旧 worker 进程拿旧 schema 校验新提示词的输出**。

## 结论

1. **定位取最具体的错误**：关键词是联合类型（`str | KeywordItem`），Pydantic 会同时给出"不是字符串"和"对象里哪个字段不对"两条错误，只报第一条就会一直显示 `keywords.0（string_type）`。现在取 `loc` 最深的那条，并去掉联合类型的分支标记（`str`/`KeywordItem`），因此报的是 `keywords.0.text（missing）` 这类能直接动手的信息。
2. **容错只覆盖"不影响语义"的形状打滑**，语义缺失照旧失败：
   - 多余字段忽略（模型多给权重或说明）；
   - 字段名换成 `keyword` / `value` / `name`（Pydantic `AliasChoices`）；
   - `text` 被包成单元素数组；
   - `kind` 写成数字或 `null` → 按主题词处理。
   而 `text` 缺失或为空仍然报错——那才是真的没有可用信息。
   这样一次形状失误不会作废整轮输出，也不会白烧三次重试。
3. **验证器不直接 `isinstance` 裸 `list`**：Pyright strict 下会留下"部分未知"的类型，抽成 `_single_item` 帮助函数做类型收敛（入参是任意 JSON 值，只能用 `object` 收口）。
4. **运维边界（本次线上现象的根因）**：API 与 worker 是**两个独立进程**（`launcher.py` 用 subprocess 分别启动，前端也是启动时重新构建的）。改完代码只重启其中一个，另一个会继续用旧代码跑——旧 worker 用 `list[str]` 校验新提示词产出的对象数组，就会报出 `keywords.0（string_type）` 这种形状的错。**改完代码必须重启 `start.cmd`（两个进程一起）**；已在旧进程里失败过的任务在退避结束后会自动重试。

## 影响范围

- `adapters/llm/boundary.py`：`KeywordItem` 增加字段别名与两种形状容错；`validation_detail` 改为取最深错误并过滤联合分支标记；新增 `_single_item`。
- 测试：`test_recovery.py` 的可恢复形状用例补上四种打滑形状，失败定位用例补上"联合类型要点出内层字段"。
