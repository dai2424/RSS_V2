> 关联决策：[热词注入与合并建议](../决策记录/2026-10-13-热词注入与合并建议.md)（D1–D7 的最终口径以该记录为准）
> 来源：承接[阶段目标 2](2-关键词与检索_AI.md) 第二期的剩余项 M5（热词注入与常驻词）与 M6 未落地部分（模型给出合并建议）；现状数据取自本机运行库 `runtime/db/rss_v2.db`（2026-10-10）。
> 文档关系：本阶段只做"让模型与人工共用同一份词表"。跨消息聚合产出文章是之后的独立阶段，不在本文范围。

## 1. 目标

阶段 2 把关键词从"给人看的标签"改成了"给机器用的检索键"，并把词表摆上了界面。但词表目前只是**被观察**的对象：模型每次加工都从零发明写法（332 个词里 301 个只出现一次），人工只能在事后把已经散开的写法一个个合并。本阶段把词表变成**被使用**的对象：

    每次加工前把现有词表注入提示词（按类型分组）
    → 模型优先复用已有写法，只有确实指新事物时才新建
    → 人工在界面上把词表里残留的同指写法批量收敛（模型给候选，人确认）
    → 词表规模下降、同一事件的消息能被同一批词命中

完成后的可验证行为：同一批消息在词表稳定后重新加工，模型产出的关键词显著偏向复用；词表页能一键标记常驻词、按批生成合并建议并采纳。

### 现状基线（2026-10-10 实测）

| 事实 | 实测值 |
| --- | --- |
| 消息版本 / 有加工结果 | 1832 / 52 |
| 关键词行 / 不同词 | 379 / 332 |
| 只出现一次的词 | 301（90.7%） |
| 来自新提示词 `enrich-v2` 的关键词行 | 30 行，覆盖 6 条消息（其余 349 行来自旧提示词，全部降级为 `topic`） |
| 人工合并次数 | 1 |
| 词表页可见工作面 | 按当前排序需人工浏览 332 个词，其中 301 个是孤词 |

**排期结论（重要）**：M5 会新增 `{{vocabulary}}` 占位符与"复用/新建"输出字段，按阶段 2 的规矩属于**提示词版本变化**，历史结果与新结果不可比。因此"用一批新加工结果重测关键词质量基线"必须放在 M5 上线**之后**执行一次，不能先测一遍再改提示词——那是两次成本、两次结论。本阶段把基线复算列为收尾项 M7。

## 2. 范围

### 包含

- 热词注入：加工（`enrich`）提示词支持 `{{vocabulary}}`，运行时注入现有词表（按类型分组、别名已解析、排序确定、条数可配）。
- 常驻词（pin）：人工在词表页标记，永远出现在注入词表里，不受条数上限与频次影响。
- 复用观测：提示词要求模型自报每条关键词是复用还是新建；**服务端以注入集合为准硬判定**，落库并在概览页给出复用率。
- 词表版本：记录"模型这次看到的词表版本"，写入加工结果，用于解释同一版本前后两次加工结果为何不同。
- 合并建议：把词表分批交给模型返回疑似同指组，落库、可忽略、可采纳；采纳复用既有合并流程（含影响面预览与撤销）。

### 不包含

- 按来源或行业分类定制词表：本阶段词表全局一份，不做分层词表。
- 向量检索、语义相似度合并：建议仍由模型给出、人工确认，不引入 embedding 与近似检索。
- 上下位关系（`broader` 分组）：合并只处理同指，粒度关系留待文章生成阶段。
- 时间衰减排序与线索活跃度：属于文章生成阶段，本文只保证注入与统计所需数据可从现有表算出。
- 文章生成与发布。
- 词表页"查看消息"仍走全文搜索（`/messages?q=`）而非已存在的 `keyword=` 精确检索：这是一处独立的小改动，另立修复，不混进本阶段。

## 3. 约束和前置条件

- 依赖：可用的 Provider 与 API Key（建议与基线复算都会真实调用模型、消耗额度）；worker 可运行；迁移编号从 `0014` 起（现有最新为 `0013_keyword_aliases.sql`）。
- 分层：注入用的词表查询只能经端口（`ports/repositories.py`）进入服务，SQL 只写在 `adapters/sqlite/`；`domain/` 里的渲染函数必须是纯函数。
- 提示词：注入内容与"复用/新建"字段都属于提示词的数据，不能硬编码在 `adapters/llm/`；新提示词走 `llm_prompts` 种子迁移并启用，版本串改变后阶段 2 的旧基线失效（见第 1 节排期结论）。
- 任务机制：合并建议是**请求内的一次同步模型调用**（与提示词试跑同类），不新增后台任务类型——新增任务类型需要按 `0009` 的先例整体重建 `tasks` 表以改 CHECK 约束，代价与本阶段的收益不匹配。若词表规模突破阈值，按第 7 节的触发条件重新评估。
- 确定性：注入文本与批次划分必须可复现（同样的词表输入两次渲染得到完全相同的字符串），否则 `llm_calls.input_hash` 无法解释、建议也无法比对。
- 规模阈值：前端组件默认不超过 200 行。`KeywordVocabulary.tsx` 现为 204 行，加常驻词列前必须先拆分。
- 迁移：只新增编号 SQL，不改历史迁移；旧库升级后 `reused` / `vocab_revision` 为 NULL 的行不参与统计、不得报错。

## 4. 关键决策（已写成决策记录，见[热词注入与合并建议](../决策记录/2026-10-13-热词注入与合并建议.md)）

下表是决策点的摘要；最终口径（含实施细化）以决策记录为准。

| 编号 | 决策点 | 选择 | 理由 |
| --- | --- | --- | --- |
| D1 | 注入内容的形状 | 按类型分组只给词，不给频次与计数；另附"近 7 天新增"一段；**常驻词并入其类型分组并保证出现**（不单列一段，避免同一个词出现两次） | 频次会诱导模型把高频词当成更重要，而注入的目的是复用不是排序；计数还会让同一词表两次渲染产生差异 |
| D2 | 注入条数上限 | 配置项 `llm_vocabulary_limit`（默认 150，`0` 关闭注入）+ `llm_vocabulary_recent_days`（默认 7） | 词表会继续增长，硬编码不可维护；默认值参考现状规模（332 个词）留出增长空间 |
| D3 | 词表版本语义 | `vocabulary_state` 单行表存"注入文本指纹 + 计数"，注入时发现指纹变化则计数 +1，并把当前计数写入 `message_enrichments.vocab_revision`；**只有加工执行推进，编译与试跑不推进** | 无需在写入与合并路径埋钩子（漏一处就会漂移），且语义正好是"模型看到的词表变了"；变更计数无法从事实数据推导，才允许落字段 |
| D4 | 复用率口径 | **纯服务端硬判定**：模型输出归一化后是否落在本次注入集合里即为 `reused`；不要求模型自报"复用/新建"字段 | 自报可以表演性填报，且多一个字段多一条容错路径与一份 token；硬判定下的复用率才是可比较指标 |
| D5 | 合并建议的执行方式 | 请求内同步调用（每批 ≤100 词），结果落 `keyword_suggestions` 表，`keyword_suggestion_batches` 做幂等台账；**任务规格标为不可分配、worker 认领集合显式写成"采集 + `LLM_TASK_TYPES`"** | 复用 `LLMFailover.execute(task_id=None, ...)` 的候选调度与 Key 冷却（试跑已验证可行）；避开重建 `tasks` 表的成本；落库避免重复付费并支持"忽略后不再出现" |
| D6 | 建议的采纳路径 | 采纳不新增合并实现，直接复用既有 `POST /api/keywords/merge`（dry_run 预览影响面），成功后回填 `merge_id` 并可撤销 | 合并的破坏性与可撤销性已经有一套实现和测试，不复制第二套 |
| D7 | 常驻词与合并的联动 | pin 以规范词为键；合并时把成员上的 pin 移到目标词（目标已 pin 则保持），撤销时按 `pinned_json`/`target_was_pinned` 还原；**已知边界：链式合并逆序撤销可能留下一个多余常驻标记，可在界面取消** | pin 表示"这个词必须一直可用"，合并后若 pin 留在被合并的写法上等于失去作用 |

## 7. 风险和取舍

| 风险或取舍 | 影响 | 缓解措施 | 触发重新评估的条件 |
| --- | --- | --- | --- |
| 注入让提示词变长 | 每次加工输入 token 上升，调用成本增加 | 只注入词、不给计数与理由；条数可配；先按默认 150 观察 token 用量 | 单次加工输入 token 明显抬升成本，或前 150 词覆盖率不足 |
| 注入降低多样性（词表被某领域占满） | 模型把不相关的新词硬塞进已有词条 | 提示词明确"只在确实指同一事物时复用"；复用率作为观测指标而非考核指标 | 复用率升高的同时相关消息质量下降 |
| 合并可能回潮 | 模型再次产出被合并掉的写法 | 注入前解析别名，被合并写法不进词表（阶段 2 已定的唯一防线） | 合并记录里出现同一组被反复合并 |
| 建议可能提上下位合并 | 抹平检索粒度（`尊界`/`尊界V800`） | 提示词只判定同指；界面沿用既有"不要合并上下位关系"说明；人工确认 + 可撤销 | 出现把上下位写进建议的批量案例 |
| 词表继续增长导致批次变多 | 人工工作面重新变大 | 建议按频次降序分批，孤词后置；概览给出待处理数量 | 词表超过约 800 词，评估把建议生成改为后台任务类型 |
| 提示词版本变化 | 阶段 2 的旧基线与历史结果不可比 | 排期上把基线复算放到 M11 一次完成；重跑入口单独评审（M12） | 每次改提示词都需要重测基线 |
| 复用率被"表演性填报" | 指标失真 | 服务端以注入集合为准硬判定（D4），自报不落库 | — |
