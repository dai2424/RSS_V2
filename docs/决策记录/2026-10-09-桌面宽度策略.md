# 决策记录：桌面内容宽度策略

> 状态：已实施（2026-10-09）
> 背景：用户在 2K（2560px）屏幕上发现内容只占窗口一半左右，右侧大片留白，提问“部分使用百分比是不是更好”。实测后确认问题不在单位，而在“一套固定上限套所有页面”：列表页上限太低，阅读页反而完全没有行宽上限。

## 实测（改前，浏览器视口 CSS 像素）

| 视口宽 | 内容宽 | 右侧留白 |
| --- | --- | --- |
| 1920 | 1180 | 350 |
| 2560 | 1180 | 990 |

两层上限叠加导致内容宽度不随窗口变化：`.main-content` 1480px 与 `.page` 1180px。1920 及以上内容恒定 1180px。

同一次实测还发现两个反向问题：

1. 消息详情页正文（`article.prose`）没有任何行宽上限，2560 下实测 1130px，约 70 个汉字一行，与规范第 4 节“阅读正文约 48rem”不符；
2. 消息列表摘要列 `.cell-subtitle` 固定 300px，在宽屏下把摘要截成两行，同时右侧留着 990px 空白。

## 结论

1. **不用百分比，按内容类型分三档固定上限。** 百分比与固定值控制的是不同的东西：列表只需要“比 1180 更宽”，阅读正文需要“不管窗口多宽都不超过一行 48rem”。按百分比缩放会让 2K 屏正文变成一行 2000px 以上，并让表格列宽随窗口抖动。

   | 容器 | 用途 | 上限 |
   | --- | --- | --- |
   | `.page-reading` | 阅读页（消息详情） | `calc(48rem + 48px)`，即正文 48rem + 卡片内边距 24px×2 |
   | `.page` | 详情页、表单页 | 1180px（沿用） |
   | `.page-wide` | 六个列表与配置页 | 1600px |
   | `.main-content` | 外壳兜底 | 1800px = 1600 + 两侧内边距上限 64px×2 |

   本项目根字号是 14px，所以 48rem = 672px，16px 正文约 42 个汉字一行。

2. **列表页也保留上限。** 不取消上限的理由是眼动距离：2K 下若不设限，表格可到 2280px，标题与发布时间分居两端无法对照。选 1600px 是因为它在 1920 视口下等于铺满内容区，在 2560 下保留约 590px 留白——留白是刻意的扫描边界，不是没利用的空间。

3. **阅读页容器跟着正文走。** 只给 `.prose` 加 48rem 会让正文缩在 1180px 卡片左侧、右边空一块；因此阅读页容器收成“正文 + 卡片内边距”，整页变成居中的窄栏文章布局。

4. **摘要列上限从 300px 提到 36rem。** 仍保留上限，避免宽屏下一行铺满整个标题列变得难读；标题列变宽后摘要可读字符数约翻倍。

5. **侧栏保持 240px 固定**，导航不随窗口缩放；应用外壳只做兜底，不承担页面宽度决策。

6. **2K 纳入验收范围。** 规范原验收宽度为 1280/1440/1920，1920 及以上内容宽度相同，宽屏问题在 1920 就存在但未被覆盖；现补 2560，并同步三处文档中的宽度口径。

## 影响范围

- 样式：`frontend/src/styles.css` 的 `.main-content`、`.page` 系列（新增 `.page-reading`、`.page-wide`）、`.prose`、`.cell-subtitle`。
- 页面：消息、来源、任务、模型配置、提示词、任务分配六个列表页改用 `.page-wide`；消息详情页改用 `.page-reading`；来源详情与表单页沿用 `.page` 不变。
- 文档：Web 界面规范第 1、3、4、9 节；开发规范第 11 节与技术选型第 9 节的验收宽度。
- 无后端、数据库与 API 变更；无迁移。

## 明确不做

- 不做按窗口比例（百分比 / vw）缩放的布局。
- 不做侧栏折叠、宽屏多栏阅读（正文与版本信息并排）等进一步利用宽屏的改版。
- 不改表单填写宽度（表单卡片仍 760px）。
- 不为手机或窄屏新增适配。
