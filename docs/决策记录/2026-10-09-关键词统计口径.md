# 决策记录：关键词统计口径

> 状态：已实施（2026-10-09，关键词管理模块第 2 步；页面见同竖切后续提交）
> 背景：有了规范词键与合并能力之后，需要回答"词表是在收敛还是在发散"。统计最容易出的问题不是算不出来，而是**同一个数字在不同页面用不同算法**——历史提示词版本、采集时间与发布时间、合并前后的写法，任一处口径不一致，结论就会互相矛盾。

## 结论

1. **三条口径先定死，全模块共用**：
   - 只统计每条消息最新版本里"当前生效"的加工结果（复用 `CURRENT_ENRICHMENT` / `LATEST_VERSION`），否则换过提示词或模型的版本会被重复计数；
   - 时间一律用 `COALESCE(published_at, collected_at)`，与检索和列表排序一致；
   - 词条按规范词键 `COALESCE(a.canonical_norm, k.normalized)` 合并，合并过的写法在词表里只占一行。
2. **聚合 SQL 只有一份**：`adapters/sqlite/keyword_sql.py` 的 `KEY_AGGREGATE` 同时供词表与概览使用；词表列表与计数走同一个 `_filters`，否则分页总数会与页面内容对不上。
3. **词表分两趟查询**：第一趟按条件聚合出规范词（分页 25 条），第二趟只对当前页的词取展示写法与被归并的写法。一次拉全表再在 Python 里聚合在数据量上来后会先崩。
4. **不做无法自动判定的指标**：计划里提过"泛化词占比"，但"这个词是否泛化"是语义判断，程序只能靠启发式猜，猜出来的数字不能用来做决策。因此概览只提供可复算的数字：规范词数、词位数、孤词占比、长尾分布、类型构成、覆盖与回填进度、来源分布。要审视泛化词，用"跨来源高频词"这一类可解释的视图，而不是编一个指标。
5. **类型裁决有明确优先级**：一个词条下的写法可能既有 `entity` 又有 `topic`，词条类型按 `entity > topic > event` 裁决，避免同一词条在类型分布里被算两次。
6. **趋势按真实日历天分桶并补零**：近 N 天（含今天）用消息发布时间分桶，没有数据的天补 0，否则折线会把"没有采集"画成"采集了但没产出"。新增词按该词条的首次出现日归属。
7. **覆盖进度与回填候选必须同源**：概览里的 `pending` 与 `POST /api/keywords/backfill` 的候选条数用同一套判断（没有成功加工结果的最新版本），测试直接断言两者相等——这两个数字是用户判断"还要不要回填"的依据，不能各算各的。
8. **接口形态**：`GET /api/keywords`（词表，`q`/`kind`/`min_count`/`since`/`until`/分页，`min_count` 默认 2 用于折叠只出现一次的写法）与 `GET /api/keywords/overview`（概览 + 类型分布 + 长尾 + 趋势 + 来源分布 + 覆盖与任务计数，一次返回）。概览刻意做成一个端点：页面一次加载、一套加载态，避免多个请求之间出现"半新半旧"的数字。
9. **`api/presenters.py` 拆出 `api/keyword_presenters.py`**：加了关键词与合并的响应转换后该文件超过 400 行规模阈值，按仓库既有做法（`api/schemas` 曾拆成包）把关键词域的搬运分出去，`presenters.py` 回到 282 行。

## 影响范围

- 领域：`KeywordEntry`、`KeywordKindStat`、`KeywordBucket`、`KeywordTrendPoint`、`KeywordSourceStat`、`KeywordOverview`。
- 端口：`KeywordRepository` 增 `vocabulary`、`count_vocabulary`、`overview`。
- 适配器：新增 `adapters/sqlite/keyword_stats.py`（词表）与 `adapters/sqlite/keyword_overview.py`（概览与分布）；共享片段模块补 `KEY_AGGREGATE` 与时间边界常量；`keyword_aliases` 的写法查询与代表写法裁决公开给统计复用。
- 服务：`KeywordService.vocabulary`、`KeywordService.overview`。
- API：`GET /api/keywords`、`GET /api/keywords/overview`；新增 `api/keyword_presenters.py`。
- 测试：新增 `tests/integration/test_keyword_stats.py`（概览与造数逐项对齐、覆盖与回填候选同源、合并后规模变化与撤销复原）；共用夹具补 `stub_providers` 与 `drain_worker`——多来源场景下 worker 会先抢到上一个来源的加工任务，打桩必须早于采集。
