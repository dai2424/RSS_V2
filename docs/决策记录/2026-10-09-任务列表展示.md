# 决策记录：任务列表展示哪些信息

> 状态：已实施（2026-10-09）
> 背景：任务页原来只有「类型 + 任务 UUID + 状态 + 尝试 + 创建时间」。用户反馈"信息有点少"——一排 UUID 看不出这条任务在干什么，失败时也看不到用的是哪个模型、哪个提示词版本，更看不出慢在哪。

## 结论

1. **目标是列表的核心一列**：任务快照里只有 `payload.message_id` / `payload.source_id`，界面要的是"这条任务作用于哪条内容"。因此在 `TaskService` 里解析 `TaskView(task, target_kind, target_id, target_label)`：
   - 消息任务 → 消息最新版本标题（为空时回落为短标识）；
   - 采集任务 → 来源名；
   - 解析不到目标时 `target_kind="unknown"`，界面显示 `—`，不编造。
2. **目标解析放在服务层，不在适配器里造读模型**：解析走已有的 `MessageRepository.latest_version` 与 `SourceRepository.get`，逐条点查（一页最多 100 条，本地 SQLite 足够快）。这样不用在任务端口上复制一份带 JOIN 的列表 SQL，端口保持"任务本体"的单一职责。
3. **执行参数从任务快照读**：`model` 与 `prompt_version` 直接取 `payload`（快照本来就是非敏感参数），嵌入在消息详情里的翻译/加工任务同样能看到，展示口径一致。
4. **耗时只在任务结束后显示**：`updated_at - created_at`，含排队等待（列头有说明）。排队中/运行中的任务显示 `—`——运行中的 `updated_at` 会被续租刷新，拿它算耗时是错的。
5. **失败原因独占一行**：原因是整句话（例如"任务快照的提示词已不存在，请重新创建任务"），塞进窄列会把「尝试」「模型」「耗时」挤成竖排。现在失败任务下面跟一整行 `colSpan` 的红色说明，其余列照常。
6. **短字段不换行**：尝试次数、耗时、创建时间加 `.cell-nowrap`，避免被长内容挤成两行。
7. **目标可点击**：消息任务跳 `/messages/{id}`，采集任务跳 `/sources/{id}`——从"看到任务"到"看到内容"一步到位（任务 UUID 只留短号，完整值放在 `title` 里）。

## 影响范围

- 领域：新增 `TaskView`。
- 服务：`TaskService` 增加 `messages`、`sources` 依赖与 `view` / `list_views`；组合根补装配。
- API：`TaskResponse` 增加 `model`、`prompt_version`、`target_kind`、`target_id`、`target_label`（都有默认值，消息详情内嵌任务不受影响）；列表、单条与重试都返回目标说明。
- 前端：任务页 9 列（任务 / 目标 / 状态 / 尝试 / 模型 / 提示词 / 耗时 / 创建时间 / 操作），失败原因整行；`lib/display.ts` 增加 `formatDuration`。
- 测试：集成用例断言采集与加工两类任务的目标、模型与提示词版本；前端单测覆盖耗时格式化（秒/分/时、负数与非法值）；E2E 断言任务页的目标链接、提示词版本，并用打桩响应覆盖失败行渲染。

## 明确不做

- 不做任务重跑历史、耗时统计或按目标聚合——需要新的读模型，等有真实需求再说。
- 不展示 `payload` 全量内容：快照里可能有将来新增的内部字段，逐个显式列出更安全。
