# 决策记录：Provider 可选请求协议（Anthropic Messages）

> 状态：已实施（2026-10-09）
> 背景：模型访问原先只有一种形状——OpenAI 兼容的 `/chat/completions`。要接只提供 `/v1/messages` 的上游（Anthropic 官方及各类 Anthropic 兼容网关），必须能在配置里选择协议，而不是再写一个专用适配器分支。

## 结论

1. **协议是 Provider 的连接属性**：`llm_providers.protocol`（迁移 0011，`TEXT NOT NULL DEFAULT 'chat_completions'`），取值由 `domain.models.LLMProtocol` 定义：`chat_completions`、`anthropic_messages`。默认值保证升级后行为不变，也不需要数据回填。
2. **不加 SQL CHECK 约束**：沿用迁移 0010 的结论——新增协议时不必重建表，取值由 `ProviderService.validate_protocol` 在应用层校验，未实现的取值直接抛 `invalid_protocol`，不做静默回退。
3. **按协议分发而不是在服务层分支**：新增 `adapters/llm/router.py::ProtocolRouter`，`bootstrap.py` 把 `LLMProtocol 取值 → 适配器` 注册进去。业务层（翻译、内容加工、连接测试、提示词试跑）继续只依赖 `LLMProvider` 端口，拿到的还是同一个实例；未知协议在调用点抛 `llm_protocol_unsupported`。
4. **两种协议共用一个边界层**：`adapters/llm/boundary.py` 放结构化输出 schema（`TranslationResponse` / `EnrichmentResponse`）、关键词归一化、稳定会话 ID、任务标记、JSON 截取、密钥脱敏与**全部错误分类**（429 → `rate_limited`、401/403 → `llm_auth_error`、5xx → `llm_server_error`、超时/网络 → `llm_timeout`/`llm_network_error`、结构不符 → `llm_invalid_output`）。协议适配器只负责端点、认证头、请求体与响应包装，所以新增第三种协议时错误语义不会漂移。
5. **Anthropic Messages 的具体形状**：端点是 `{base_url}/messages`；系统提示走顶层 `system`（任务标记仍然拼在最前面，假端点与日志据此识别任务类型）；`max_tokens` 必填（取 8192，译文与摘要都用不到更多）；响应文本在 `content[]` 里，`stop_reason` 的 `end_turn` 视为正常结束、其它取值（如 `max_tokens`）写进结构化输出错误信息。
6. **认证头两份都给**：官方 API 认 `x-api-key`，兼容网关常直接复用 `Authorization: Bearer`。同一个密钥放进两个请求头是同一主机的同一次 TLS 请求，不额外暴露密钥，却能让同一份配置连上两类上游；另外附带 `anthropic-version: 2023-06-01`。
7. **用量字段归一化**：Anthropic 的 `input_tokens`/`output_tokens` 折算成 `prompt_tokens`/`completion_tokens`/`total_tokens`，`llm_calls.token_usage_json` 在两种协议下可以直接比较。
8. **可选参数被拒时同样重试一次**：与 chat completions 的 400 重试对齐，Messages 协议删除 `temperature` 后重试一次，结构化输出仍由 Pydantic 校验和有限重试兜底。
9. **界面**：新建与编辑连接弹层都有「API 格式」下拉（显示协议名与端点），详情页的「API 格式」行显示当前协议；后端未实现的历史取值原样显示，便于发现问题。前端协议列表集中在 `features/providers/types.ts`。
10. **顺带修掉一个既有缺陷**：`ProviderEditDialog` 的表单初值只在挂载时读一次，切换供应商后不重挂会把上一个供应商的名称与地址写到当前记录上。详情页现在用 `key={provider.id}` 隔离该弹层；新增的 E2E 步骤（切协议并保存）在完整套件里正好暴露了这个问题。

## 影响范围

- 领域：新增 `LLMProtocol`；`Provider` 增加 `protocol` 字段。
- 数据：迁移 0011 加列，默认 `chat_completions`。
- 适配器：新增 `anthropic_messages.py`、`router.py`、`boundary.py`（从 `openai_compatible.py` 抽出共用件，`openai_compatible.py` 只留 chat completions 的请求体与响应包装）。
- 服务：`ProviderService` 增加协议校验；翻译与加工的失败占位 Provider 补上协议字段。
- API：provider 新建/更新请求与响应带 `protocol`。
- 前端：协议下拉与详情行；`ProviderEditDialog` 按供应商隔离。
- 测试：`tests/integration/test_llm_protocols.py`（协议校验、Messages 形状、错误分类与冷却、路由分发）、E2E 在假端点上切协议并用用量差异证明请求打到 `/messages`。

## 明确不做

- 不做第三种协议（如 Gemini 原生、Responses API）；需要时按第 3、4 条加一个适配器即可。
- 不做自定义端点路径：端点固定为协议规定的那一个，`base_url` 里已包含版本前缀。
- 不做按协议区分认证方式的可配置项：第 6 条的两份请求头已覆盖官方与网关两类上游。
