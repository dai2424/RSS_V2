## 1. 背景与问题

阶段 4 需要"点击发现选题 → 得到同一事件的候选 → 选择并进入写作"。P1a 复核已经证明：现有关键词组与"相关消息"都是**主体/主题级**候选，同一组里混有 5–13 个不同事件，且窗口内 40% 的消息没有加工结果、关键词检索取不到。因此事件发现不能用关键词或相似度作为成员来源，必须按时间窗口全量取消息后由模型判定事件边界，再由服务端做确定性校验。本记录冻结该流程的输入、分批、聚合、推荐与幂等口径。

## 2. 候选方案与决定

| 决策点 | 候选方案 | 决定与理由 |
| --- | --- | --- |
| 成员来源 | A. 关键词组/相关消息；B. 时间窗口全量消息（含未加工）；C. 向量近邻 | **B**。A 已被 P1a 证否（误合并率高、40% 消息不可达）；C 引入未验证基础设施，阶段目标明确不预设向量；B 可复现、可解释，且天然覆盖无关键词短快讯。 |
| 事件判定 | A. 规则聚类（URL/标题相似度）；B. 模型分组 + 服务端校验 | **B**。同一事件的判定需要语义（发布/评测/回应属于同一事件），规则只保留"同一 URL/同一内容指纹"这类确定性去重；模型输出只提供 `message_id`，版本由服务端解析。 |
| 分批 | A. 一次全窗口；B. 固定条数分批 + 跨批合并 | **B**。单次输入受模型上下文与成本限制；顺序确定性（时间序）保证同窗口可复现。 |
| 跨批同事件 | A. 不再合并；B. 共享成员即并集合并；C. 再跑一次模型合并 | **B**。确定性、零额外调用；C 成本翻倍且引入新的误合并面。同一事件跨批时通常至少共享一条消息（同一条报道出现在两批不可能——分批按消息切分，故共享成员来自"同一事件的不同消息被分到不同批"的情形，此时不做合并会拆成两个候选，因此 B 用"候选之间共享消息"作为合并信号只能覆盖部分情况，剩余情况由批内时间连续性承担，见 §3.4 与重新评估条件）。 |
| 推荐排序 | A. 只按报道数量；B. 模型自评分数 + 可解释理由；C. 先做公式评分 | **B**。产品要求"先做可解释的推荐，不锁定评分公式"；报道数量只作为材料信息展示，不参与排序。 |
| 输入范围 | A. 默认全部时间；B. 默认最近 7 天，可限定时段与分类/来源 | **B**。产品口径已确认。 |

## 3. 决定内容

### 3.1 输入与范围

- 请求参数：`window_start`（UTC 秒，含）、`window_end`（UTC 秒，不含）；`category_id`、`source_id` 可分别或同时给出（同时给出时按 AND 组合；来源必须属于所选分类，否则 400 `discovery_scope_mismatch`）。
- 默认窗口：`[now - discovery_window_days * 86400, now)`，`discovery_window_days` 默认 7。请求时刻由服务端取一次并固定写入批次，运行中不再漂移。
- 校验：`window_end > window_start`，跨度 ≤ `discovery_max_window_days`（默认 90）；窗口内消息数 > `discovery_max_window_messages`（默认 400）时返回 400 `discovery_window_too_large`，提示缩小时间范围或增加筛选，**不静默截断**。
- 消息时间口径：`COALESCE(published_at, collected_at)`，与列表一致；每个消息取**最新版本**，并把该 `message_version_id` 固定为候选成员。缺失 `published_at` 的回落情况在界面标注（沿用消息页口径）。
- 确定性顺序：`(COALESCE(published_at, collected_at), message_id)` 升序；同窗口同输入得到同一顺序，保证可复现。

### 3.2 覆盖路径（关键词不是门槛）

- 窗口内的消息全部进入发现输入，**不按是否有关键词过滤**；已有关键词的版本把词条作为附加上下文传入（`entity/topic/event` 原样列出，不参与排序）。
- 单篇候选允许成立（成员数 ≥1）：模型可把"值得写"的单条报道单独成候选。
- 同一事件的多篇报道（不同来源、不同时间）应聚为一个候选；同一 URL 或同一内容指纹的消息在批内只保留最早一条作为成员，其余记为重复并在候选上计数（`duplicate_members`）。

### 3.3 模型输出与服务端校验

模型按批处理消息并输出结构化结果（Pydantic 校验，schema 见 [实施契约](../阶段目标/4-文章聚合_实施契约.md)）：

```json
{"candidates": [{"member_message_ids": ["..."], "title": "...", "summary": "...",
                 "event_time": 1791427311, "score": 4,
                 "reasons": [{"kind": "important", "text": "..."}]}]}
```

服务端规则（确定性，不依赖模型自述）：

1. `member_message_ids` 只允许**该批输入内**的消息 ID；越界 ID 丢弃并累加 `out_of_range` 计数。
2. 成员解析为输入批内的最新 `message_version_id`；模型不能提供版本号。
3. 一个消息只能属于一个候选：先出现的候选保留，后续重复出现从该候选中移除并累加 `duplicate_members`。
4. 成员数 > `discovery_max_members`（默认 20，沿用线索上限）时按输入顺序截断，超出部分累加 `dropped_members`，界面显示"另有 N 篇未纳入"。
5. 成员数变 0 的候选丢弃并计数。
6. `score` 取值 1–5，用于排序展示；`reasons` 至少 1 条、最多 3 条，`kind ∈ {interesting, important}`，文本为空或超长的候选记为无效并丢弃（计数）。
7. 候选标题截断到 120 字符、概要 600 字符后入库；线索标题（`leads.title`）取候选标题前 80 字符。
8. 模型返回 0 个候选是**成功**结果（空态），不是失败。

### 3.4 跨批合并

- 批内先做第 3.3 节的规范化；批间按"共享至少一个 `message_version_id`"合并为并集，理由合并去重，标题取 `score` 更高（同分取更早批）的候选标题，`event_time` 取最早。
- 合并后再过滤一次：成员数 > `discovery_max_members` 的候选按时间序截断；成员数 0 的丢弃。
- 候选总数 > `discovery_max_candidates`（默认 30）时按排序保留前 N，其余累加 `dropped_candidates` 并在批次上展示。
- **已知局限**：仅共享消息的并集合并无法识别"同一事件的两条消息被分到不同批且互不共享消息"的情况。缓解手段是分批按时间连续切分（同一事件的消息通常在时间上相邻，落在同一批或相邻批）。若 P5/P7 的真实样本出现该情形的误拆，先按"重新评估条件"调整，不在本阶段引入二次模型合并。

### 3.5 排序与展示

- 排序：`score` 降序 → `event_time` 升序 → `id` 升序（稳定可复现）。
- 候选展示：标题、概要、事件时间、成员报道（来源名 + 标题 + 时间 + 版本号）、推荐理由、`rank`；批次展示实际生效范围（起止时间、分类、来源）、状态、消息数、候选数、各计数（越界/重复/截断/丢弃）。
- 推荐理由必须来自模型给出的文本，界面原样展示，不生成模板套话；"报道数量"只作为材料信息，不作为推荐语。

### 3.6 幂等与重复点击

- 输入快照指纹：窗口内 `(message_id, version_id)` 有序列表的 SHA-256（`input_fingerprint`）。
- 幂等键：`discover:{scope_hash}:{input_fingerprint}`，其中 `scope_hash = sha256(window_start|window_end|category_id|source_id)`。
- 同一幂等键已存在批次（无论排队/运行/完成）时，创建接口直接返回该批次并带 `reused=true`，不新建任务；失败（`failed`）的批次允许创建新任务重试（同一批次行，新增尝试）。
- 批次状态：`queued → running → succeeded | failed`，由服务在租约内更新；`failed` 记录 `error_code`/`error_message`（分类沿用 worker 的错误分类）。

### 3.7 任务与提示词

- 任务类型 `discover_events`，进入 `WORKER_TASK_TYPES` 与 `LLM_TASK_TYPES`；worker 只负责调度，服务自完成（同 `keyword_merge_suggest` 的模式）。
- 提示词规格：`kind=discover_events`、`label=选题发现`、`variables=(window_start, window_end, scope, messages, batch_index, batch_total, message_count)`、`required_variables=(messages,)`、`output_fields=(candidates,)`、`assignable=False`（不按来源/分类分配，直接取该 kind 当前 active 版本，同 `keyword_merge_suggest` 的做法）。
- 任务 payload 快照：`{batch_id, offset, size, provider_id, model, prompt_id, prompt_version}`；模型调用经 `LLMFailover.execute` 并写入 `llm_calls`。

## 4. 影响

- 新增 `discover_events` 任务类型需要重建 `tasks` 表 CHECK 约束，并同步 `TaskType`、`WORKER_TASK_TYPES`、`LLM_TASK_TYPES`、`TASK_SPECS`、worker 分发、任务列表展示（目标=批次）与 `api/routers/tasks.py` 的 `task_type` 过滤正则。
- 发现候选复用 `leads` 存储消息版本集合（新增 `leads.kind` 区分 `manual`/`discovery`，人工线索页默认只看 `manual`），不新建重复的事件成员表。
- 一次发现的最大成本 ≈ ceil(400/40) = 10 次模型调用；默认 7 天窗口在当前样本（89 条）下为 3 次。
