# RSS 订阅实现说明（AI）

当前范围依据用户确认的实现计划：来源与分类、RSS 采集与版本、翻译与 Key 池、独立 worker、React 工作台。人工需求原稿保持不变。

## 已实现的行为

- SQLite 编号 SQL 迁移、校验和检查、WAL、短事务与在线备份；采集运行和任务原子创建。
- 来源新增、编辑、启停、分类筛选与健康历史；内置分类和自定义分类并存。
- 原文纯文本保存，按来源外部 ID、规范化 URL、内容哈希去重；内容变化追加版本，包括 A → B → A。来源只提供 `description` 时正文留空，不再复制摘要；内容指纹仍按摘要兜底计算，迁移 0008 归一历史副本后重新采集同一来源不会产生假新版本。
- 翻译绑定入队时的消息版本、首选 Provider×模型和 prompt 版本；成功结果复用。标题、摘要、正文全部经 Pydantic schema 校验。
- Provider 表示兼容服务连接（Base URL、超时、会话头、非敏感请求头）；下挂可启停的模型列表，每行独立优先级。调度候选为 Provider×启用模型，按模型优先级排序，失败后依次切换 Key、模型与 Provider；每次模型尝试记录 `llm_calls`（含实际请求模型与密钥掩码）。模型配置页为左供应商列表（状态点：上次调用成功／失败／冷却中／未配置 Key／已停用）、右详情（连接信息、模型列表、API Key），行内启停，编辑走弹层。
- API Key 在界面直接录入并按 Provider 保存多枚：密钥值只写入运行目录数据库，接口、日志与审计只出现末四位掩码；录入与替换弹层可切换明文核对，保存后不再明文回看。
- Worker 租约 token、续租、过期恢复、三次有限自动重试、失败后手动重排；自动重试期间采集运行保持 running。译文写入与租约校验处于同一事务，过期 worker 不能覆盖新结果；翻译重试等待时间不短于 Key 冷却时间。
- 统一 OpenAPI 类型与稳定 API 错误码；本机 Host、Origin 和客户端地址检查。
- 单一 React 工作台覆盖来源、消息、任务和模型配置；路由懒加载，筛选与分页保存在 URL，表单失败保留输入，离开未保存表单时可继续编辑。
- 来源列表返回过滤后总数用于分页；行内可直接启停、测试地址和单源采集，健康失败在列表显示错误摘要；新增行业收进筛选区弹层并在成功后自动选中。列表按创建时间倒序（同秒按入库顺序），编辑或启停不改变行位置。操作反馈统一走顶部浮层提示：成功/信息/错误变体、自动消失、不遮挡页面操作。
- 删除来源在单个事务内级联清理消息、版本、译文、健康记录、采集结果、相关任务与调用审计，并清理 v1 导入映射；未完成的采集运行移除该来源后按剩余任务收敛状态。列表与详情页均可删除，确认弹层展示消息条数与不可恢复说明。

## 采集自动翻译与内容加工（2026-10-08）

- 采集写入新版本后由 `ProcessingService` 统一判定入队：识别为英文的版本自动创建翻译任务（不设条数上限，允许排队），标题超过 40 字符或摘要/正文超过 300 字符的版本自动创建内容加工任务；阈值和提示词版本都可配置。
- 自动入队失败（例如没有可用 Key）只写警告日志并跳过，采集统计不受影响；存量消息不回填，只对新采集内容生效。
- 内容加工任务 `enrich_message` 产出精简标题、1 至 3 句中文摘要和 3 至 8 个关键词，保存在 `message_enrichments`（迁移 0009，按版本 + 提示词版本 + 模型唯一），与译文分别保存、互不覆盖；幂等键为 `enrich:{version_id}:{model}:{prompt_version}`。
- 翻译与加工共用 `services/llm_failover.py`：候选排序、Key 冷却过滤、每次调用的审计写入和逐级回退只实现一次；`TranslationService` 因此回到规模阈值内。
- 列表优先展示加工结果、其次译文、最后原文，并标记「机器」；摘要两行截断，完整内容在详情页。详情页新增「内容摘要（机器生成）」标签页和「生成摘要」按钮。
- 检索的 `LIKE` 范围扩展到最新成功译文与加工结果（含关键词），中文关键词因此能命中英文来源的消息；仍未引入 FTS5。

## 结构化输出容错与失败可定位（2026-10-09）

- 现场反馈：`deepseek-v4.1-flash`（推理模型，返回带 `reasoning_content`）的加工调用间歇性报「模型返回的结构无法校验」，同批翻译调用成功，且错误信息没有任何可定位的内容。
- 解析容错：模型输出前后带 Markdown 围栏或说明文字时，先截取首尾大括号之间的 JSON 再校验；关键词被写成逗号或顿号分隔的字符串时折算成列表。两者都只是把可恢复的形状还原成契约形状，仍由 Pydantic schema 校验，非法内容照旧失败。
- 失败可定位：校验失败的错误信息改为「失败字段（错误类型）+ 结束原因 + 返回片段」。返回片段压成单行、替换密钥、限制 200 字符；`finish_reason` 为 `length` 时明确写出结束原因，用于区分「模型答错」与「被输出上限截断」。任务、译文与加工记录的错误信息都来自同一处，界面直接可见。
- 界面文案：记录失败但任务仍在排队或运行时，详情页显示「上次尝试：失败，任务已排队自动重试」，不再与工具栏的「加工任务：已排队」互相矛盾。
- 仍然保留 `extra="forbid"`：模型答成另一种结构（例如返回翻译形状）必须失败而不是静默降级；若真实失败原因确为多余字段，错误信息现在会直接给出 `extra_forbidden` 字段名，再按证据决定是否放宽。

## 提示词库与任务分配（2026-10-09）

- 提示词从适配器硬编码搬进数据库：`llm_prompts` 一条记录一个不可变版本，版本串仍是 `{prompt_key}-v{version}`，与既有 `prompt_version` 逐字一致，因此结果表、审计与任务幂等键零迁移；迁移把旧文本原样种子化为 `translation-v1`、`enrich-v1`。
- 编译 = 模板 + 校验 + 预览：占位符 `{{title}}`/`{{summary}}`/`{{content}}`；未声明该任务的结构化输出字段按错误处理（避免模型漏字段后静默降级），未引用输入占位符只警告；有错误时只返回问题清单，不渲染。
- 任务分配三层覆盖：来源 → 行业分类 → 全局默认，`enabled` 与 `prompt_id` 独立继承，来源可以只关任务不动提示词。
- `LLMProvider` 改收渲染好的 `PromptPayload`；适配器在系统消息前附加 `[task: <kind>, prompt: <version>]` 标记，假端点与日志据此识别任务类型。`llm_calls.input_hash` 改为渲染后提示词的哈希。
- 试跑真实调用一次模型：写 `llm_calls`（`task_id` 为空、版本串带 `+prompt-test`）、复用 Key 冷却，但不写译文或加工结果。
- 任务类型不写死：`task_kind` 无 SQL CHECK，规格由 `domain/prompts.py` 的 `TASK_SPECS` 提供；新增任务类型的清单与已知边界（聚合类任务需要新的输入与结果模型）记在决策记录里。
- `api/schemas.py` 因新增模型超过 400 行阈值，拆成 `api/schemas/` 包（catalog / messages / llm），原导入路径通过 `__init__` 重导出保持不变。
- 提示词 CRUD 补全（`PromptUsage`）：新建全新业务键从 v1 开始；名称与版本说明随时可改；**未被任何引用**的版本可以就地改文本或真删除（`PATCH` / `DELETE`），被引用过的只能另存新版本或归档，启用中的版本要先启用另一个才能删。判定口径集中在 `PromptRepository.usage`：调用审计（含试跑的 `+prompt-test`，版本串精确匹配，`v1` 不会命中 `v10`）、译文与加工结果、任务快照 `payload_json.prompt_id`、来源与分类的任务分配四类引用；`used` 由四项计数派生，界面按项说明影响。理由与界面限制见决策记录[《2026-10-09-提示词就地编辑与删除》](../决策记录/2026-10-09-提示词就地编辑与删除.md)。

## 模型访问协议（2026-10-09）

- 模型访问可选协议（迁移 0011）：`llm_providers.protocol` 取 `chat_completions`（默认）或 `anthropic_messages`；`adapters/llm/router.py` 按配置分发，`adapters/llm/boundary.py` 承担两种协议共用的结构化 schema、错误分类与脱敏，Messages 适配器只负责端点、认证头、请求体与响应包装。界面在新建与编辑连接弹层选择「API 格式」，详情页显示当前协议。理由与形状细节见决策记录[《2026-10-09-Provider协议可选》](../决策记录/2026-10-09-Provider协议可选.md)。
- 两种协议共用一个边界层：错误分类、密钥脱敏、结构化输出 schema 与 JSON 截取只有一份实现，因此 429、认证失败、超时与结构不符在两条链路上得到相同错误码；Anthropic 的 token 字段折算成 `prompt_tokens`/`completion_tokens`/`total_tokens`，`llm_calls` 里的用量可以直接比较。
- 连接探测只校验协议 envelope（`LLMProvider.probe`）：模型回一句普通文本就算连通，只有连不通、认证/限流/5xx，或上游回的不是该协议形状才判失败；结果把模型回复片段带回界面。假端点的探测请求同样返回普通文本，避免比真实上游更配合。
- 界面「API 格式」下拉与详情行显示当前协议；顺带修掉 `ProviderEditDialog` 表单初值不随供应商切换重挂、会把上一个供应商的地址写到当前记录上的既有缺陷。

## 实现边界与评审

2026-10-08 用户确认仅在电脑浏览器使用：最低支持 1280px 内容区宽度，以 1440px 为设计基准，验收覆盖 1280、1440、1920px。手机及低于 1280px 的窗口不纳入支持范围；本次同步规范和测试，保留已有响应式样式。

当前检索使用 `LIKE`，范围覆盖原文、最新译文与最新内容加工结果；支持独立的 [v1 RSS 导入](1-RSS订阅_v1迁移_AI.md)。不接入定时任务、局域网认证、图谱、发布或外部分布式队列。

前端构建写入 `runtime/frontend/`，可配置；API 和 worker 必须指向同一配置与同一数据库（模型 API Key 随数据库共享，不再依赖密钥环境变量）。API 不执行持久化后台任务，续租线程仅在 worker 进程内运行。

日常运行统一使用根目录 `start.cmd`。启动器自动准备锁定依赖、按源文件指纹更新前端、执行迁移，启动 API 与独立 worker 并打开页面。两个子进程继承同一配置；Ctrl+C 或任一子进程退出时停止本次启动的两个进程。日志写入运行目录；首选端口不可用时由操作系统分配空闲本机端口，并传给两个子进程与浏览器，不修改配置文件或结束已有进程。单独的 `api` 命令仍使用配置中的固定端口。

保留三个超过默认 60 行评审阈值的函数：`bootstrap.build_container`、`api.app.create_app` 是完整装配清单，内嵌处理函数各自较短；`HTTPXFeedClient.fetch` 是单次下载与 RSS 边界映射。业务翻译已拆为输入检查、单次尝试、审计与结果保存；路由、仓储按领域拆分。后续复杂度增长时重新评审这些例外。

前端手写组件文件均不超过 200 行。展示函数超过 60 行的主要是完整表单和表格的 JSX；本次评审保留其完整展示结构。来源数据用例、行内操作、字段与历史面板，模型配置的列表、详情、连接表单、模型行、Key 设置与离开保护已分别拆分；新增业务规则应进入数据 hooks 或用例，不能继续堆入展示函数。OpenAPI 生成文件不计入规模阈值。

数据库操作时间和消息发布时间使用 UTC 秒整数。Feed 的原始更新时间文本属于来源元数据。采集统计按来源记录最近一次尝试；任务最终状态决定整个运行何时完成。

进程崩溃后的任务会重做幂等检查，成功译文能避免重复调用。若进程在模型返回与译文持久化之间被强制终止，恢复后仍可能再次调用外部模型；跨外部 API 和 SQLite 不承诺 exactly-once。

- 迁移 `0006_provider_models.sql` 新建 `llm_provider_models`，把存量 Provider 的单一 `model` 迁为一条模型行（沿用原 `updated_at` 与应用迁移时刻作为时间戳），随后删除 `llm_providers.model` 列；`llm_providers.priority` 列保留但不再被读写，排序与优先级移到模型行；`e2e` 真实数据升级后模型行可继续参与翻译调度。
- 领域与端口：`Provider` 移除 `model`/`priority`，新增 `ProviderModel`；`LLMConfigRepository` 增加模型行的查询与增改；仓储层校验模型行归属，跨 Provider 修改返回 404，重复模型 ID 返回 409 `model_exists`。

- 前端：模型配置页重构为左侧供应商列表 + 右侧详情（连接信息、模型列表、API Key）；模型行内启停、弹层编辑；新增供应商后自动选中并定位到该供应商，创建失败保留输入。

## API Key 直接录入（2026-10-08）

- 迁移 `0007_api_keys.sql` 重建 `llm_provider_keys`（改为保存密钥值 `secret`），并把 `llm_calls`、`translations` 的 `key_ref` 列改名为 `key_masked`；旧引用行只有环境变量名、没有可兑换的密钥值，因此不迁移数据，升级后在界面重新填写。
- 领域与端口：`ProviderKey.secret` 保存密钥值；`mask_secret` 统一生成末四位掩码；`mark_key` 改用密钥行 ID；移除 `EnvironmentSecretResolver` 与翻译用例的 `secret_available` 回调，可用密钥改为“启用且未冷却且密钥值非空”。
- API：`POST/PATCH /api/llm/providers/{id}/keys` 接收 `secret`，响应只返回 `masked`；密钥值不出现在响应、日志与审计，空值与含换行的密钥被拒绝。
- 前端：API Key 直接录入，输入框默认遮蔽并可切换明文核对；列表行只显示掩码，支持替换密钥（弹层内确认旧值覆盖）与启停；页面与提示文案不再提及环境变量引用。
- 验收脚本与预览服务不再注入 `RSS_LLM_KEY_*` 环境变量；e2e 在缺少可用密钥时通过接口补一枚假密钥。

- 兼容性与错误可见性（2026-10-08 补充）：上游 4xx/5xx 的 `error.message`（或 `message`/`detail`）经脱敏（替换密钥值、压成单行、截断 300 字符）后进入错误信息，界面与任务详情可直接看到网关原因；401/403 归类为 `llm_auth_error` 且不冷却 Key。网关拒绝可选参数时（HTTP 400）去掉 `response_format`/`temperature` 自动重试一次，结构化输出仍由 Pydantic 校验与有限重试兜底。
