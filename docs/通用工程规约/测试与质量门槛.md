# 测试与质量门槛

本文件把“能运行”转成可重复的验收证据。项目应在技术附录中填写实际命令和工具名称。

## 1. 测试分层

- [必须] 领域规则和纯函数有快速单元测试。
- [必须] 端口和适配器有契约测试，验证不同实现对同一接口的行为一致。
- [必须] 关键入口有集成测试，覆盖输入校验、用例调用、持久化和错误转换。
- [必须] 重要跨层用户流程有定向端到端测试；简单文案、样式或局部逻辑不强制使用端到端测试。
- [约定] 测试替身、固定样例和临时数据与生产数据完全隔离。

## 2. 每项变更的最低验证

适用检查由变更范围决定，至少包括：

- [CI] 格式化、静态检查和严格类型检查；
- [CI] 相关单元测试和契约测试；
- [CI] 涉及入口或数据时的集成测试；
- [可选] 涉及重要跨层流程时的定向端到端测试；
- [CI] 构建或打包检查（包含构建产物可加载性）。

项目在此处补充命令：

```text
<格式化检查命令>
<静态检查命令>
<类型检查命令>
<单元与集成测试命令>
<构建命令>
<端到端测试命令>
```

## 3. 必测行为

- [必须] 重复输入不会产生不符合预期的重复结果。
- [必须] 内容或配置发生变化时，版本、缓存和幂等行为符合记录的规则。
- [必须] 一个外部依赖失败时，不会无故破坏其它独立操作。
- [必须] 任务重试、进程重启和超时恢复有验证。
- [必须] 错误引用、越权输入和不完整数据不会绕过边界校验。
- [必须] 全新环境可以完成结构初始化和最小闭环。
- [必须] 测试不会修改代码目录中的真实数据、密钥或演示产物。

## 4. 可重复性

- [必须] 固定时间、随机数、外部响应和环境变量的测试使用显式替身。
- [约定] 每个失败用例能通过日志中的关联标识定位到请求、任务或数据版本。
- [CI] 锁定依赖版本，构建和测试使用同一依赖解析结果。
- [评审] 发现 flaky test 时必须记录原因、影响和修复计划，不能长期重试掩盖。

## 5. 阶段完成定义

- [ ] 目标行为可演示，范围和不做事项与阶段计划一致。
- [ ] 领域、契约、集成和必要的端到端测试通过。
- [ ] 失败、重试、幂等、恢复和兼容行为已有证据。
- [ ] 全新环境初始化成功，运行产物不写入代码目录。
- [ ] 文档、注释、配置说明和实现一致。
- [ ] 没有未说明的依赖方向、复杂度或安全问题。
- [ ] 变更已在最新基线上重新检查并完成交付流程。
