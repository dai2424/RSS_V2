建议顺序：

```text
P1a → P1b → P2a → P2b → P3a → P3b → P4 → P5 → P6a → P6b → P7
```

## 2. 所有任务的共同规则

- 先读 AGENTS.md、技术选型、开发规范、本阶段计划；改任何文件另读 Git 工作流，涉及页面另读 Web 界面规范。
- 分层、Protocol、组合根、Pyright strict、中文说明、规模约束继续适用。避免把所有新领域类型、仓储或响应 schema 塞进已经很大的通用文件；新增模块前检索复用点。
- 具体适配器只在 bootstrap.py 装配。模型统一走 LLMProvider、LLMFailover 和提示词库，不复制调度、冷却、重试或审计。
- 新任务需同步 TaskType、WORKER_TASK_TYPES、LLM_TASK_TYPES 的适用分类、TASK_SPECS、worker 分发、任务展示和 fake；任务结果持久化要校验租约，过期 worker 不能写入晚到结果。
- 新增迁移编号以当时最新 migrations 为准，不能预占固定编号或修改旧 SQL。新增任务类型需更新数据库 CHECK 约束并验证旧任务、索引和外键；不要只改 Python 枚举。
- 新 API 返回 Pydantic 契约；前端只用生成的 openapi-fetch client。新增前端路径要注册路由、懒加载、导航和 static.py 的刷新回退；未实现的后续入口不显示可工作的按钮。
- 数据、网页读取、模型结果均需有真实失败分类。无结果、部分资料失败、任务失败、已排队、执行完成和人工核对状态分别呈现。
- 自动测试用 fake 模型和固定网络 fixture；生产链路必须有可配置的真实适配器。Agent 自己的搜索工具不等于应用具备联网检索能力，搜索摘要不等于已读取原文。
- 验收使用隔离运行目录。通过产品 API/服务读取必要的现有消息，必要时通过产品备份创建隔离测试库；不修改真实业务库、模型配置或密钥。真实调用使用用户已配置且授权的凭据，不将密钥写入报告、任务文本或仓库，含凭据的测试库不得成为 fixture。运行证据、网页资料、导出和日志不进 Git，只有经筛选的固定测试资料可作为 fixture 入库。
- 这批任务只实现文字、引用和已确认流程；图片、自动发布、定时选题、杂谈专栏等沿用阶段目标的范围排除。
- 各 Agent 不需要为已确认目标重新做产品访谈。规范未覆盖的工程决策先记录依据再实现；遇到未配置的真实服务或实质性兼容冲突，保存现场、说明阻塞项，不能用 fake 或删测试来宣称完成。

## 3. 固定样本与检查命令

### 3.1 样本索引

P1a 为下面每类提供固定输入、消息/资料版本和可核对的预期结果。真实文章样本与异常 fixture 分开；先标注期望，再实现算法，不能按实现结果倒改答案。发现输入记录固定参考时刻及窗口，避免「最近 7 天」随日期变化导致测试失效。

| ID | 样本 | 应证明的行为 |
| --- | --- | --- |
| S01 | 多来源报道同一事件 | 正确聚合，去重并保留互补关键事实 |
| S02 | 有趣的单篇报道 | 可推荐、选择，资料足够时可走完整写作流程 |
| S03 | 需要背景与行业影响分析的事件 | 能读取补充资料、解释背景，分析有依据且不冒充事实 |
| B01 | 同公司或同产品的两个独立事件 | 共享实体或关键词不能把事件混成一篇 |
| B02 | 无关键词短快讯与已有长文同事件 | 短快讯参与候选或材料，不强制补关键词 |
| B03 | 时间边界、缺失发布时间、分类/来源组合、无结果 | 筛选准确，时间回落可见，空态真实 |
| B04 | 原文超时、404、无法解析或只能读到摘要 | 保留已获资料，提示缺口；未读取内容不能成为引用 |
| B05 | 可靠来源相互矛盾、关键事实缺料 | 呈现冲突与待核对，不能伪装已达到可发布质量 |
| B06 | 模型 JSON 非法、越界消息/证据 ID、遗漏来源 | 校验失败可诊断，不保存未经校验的合格稿 |
| B07 | 重复点击、崩溃重启、租约失效后的晚到结果 | 幂等与恢复有效，晚到 worker 不能污染当前结果 |
| B08 | 未确认提纲、确认后编辑、生成中更改提纲 | 全文绑定确认时的不可变版本，状态不会串用 |
| B09 | 来源更新或删除后查看旧稿 | 旧依据保留或明确不可用，不替换成最新正文 |
| B10 | 保存失败、刷新、并发编辑、重生成 | 已保存内容可恢复，人工改稿不被覆盖，冲突不静默覆盖 |
| B11 | 复制或导出的链接、长段落、中文、HTML/Markdown | 结构与来源完整，不执行不可信 HTML 或危险链接 |

S01–S03 各形成一篇真实文章，三篇均需达到少量修改即可发布。B 类证明边界行为，不要求冲突、缺料样本强行产生合格文章。

### 3.2 检查命令与执行位置

从任务 worktree 根目录运行后端检查（简称 B）：

```powershell

uv run ruff format --check .
uv run pyright
uv run pytest
```

前端接口发生变化时，先在 worktree 根目录导出，再从 frontend 目录生成（简称 G）：

```powershell
uv run python -m rss_v2.main schema --output frontend/openapi.json
Set-Location frontend
npm run generate:api
```

从 frontend 目录运行前端检查（简称 F）：

```powershell
npm run typecheck
npm run test
npm run format:check
npm run build
```

重要流程运行定向 E2E（简称 E）。后续新增用例文件建议为 stage4-topics.spec.ts、stage4-writing.spec.ts、stage4-output.spec.ts；以实际实现的文件名为准，并在交接报告写全命令，不能引用不存在的测试。P7 从 frontend 目录执行完整：

```powershell
npm run test:e2e
```

API 变化还需重导出并重生成后确认生成文件无新增差异，以证明 schema 与类型同步。P1a/P1b 仅文档时做本地链接、格式、样本索引与 git diff --check；确实新增可运行样本工具时按变更补测试。每步按下文执行相关检查，避免把每个文案改动都变成完整 E2E；P7 执行完整 B、F、E。

迁移与兼容重点复用 tests/integration/test_migrations.py，线索回归复用 tests/integration/test_leads.py，任务恢复复用 tests/integration/test_recovery.py、test_system_boundaries.py，协议回归复用 test_llm_protocols.py，E2E fixture 入口是 tests/preview.py。这些都是真实现参考，不自动等于新增功能有覆盖。

## 4. 各任务详细说明

### P1a：固定样本与 M11 复核材料

**交付目标**：所有 Agent 和最终验收者使用同一组输入与预期，能明确指出聚合漏了什么、混入了什么、文章遗漏了哪项事实。

**需要做的事情**

1. 读取阶段 3 M11 复算方法、复核清单及当前消息/关键词 API。通过只读服务/API 查看完整相关消息，不仅看清单中截断标题。
2. 对现有 M11 组逐项记录：是否混入其他主体/事件、应归入哪个事件、已知应命中的消息是否缺失；引用具体消息版本作依据。说明「同一主体」与「同一事件」的区别。
3. 选择 S01–S03 三个真实事件，写出消息版本、来源 URL、时间、事件边界、应覆盖关键事实、预期补充资料和选题有趣/重要的理由。
4. 为 B01–B11 制作最小固定输入与预期；真实资料与合成 fixture 标明来源和用途。
5. 新建样本说明文档，按需在 tests/fixtures 下保存精简合法测试资料；记录参考时刻、起止时间、如何装入隔离环境。不要为准备样本再次全量重跑 M11 加工。
6. 复核记录如实注明执行者；Agent 内容复核不能写成「用户本人已确认」。有未核实结论就列待核对，不勾成已通过。

**交付物**：建议 docs/阶段目标/4-文章聚合_样本与复核.md，固定 fixture/清单、M11 逐组复核证据与未决项。

**自检与交接**：文档与样本检查；若新增工具补 B 中适用检查。交接 S/B 索引、完整证据入口、取样和隔离环境复现步骤。最终复核将检查预期不是模型自造的答案。

### P1b：实施契约、任务与预算决策

**交付目标**：后续 Agent 能依据明确契约连续开发，而不各自定义文章结构、来源语义或任务状态。

**需要做的事情**

1. 基于 P1a 说明最小事件发现方案：如何覆盖全量窗口、如何利用关键词及无关键词输入、如何分批和避免跨批同事件重复，如何说明「有趣/重要」；不预先引入向量系统。
2. 明确领域关系：发现批次、候选事件与消息版本、选定的写作项目、资料/证据快照、事实/分歧/缺口、提纲版本与确认、生成稿与人工保存稿。决定如何复用 lead，避免新建重复仓储。
3. 画出 API 请求/响应及状态转换，约定每步输入版本、输出 ID、错误分类、引用关系、删除和缺失资料语义。写清分类与来源同时选择的组合规则、UTC 秒窗口边界及发布时间回落。
4. 定义后台阶段任务、幂等键、提示词和模型快照、阶段重试、租约校验与崩溃恢复。快照相同的重试避免重复产物；用户主动重生成产生新版本。
5. 选择应用运行时真实搜索、网页读取方案，查阅对应官方技术文档，写明配置、协议、可用服务与失败限制。缺少所需服务配置时如实列依赖；不能以 Agent 浏览器或模型虚构资料取代运行时适配器。
6. 明确内容生成 schema 和校验原则、事实证据映射、分析/推测类型、提纲确认约束；说明用户改写后引用和核对状态如何处理。
7. 为候选数量、批量、搜索条数、读取次数/字节、调用次数、输入长度、超时、阶段耗时定有限初始预算和可配置项；能实测的记录实测，未实测标明暂定及验证方法。
8. 比较博客与公众号输出需要，确定首版复制/导出方案及预览验证办法。先避免依赖复杂富文本编辑器；具体选择写入决策，以后按该决策实施。
9. 写实施决策和契约文档，并同步真正需要变更的技术选型、项目结构或规范说明。只做文档设计，不先创建全阶段的空表、空端口和空路由。

**交付物**：日期化实施决策记录、契约和状态说明、真实依赖与预算表、P1a 未决项的处理说明。每一项需有具体结论，不能仅列「后续再定」。

**自检与交接**：文档检查、契约逐项覆盖、可配置依赖核查。将已确定的端口、API、schema、任务名称和预算作为 P2–P6 的输入；尚不可用的真实依赖单独列未验证项。

### P2a：事件发现后台、候选存储与选择 API

**交付目标**：隔离环境内，调用 API、运行 worker，可以从真实订阅消息形成候选并选择单篇或多篇事件。

**需要做的事情**

1. 按 P1b 增加本步实际用到的领域对象、Protocol、仓储和新迁移；保存发现批次的时间/分类/来源范围及输入消息版本快照。
2. 默认最近 7 天、全部订阅；验证有限起止时间，按实际约定组合筛选，处理发布时间缺失，按确定顺序分批。无关键词消息必须进入覆盖路径。
3. 实现事件候选整理与推荐，输出概要、事件时间、成员版本、有趣/重要的具体理由；过滤模型给出的越界成员。处理跨批重复，不能只按公司名称建一个事件。
4. 若使用模型，扩展 LLMProvider 和两个现有协议适配器，复用结构化 schema、LLMFailover、提示词/任务分配和审计；同步 fake provider 与协议测试。
5. 按 P1b 接入新任务类型、数据库约束、worker 和任务展示；持久化结果时验证租约，阶段错误可诊断。重复请求同一在途发现返回既有任务或明确重复状态。
6. 提供创建发现任务、查看批次/候选/状态、选择候选并建立写作上下文的 API。选择绑定发现时的成员版本，不能把消息 ID 再解析成已变化的最新版本。
7. 调整至少两条消息的旧门槛，允许单篇；零条、重复成员、无效版本与容量仍有明确校验。旧 lead API 和存量数据兼容，旧测试按新规则改写并补相应边界，不直接删除。
8. 用新库和从 0024 基线升级的库验证迁移；验证 S01、S02、B01–B03、B06–B07 的后台行为。

**涉及现有点**：services/leads.py、adapters/sqlite/leads.py、api/routers/leads.py、domain/models.py、domain/prompts.py、llm、tasks/worker.py、bootstrap.py、tasks 仓储与展示。文件名是复用入口，新增领域模块按职责组织。

**自检与交接**：B + G + F（生成 API 类型的适用部分）。交接 API 调用到 worker 执行的完整复现、批次输入/输出与幂等证据、单篇选择结果、兼容说明。

### P2b：发现选题与选择界面

**交付目标**：用户在现有应用里设置范围，发现并选择一个真实候选。

**需要做的事情**

1. 按 P1b 接入页面/路由，复用 DateRangeInputs、分页、表单、任务反馈和设计变量；显示最近 7 天、全部订阅的默认值。
2. 允许改有限时间、分类和来源，并在结果中显示已生效条件；筛选/分页放 URL，进详情返回恢复位置。
3. 点击只创建后台任务，显示排队/运行/失败/完成状态；候选有概要、成员报道、时间和推荐理由，单篇也能选。
4. 选择候选调用 P2a API，进入已实现的事件/写作详情；未实现的资料、提纲、生成入口不显示为可执行功能。
5. 完整处理首次加载、刷新保留内容、无结果、失败重试、重复点击、键盘焦点；界面状态来自服务端。
6. 更新导航及新路径的 static.py 深链接回退，确认刷新详情不 404。新增定向 E2E，并检查支持的桌面宽度。

**自检与交接**：F + E；若改变后端回退做适用 B。交接完整操作截图/步骤、筛选与状态证据、新路由刷新和键盘结果。

### P3a：真实检索、原文读取与证据快照

**交付目标**：应用能够在 worker 中读取原文、搜索补充材料，并将实际使用的证据存储为可查看的资料。

**需要做的事情**

1. 按 P1b 定义/实现 SearchClient、ArticleReader 等实际端口及具体适配器；在 bootstrap.py 统一装配，设置可配置服务/超时/预算。端口名称以冻结契约为准。
2. 获取选定报道原文，对标题、发布者、发布时间、正文、原 URL/最终 URL 作清晰提取；HTML 清洗、链接协议和重定向/体积限制按决策处理。无法解析、受限访问或只获摘要如实记录。
3. 联网搜索相关报道、官方资料与背景；搜索命中只是候选，读取成功后才是引用资料。允许历史背景早于发现窗口，记录原始时间。
4. 去除相同 URL/相同内容的重复资料，保存资料 ID、获取 UTC 秒、可用发布时间、内容指纹和实际证据；RSS 资料保留消息版本来源。
5. 通过新迁移/仓储存储本步所需资料与状态；任务按资料保存可恢复的进度，部分失败保留已有资料，预算耗尽返回范围与缺口说明。
6. 提供资料读取/状态/证据详情 API；区分真实数据、未读取和失败，避免正文进入日志、密钥进入响应。
7. 为搜索、提取、跳转、失败、去重、快照和版本行为增加 fixture/契约/集成测试；至少做一次隔离环境的真实搜索与原文读取，列实际服务和资料证据。
8. 更新假端点供后续 E2E，生产应用不注册 fixture 路由。若真实服务缺配置，只能交接「实现已自测、真实依赖未验证」，本步不得宣称联网能力已验收。

**自检与交接**：B + G + F 的适用部分，重点 B04、B07、B09；单独交真实联网证据。不能用一次手工浏览网页作为运行时搜索测试。

### P3b：资料整理、事实与核对界面

**交付目标**：用户选题后看到已读资料、关键事实的证据、来源分歧与缺口，再进入提纲流程。

**需要做的事情**

1. 基于 P3a 资料快照整理关键事实、背景、分析依据、分歧和缺口；只关联本项目内已读取证据，模型输出用结构化 schema 校验。
2. 使用统一模型链路、提示词、任务和审计；新增协议实现与 fake，避免重写调用治理。
3. 保存资料包版本，记录所有输入证据；来源状态变化不能悄然替换历史资料。事实/分析/推测有独立标记。
4. 展示来源列表、原文入口、事实与证据关系、冲突位置、缺失的关键材料、阶段进度与失败重试。区分来源确实官方和模型仅自称官方。
5. 关键缺口影响主线时显示待处理状态；提供 P1b 约定的重新获取/重试或确认处理结果入口。未经解决的关键事实不能标成已可发布。
6. 引用 ID 验证、冲突显示和内容支持关系分别核对；固定样本说明每个关键事实的实际依据，不能只提供合法 ID。
7. 做资料列表、证据跳转、冲突/缺料、部分失败、历史资料和键盘的定向测试。

**自检与交接**：B + G + F + E，重点 S03、B04–B06、B09。交接至少一个资料包从原文到事实/分歧界面的复现及逐项证据。

### P4：提纲生成、修改保存与确认

**交付目标**：用户得到可编辑提纲，确认指定版本后才有全文生成资格。

**需要做的事情**

1. 依据选题与确定资料包生成标题/切入点、分节结构、每节应讲事实和证据、可能的行业影响分析；提纲符合普通科技读者的理解顺序。
2. 接入 LLMProvider、两协议、提示词规格/种子/分配、任务/审计与 fake；输入绑定选题和资料包版本。
3. 建立提纲版本和生成、修改保存、确认的服务/API 及迁移。确认后的输入版本不可变；修改产生新版本并需重新确认。
4. 前端独立页面编辑、保存、确认，展示资料依据和待核对项；离开保护、保存失败保留输入、刷新恢复已保存内容。
5. 新稿未确认、确认被旧版本替换、或主线仍缺关键事实时，按冻结契约拒绝生成资格并说明原因。确认请求也做版本/状态校验，不只靠按钮禁用。
6. 验证确认前后状态、生成失败、修改后重确认、重复确认、并发和快照绑定。

**自检与交接**：B + G + F + E，重点 B05、B07–B08；交提纲原版、修改版、确认记录及其输入资料 ID。

### P5：全文生成、来源绑定与预览

**交付目标**：用已确认提纲与证据生成可阅读的科技博客全文，保存可追溯生成版本。

**需要做的事情**

1. 按 P1b schema 输出标题、导语和正文结构；关键事实携带证据，分析/推测有明确类型和依据。长度按材料与事件复杂度组织。
2. 输入锁定确认提纲、资料包、提示词和模型快照；生成中改提纲不能改变这次任务输入，也不能让旧结果覆盖新状态。
3. 接入模型端口、两协议、任务/种子/分配与审计，设置适用输出长度和超时；用实际任务产物做恢复和幂等。
4. 校验正文结构、事实引用和链接：证据必须属于已读输入，URL 由已验证资料产生。越界或缺关键来源时拒绝或标明确需处理，不得只删引用而保留无依据的「合格结论」。
5. 保存生成稿、输入关系、生成元信息；重生成另存新版本。来源更新、删除、任务重试都不改变旧依据。
6. 预览正文关键位置的来源链接与文末来源列表，支持点回证据；与核对状态、任务状态分别展示。单来源不虚构多方一致意见。
7. 为生成、非法响应、来源校验、版本和提纲绑定、失败恢复增加后台和定向 E2E。至少用 S01–S03 作首次稿件质量检查，将问题归因到资料、提纲或正文。

**自检与交接**：B + G + F + E，重点 B06–B09。交三类样本原生成稿、事实—证据映射、提示词/模型/任务/耗时 token 和质量问题；P5 不独自宣称整阶段可发布达标。

### P6a：系统内编辑、保存与历史版本

**交付目标**：用户能修改文章，保存后可恢复，重生成和并发操作不能覆盖人工成果。

**需要做的事情**

1. 按 P1b 输出结构选择最小可用编辑器，支持标题和正文修改、预览、保存；不另建前端或引入无必要的复杂编辑框架。
2. 保存为人工版本，关联依据的生成稿/前一版本；提供最新和历史查看，区分 AI 生成、人工保存、任务执行与核对状态。
3. 保存时检查基础版本，陈旧编辑或异步生成不能静默覆盖；保存失败保留当前输入，服务端确认后才提示成功。
4. 处理刷新、路由返回与未保存离开：已保存内容可恢复，未保存输入按项目规范提示继续编辑或放弃。
5. 人工删改引用或新增事实时校验资料引用关系；受影响内容标明需重新核对，不能沿用「原稿已核对」状态来证明新文本真实性。
6. 旧消息/资料更新、新提纲、新生成稿都不改写人工保存稿。验证旧稿与证据能查看或有明确不可用标记。
7. 测试保存失败、并发版本冲突、未保存保护、刷新、历史查看、生成中编辑与编辑后重生成。

**自检与交接**：B + G + F + E，重点 B08–B10。交从生成稿到人工改稿及冲突/重生成后的完整版本记录。

### P6b：复制、导出与发布编辑器验证

**交付目标**：已保存文章能以首版确定的方式转入个人博客和公众号编辑器，结构与来源保留。

**需要做的事情**

1. 按 P1b 输出决策实现复制或导出入口，输入明确为用户选择的已保存版本，不能把尚未保存的修改或旧生成稿混入。
2. 输出标题、导语、正文、小标题、来源信息及完整可读 URL；读者不依赖内部证据 UUID 或本机路由才能知道来源。
3. 清洗渲染 HTML/Markdown，校验链接协议，覆盖中文、长标题、长 URL、特殊字符与引文；复制失败/文件写入失败反馈清楚。
4. 若导出文件，目录由配置决定并与代码分离；预览与复制/导出使用相同保存版本。
5. 在用户提供或已授权访问的实际博客编辑器和公众号编辑器分别做粘贴/导入预览，记录工具、方式、截图和结构/来源结果；不点击发布或群发。
6. 用户未提供或当前无法访问某个平台编辑器时，先交可复现的输出和本地结构检查，清楚记录该平台实测待完成，不能以文件存在代替平台验证。
7. 加定向输出测试，验证导出来源未丢、未保存/历史版本选择正确，不把任意外部 HTML 直接注入页面。

**自检与交接**：F + E；增加后端导出逻辑时 B + G。交博客/公众号两份实际结果，未实测项明确列出。内容最终是否发布由用户自行决定。

### P7：完整回归与最终验收材料

**交付目标**：把整个主流程、异常边界和三篇真实文章交给本对话 Codex 独立验收。

**需要做的事情**

1. 在最新合并基线上检查 P1a–P6b 契约、迁移与功能；核对计划里的每个验收项是否有实现和证据，不仅看各 Agent 的报告。
2. 在隔离环境跑全新迁移和旧库升级；运行完整 B、F、E，验证 schema/生成类型同步。确保没有 fixture 端点、fake 统计或测试专用行为进入生产。
3. 跑完整「发现 → 选题 → 资料 → 确认提纲 → 全文 → 编辑保存 → 复制/导出」E2E，并覆盖 B01–B11。
4. 按 Web 规范完成 1280、1440、1920、2560px 实际布局与键盘检查，复现加载、空态、错误、未保存保护和返回位置。
5. 对 S01–S03 用真实运行时检索、原文读取和模型链路生成三篇文章；记录固定输入和各阶段产物、资料/提纲/文章版本、调用元数据。真实缺依赖时列缺口，不伪造完成。
6. 提供三篇原稿、所做人工修改与前后差异。逐项核对关键事实、引用支持、分析/推测、可读性、去重补全；需要重写主线、补关键事实或大段改结构的样本写失败，不能改口称少量修改。
7. 汇总博客/公众号输出证据、任务恢复/租约/幂等证据和所有未验证项。生成一份「自测结果与最终待验收项」报告，更新实施进度但不替最终验收者签署通过。
8. 若发现问题，按完整修复提交、重新跑受影响检查；保留失败记录和修复证据。不能通过删除测试、换掉困难样本、只导出人工重写稿来隐藏失败。

**交付物**：最终提交/基线、验收矩阵、复现环境说明、三篇完整产物与修改记录、事实证据表、真实调用元数据、完整检查结果、两类输出证据、已知问题。运行产物位于配置运行目录，报告引用可供本对话读取的路径。

**自检与交接**：完整 B + G 同步核对 + F + E；全部 S/B 样本状态分别写「通过/失败/未验证」。最终通过由下一节的独立核查决定。

## 6. 本对话 Codex 的最终验收

收到 P7 及各任务的提交/证据后，本对话会：

1. 核对真实基线、提交内容和工作树状态，确认范围与文档一致，检查分层、装配、类型、规模、迁移、真实网络适配器和模型统一入口。
2. 重跑适用检查与重要 E2E，复现单篇、事件混淆、无关键词、冲突缺料、过期租约、保存失败和重生成等关键边界；不只读取测试摘要。
3. 检查资料、确认提纲、生成稿及人工保存稿的版本关系，逐项核对三篇文章的关键事实与证据，确认分析、推测和不确定性表达。
4. 比较原生成稿与人工修改，判断是否真正只需少量修改；核对两种目标编辑器的输出结果。
5. 给每项明确结论：通过、失败或未验证；列出具体问题、影响、证据和需修复任务。缺失真实联网、关键事实支持或平台验证的部分不能默认为通过。
6. 实现缺陷由本对话定位并交回对应任务或在用户授权范围内修复；主观写作偏好与尚未提供的平台访问条件单列，避免将其混成代码已经通过。

阶段最终通过需满足产品计划第 6 节全部要求，并遵守 DoD。Agent 自测通过和合并完成都不是最终质量签署。
