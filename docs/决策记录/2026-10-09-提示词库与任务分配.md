# 决策记录：提示词库与任务分配

> 状态：已实施（2026-10-09）
> 背景：翻译与内容加工的提示词硬编码在 LLM 适配器里，只能靠 settings 换一个版本字符串；不同来源无法使用不同提示词，也无法只关掉某一类任务；改提示词只能改代码，改完不知道会得到什么。

## 结论

1. **提示词入库**：新增 `llm_prompts`（迁移 0010），一条记录是一个不可变版本，字段为任务类型、业务键、版本号、名称、状态（draft/active/archived）、系统模板、用户模板、版本说明。
2. **版本串沿用 `{prompt_key}-v{version}`**：与既有 `translations.prompt_version`、`message_enrichments.prompt_version`、`llm_calls.prompt_version` 逐字一致，因此**结果表、审计表、任务幂等键、前端展示都不需要迁移**。迁移把改造前的硬编码提示词原样种子化为 `translation-v1` 与 `enrich-v1`（有测试断言渲染结果与旧文本逐字相同），升级后行为不变。
3. **版本不可变、只归档不删除**：编辑等于新建版本，启用某版本时同任务类型的其它启用版本自动归档（`UNIQUE INDEX ... WHERE status='active'` 保证每类任务只有一个启用版本）。这样 `{key}-v{n}` 永远能回溯到当时用的文本，审计与幂等键不会说谎。
4. **"编译" = 模板 + 校验 + 预览**：提示词是带 `{{title}}`、`{{summary}}`、`{{content}}` 的模板。编译校验未知占位符、空用户模板、以及**没有声明该任务的结构化输出字段**（后者按错误处理：模型漏给字段只会让结果静默降级）；没有引用必需输入占位符只警告。有错误时只返回问题清单、不做渲染。
5. **任务分配三层覆盖**：新增 `task_settings(scope, scope_id, task_kind, enabled, prompt_id)`，来源与分类共用；`enabled` 与 `prompt_id` 为空表示继承。解析顺序是**来源 → 行业分类 → 全局默认**，两个字段各自独立继承，因此"来源只关掉翻译、提示词仍用分类默认"是自然行为。界面上 `scope` 表示生效提示词来自哪一层。
6. **端口改造**：`LLMProvider.translate/enrich` 不再接收 title/summary/content，改收渲染好的 `PromptPayload(system, user)` 与版本串。模板、占位符、版本选择全部留在服务层（`services/prompt_resolver.py` 是唯一解析点），适配器不再持有任何提示词内容。
7. **适配器附加稳定标记**：系统消息是 `[task: <kind>, prompt: <version>]` + 用户编写的系统提示。标记属于协议层，供网关、日志与假端点识别任务类型（`tests/preview.py` 原先靠 `"enrichment"` 子串识别，提示词入库后会失效，已同步改为按标记识别）。
8. **审计输入哈希改为渲染后的提示词哈希**：`llm_calls.input_hash` 现在对 `system + user` 取 SHA-256，换提示词版本一定会换哈希；`LLMFailover.execute` 因此与消息版本形状解耦（只收 task_id 与哈希），提示词试跑也能复用同一套回退与审计。
9. **试跑**：`POST /api/llm/prompts/{id}/test` 用真实消息版本或手填样例真实调用一次模型，复用候选调度与 Key 冷却，**写 `llm_calls`**（`task_id` 为空、版本串带 `+prompt-test` 后缀）但**不写译文或加工结果**——试跑是"看会得到什么"，不是正式产出。
10. **配置退役**：`settings.llm_default_prompt_version` 与 `llm_enrich_prompt_version` 删除。提示词是数据不是配置，默认值由"每个任务类型的启用版本"表达。

## 扩展缝：后续的文章生成与调研任务

提示词层与配置层**不写死任务类型**：`task_kind` 列没有 SQL CHECK 约束（0009 已吃过改 CHECK 要重建表的苦），取值由 `domain/prompts.py` 的 `TASK_SPECS` 注册表在应用层校验；界面按规格渲染占位符与输出字段提示。新增一类任务的完整清单：

1. `TaskType` 枚举与 `TASK_SPECS` 加一条规格；
2. 迁移建该任务的结果表（沿用 `translations`/`message_enrichments` 的形状）；
3. 新增执行服务、`worker.execute` 加分支、`services/prompts.py` 的 kind→调用方法映射加一项；
4. 前端展示该结果。

**已知边界**：当前任务模型是"一任务 = 一个消息版本"。文章生成与调研是跨多条消息的聚合任务，届时需要新的输入范围与结果模型，不是加一条规格就够。本次不预先实现通用结果表。

## 影响范围

- 领域：`Prompt`、`TaskSetting`、`TaskSettingView`、`ResolvedTask`、`PromptSample`、`PromptTest`；新增 `domain/prompts.py`（规格表、渲染、编译）。
- 端口：新增 `PromptRepository`、`TaskSettingRepository`；`LLMProvider` 签名变更。
- 适配器：`adapters/sqlite/prompts.py`；`openai_compatible.py` 不再拼提示词。
- 服务：新增 `services/prompts.py`（编译、版本、试跑）、`services/task_settings.py`、`services/prompt_resolver.py`；`translation.py`/`enrichment.py` 按 payload 快照的 `prompt_id` 渲染执行；`processing.py` 的 `enqueue` 增加来源参数并按任务分配开关判断。
- API：`api/schemas.py` 拆成 `api/schemas/` 包（catalog/messages/llm，原导入路径不变）；新增 8 个提示词端点与 2 个任务分配端点。
- 数据：迁移 0010（`llm_prompts`、`task_settings`、种子提示词）；来源删除显式清理任务分配。
- 前端：提示词管理页、任务分配页与来源表单配置区（另见后续提交）。
