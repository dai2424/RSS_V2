# 阶段目标 4：文章聚合与线索草稿（AI 整理稿）

> 状态：**计划中（2026-10-14 立项，尚未实施）**。前置是[阶段目标 3](3-关键词收敛_AI.md) 的 M11 复算与人工复核：线索聚合的质量判据（"同一线索能否找全""不同主体是否被误关联"）必须在关键词口径稳定之后再定，否则草稿的证据基础会随时间漂移。
> 负责人：lyx
> 更新时间：2026-10-14
> 关联决策：[关键词覆盖范围与检索索引](../决策记录/2026-10-14-关键词覆盖范围与检索索引.md)（短快讯不进关键词体系，聚合时要单独处理）、[热词注入与合并建议](../决策记录/2026-10-13-热词注入与合并建议.md)（词表是模型与人工共用的唯一收敛层）。
> 来源：承接[阶段目标 3](3-关键词收敛_AI.md) 的结论——关键词已经能收敛写法、能按线索找出相关消息，下一步是把"多条消息说同一件事"变成可阅读、可核对的草稿。

## 1. 目标

把"找同一条线索的消息"从浏览动作变成一条可追溯的产出：**人工选定一组消息 → 生成一篇草稿 → 草稿里每项结论都能点回它依据的那条消息版本**。关键词负责把候选聚到一起（`related` 已有实体 4 分、主题 2 分、事件 1 分的计分），人工负责确认"这些确实是一件事"，模型只负责把已确认的输入写成草稿。

## 2. 范围

### 包含

- **线索（lead）**：人工选定的一组消息，入库为独立实体，成员精确到**消息版本**（选择时锁定当时的最新版本）。
- **草稿生成**：一个后台任务（与合并建议同样走任务表），输入是线索成员的版本快照与各自的加工结果，输出是结构化的草稿：标题、导语、分节结论，**每项结论带来源**（`message_id` + `message_version_id`）。
- **引用校验**：模型给出的来源必须在输入集合内，否则丢弃并计数（与合并建议"越界写法丢弃"同一套做法，不采信模型自证）。
- **草稿界面**：线索列表与草稿页，每项结论旁列出可点击的来源消息版本；生成时的输入版本被冻结，之后消息出现新版本也不改写历史草稿（重生成会生成新版本草稿）。
- **短快讯的参与方式**：按[覆盖范围决策](../决策记录/2026-10-14-关键词覆盖范围与检索索引.md)第 5 条第 2 项，短快讯用"来源 + 时间窗"进入候选面板（它没有关键词），但**不因此获得关键词**——关键词体系的口径不动。

### 不包含

- 自动聚类 / 相似度召回：不引入 embedding 与向量检索；"哪些消息是一件事"仍由人工确认，程序只提供候选（`related` 计分 + 时间窗 + 来源）。
- 自动发布与外发：草稿只落库、只在界面阅读与复制，不接任何外部平台。
- 跨线索的全局排序、热度榜、定时汇总：属于后续可能的"日报/周报"话题，本文不做。
- 改写既有消息与加工结果：草稿是新的派生物，不动源数据。
- 为草稿单独做一套提示词治理：沿用提示词库 + 任务分配 + `LLMFailover` 的既有链路。

## 3. 约束和前置条件

- 前置：M11 基线复算完成，且人工复核（同一线索能否找全 / 不同主体是否被误关联）给出结论；复核发现关键词口径问题先修关键词，不带着问题做聚合。
- 任务机制：草稿生成是**长模型调用**（多条消息的正文 + 生成），必须走任务表 + worker。新增任务类型要按 `0009`/`0019` 的先例重建 `tasks` 表的 CHECK 约束（编号顺延到 0024），并在任务列表里给出可读目标（线索名 + 成员条数）。
- 分层与类型：线索本体与草稿结构放 `domain/`，纯函数做引用校验；仓储端口在 `ports/repositories.py`，SQL 只在 `adapters/sqlite/`；模型调用只经 `LLMProvider`，结构化输出用 Pydantic schema 校验，每次调用写 `llm_calls`。
- 追溯性：草稿的每项结论必须携带来源版本 id；界面上不得只显示消息标题而不可点回版本。
- 成本：一次草稿 = 一次调用，输入随成员条数增长；必须有成员条数上限（建议 20 条，超过就让用户分批）与逐次调用审计。

## 4. 关键决策（先写决策记录，再写代码）

| 编号 | 决策点 | 倾向 | 理由 |
| --- | --- | --- | --- |
| L1 | 线索的边界 | 人工选定，不自动聚类 | "是不是同一件事"是语义判断；关键词只能给候选。与合并"人工确认"的既有原则一致 |
| L2 | 成员的版本语义 | 锁定选择时的最新版本；成员表存 `message_version_id` | 结论可追溯到具体版本；消息后续更新不影响已生成的草稿 |
| L3 | 生成方式 | 后台任务（`compose_lead_draft`），任务表重建一次 | 一次调用几十秒，同步调用会拖住界面且无法重试；与合并建议的教训一致 |
| L4 | 结论与来源的绑定 | 结构化输出：`{section, text, sources: [message_version_id]}`；服务端丢弃越界来源并计数 | 追溯靠服务端校验，不靠模型自证；与 D4（复用硬判定）同一原则 |
| L5 | 草稿版本 | 每次生成存一版草稿，保留历史；界面默认看最新一版 | 输入变了就要能对比"模型这次改了什么"；与译文/加工结果的多版本语义一致 |
| L6 | 短快讯 | 经"来源 + 时间窗"进入候选；不补关键词 | 见[覆盖范围决策](../决策记录/2026-10-14-关键词覆盖范围与检索索引.md)：短快讯的关键词缺口是设计选择 |

## 6. 验收标准

- [ ] 选定 3 条以上同一线索的消息能生成草稿；成员不足时明确拒绝并说明原因。
- [ ] 每项结论都有来源，且来源一定是**输入集合内**的版本；模型给出的越界来源被丢弃并计入日志与任务记录。
- [ ] 来源消息出现新版本后，旧草稿的引用仍指向生成时的版本（测试断言），重生成产生新版本草稿而不覆盖旧版。
- [ ] 任务列表能看到草稿任务（类型、目标=线索名与成员数、模型、提示词版本、失败原因可重试）。
- [ ] 短快讯能作为成员进入线索（候选面板可见），且不因此获得关键词（词表口径不变，测试断言）。
- [ ] 人工作答两个质量判据（同一线索能否找全 / 不同主体是否被误关联）在固定样本上有明确结论，结论写入本文。

## 7. 风险和取舍

| 风险或取舍 | 影响 | 缓解措施 | 触发重新评估的条件 |
| --- | --- | --- | --- |
| 模型把不同主体写成一件事 | 草稿误导阅读 | 每项结论可点回原文核对；来源只允许是输入集合内的版本；结论不合并不同主体的表述 | 复核里"误关联"占比偏高时先回到关键词合并层收敛 |
| 输入过长导致成本与超时上升 | 一次调用 token 高、失败率上升 | 成员上限（建议 20 条）、正文按来源截断、失败可重试且计费可见 | 单次草稿平均 token 或失败率超过阈值 |
| 线索越攒越多、没人用 | 数据膨胀 | 线索是人工显式创建；列表显示成员数与最后生成时间；不做自动建线索 | 线索使用率低时评估是否需要"草稿即弃"模式 |

## 8. 本次不做

- 不做自动聚类、embedding、相似度阈值调参。
- 不做每日/每周自动汇总、不做发布到任何外部平台。
- 不做草稿的人工编辑回写（第一版只读 + 复制；编辑留待有实际需求再评审）。
- 不为草稿新增第二套检索或索引（沿用既有消息检索与关键词）。
