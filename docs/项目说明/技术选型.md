# RSS v2 技术选型

> 状态：v0.2 建议版（第一版最小验证前）
> 更新时间：2026-10-07
> 用途：约束 v2 第一版实现，避免在代码完成后再争论基础技术。

## 1. 选型原则

1. 先验证最小闭环，再为未来规模预留接口。
2. 不引入可以由 SQLite 或进程内代码承担的外部基础设施。
3. 业务层只依赖领域对象和端口，数据库、HTTP、模型 SDK 都在适配器层隔离。
4. 运行环境、依赖版本、迁移和测试必须可重复。
5. 未经第一阶段验证的技术标记为“验证项”，不写成既定事实。

## 2. 决策状态

| 状态 | 含义 | 当前内容 |
| --- | --- | --- |
| 已锁定 | 第一版直接使用 | Python 3.12、FastAPI、SQLite、React、TypeScript、shadcn/ui、uv、pytest、Vitest、Ruff、Pyright |
| 第一阶段验证 | 先做小实验，验证通过才进入主流程 | SQLite WAL 双进程、FTS5 trigram、OpenAI 兼容模型适配器、Cookie 会话、OpenAPI 类型生成 |
| 暂缓 | 第一版不实现，只保留替换条件 | simhash、向量检索、sqlite-vec、networkx、APScheduler、PostgreSQL、Neo4j、分布式队列 |

“技术选型”不是所有库的永久承诺。第一阶段验证失败时，先更新本文档，再调整实现。

## 3. 第一版技术栈

| 领域 | 选择 | 约束 |
| --- | --- | --- |
| 后端语言 | Python 3.12 | 第一版固定 3.12，依赖稳定后再评估 3.13+ |
| Web API | FastAPI + Pydantic v2 | 路由只做参数校验和用例调用，不直接访问仓储 |
| 包管理 | uv + `pyproject.toml` + `uv.lock` | 开发、测试和部署使用同一锁文件 |
| 静态检查 | Ruff + Pyright strict | Ruff 负责格式和 lint；Pyright 检查业务代码与端口实现 |
| 数据库 | SQLite + WAL | 只允许短事务；配置 busy timeout；明确单写者、重试和备份规则 |
| 前端 | React + Vite + TypeScript | 只保留一套前端；生产构建产物由 FastAPI 托管 |
| UI | shadcn/ui + Tailwind CSS | 组件源码入库；统一设计 token；不再引入 Ant Design |
| 前端数据 | TanStack Query + TanStack Table | 服务端状态与表格行为分离 |
| 表单校验 | React Hook Form + Zod | 表单 schema 与 API 类型分开维护 |
| API 类型 | openapi-typescript + openapi-fetch | 类型自动生成，生成文件禁止手工编辑 |
| 测试 | pytest + Vitest + HTTPX | 网络和模型调用默认使用 fixture 或 fake adapter |

第一版不把 ECharts、React Flow 等图表和图谱库放入基础前端依赖；需要对应页面时再加入。

## 4. 后端结构

采用模块化单体，不拆微服务：

```text
领域对象 / 用例
        ↓
端口（Protocol）
        ↓
适配器（SQLite、RSS、LLM、文件）
        ↓
FastAPI 路由 / CLI / worker
```

第一版只建立实际需要的端口：

- `SourceRepository`
- `MessageRepository`
- `CollectionRunRepository`
- `CategoryRepository`、`HealthRepository`
- `TranslationRepository`、`LLMConfigRepository`、`LLMCallRepository`
- `TaskRepository`
- `LLMProvider`

不预先创建一组没有使用场景的 Repository。业务代码禁止导入 `sqlite3`，SQL 只出现在迁移器和 SQLite 适配器中；该规则由静态检查和架构测试共同约束。

FastAPI 按领域拆分 `APIRouter`，当前按 categories、sources、collection、messages、tasks、providers 分文件。静态托管不混入业务路由。

## 5. 数据库和迁移

SQLite 继续作为第一版权威存储。启用 WAL，但必须同时实现：

- `busy_timeout` 和有限次数的写入重试；
- API、worker、迁移器之间的互斥规则；
- 事务边界和失败回滚；
- worker 崩溃后的任务租约回收；
- `VACUUM INTO` 或等价的可验证备份；
- 备份恢复测试。

迁移规则：

1. 每个迁移是独立 SQL 文件。
2. `schema_migrations` 记录版本、校验和、执行时间。
3. 已执行迁移的文件内容被修改时直接报错。
4. Python 代码不隐藏 `ALTER TABLE`、建表和数据回填。
5. v1 数据导入是独立、可重复、可预览的命令，不混入结构迁移。

当前 RSS 阶段从空库开始；后续按用户要求增加独立的 v1 RSS 导入，映射与边界见 [v1 RSS 数据导入](../阶段目标/1-RSS订阅_v1迁移_AI.md)。不修改 v1 数据库。

## 6. 检索和去重

### 6.1 检索

当前 RSS 阶段使用结构化过滤与 `LIKE` 检索；FTS5 trigram 尚未验证，后续按真实数据量评估。中文短词不能假设一定能被 trigram 的 `MATCH` 命中；SQLite 官方文档说明少于 3 个 Unicode 字符的全文查询不会匹配，因此必须用中文样例测试单字、双字、三字和混合中英文查询：

<https://www.sqlite.org/fts5.html>

验证未通过时，第一版退回“结构化过滤 + LIKE”，不引入 OpenSearch。

### 6.2 去重

第一版只做可解释的去重：

1. `source_id + external_id`；
2. 规范化 URL；
3. 标题、正文、摘要的内容哈希。

simhash 和向量去重暂缓，只有当真实数据中出现大量改写转载且精确去重无法解决时才立项，并先用固定样本测阈值。

## 7. LLM 接入

第一版不直接让业务代码依赖具体模型 SDK，也不把 Agent 框架作为核心依赖。定义项目自己的 `LLMProvider`，第一种实现为基于 HTTPX 的 OpenAI 兼容适配器：

- 请求和响应由 Pydantic 模型校验；
- 结构化输出失败时只做有限重试；
- 429、5xx、超时与格式错误分开记录；
- 不把模型调用放进数据库事务；
- 支持 fake provider，测试不依赖真实模型。

每次调用写入 `llm_calls`：模型、provider、prompt 版本、输入摘要哈希、耗时、token 用量、状态、错误分类和关联任务。默认不保存完整 prompt，避免把原文和密钥写入审计表。

后续若确实需要多步工具调用，再评估 Pydantic AI 等框架；框架必须包在 `LLMProvider` 后面，不能改变业务接口。

## 8. 任务执行和调度

只保留一套执行机制：

```text
API / CLI 创建任务
        ↓
SQLite 任务表
        ↓
独立 worker 领取、续租、执行、重试
```

任务表至少包含状态、尝试次数、租约截止时间、错误分类、输入版本和幂等键。worker 必须支持进程重启后回收超时任务。

当前阶段只支持手动 API 创建采集任务，不接入定时触发。后续 Windows 任务计划程序只负责创建任务，worker 作为独立进程运行；开发环境支持 `worker --once`，生产环境可用 NSSM 或 Windows 服务托管长期运行的 worker。

不引入 Celery、Redis 或其它外部队列，除非出现多机执行或任务吞吐无法由 SQLite 任务表承担的实际证据。

## 9. 前端方案

前端只保留 React 单页应用：

- React + Vite + TypeScript；
- shadcn/ui + Tailwind CSS；
- TanStack Query 管理服务端状态；
- TanStack Table 负责高数据量列表；
- React Hook Form + Zod 负责表单；
- openapi-typescript + openapi-fetch 负责 API 类型和请求；
- 路由级代码分割从第一天启用。

当前 RSS 阶段实现来源、消息、任务和模型配置页面。证据和核验属于后续阶段。图表、事件时间线、图谱和复杂编辑器等页面等后端契约稳定后再增加。

## 10. 认证和部署

当前 RSS 阶段免认证，只允许 loopback 访问，同时拒绝外部 Host/Origin。局域网部署前必须补齐单管理员认证，不做多用户和角色系统：

- 密码使用 Argon2id 哈希；
- 使用签名 HttpOnly Cookie 保存短会话标识；
- 写操作启用 CSRF 防护；
- 密钥从仓库外的环境或系统配置读取；
- 本机开发可用 loopback + 显式关闭认证模式，局域网模式默认开启认证。

部署采用 Windows 裸机的 API + worker 两进程。数据库、日志、备份、前端构建产物和运行输出均放在配置指定的运行目录，不写入代码目录，也不提交到 Git。

## 11. 测试和质量门槛

每个竖切至少包含：

- 领域用例测试；
- SQLite 仓储契约测试；
- API 集成测试；
- 失败、重试和幂等测试；
- 全新数据库迁移测试。

v1 测试作为行为参考，不机械复制所有测试。第一版必须验证：

1. 重复采集不产生重复消息；
2. 内容变化生成新版本；
3. 单个来源失败不影响其它来源；
4. 两个进程同时访问 SQLite 时不会破坏数据；
5. worker 重启后任务可恢复；
6. 错误引用无法写入；
7. 生成的前端 API 类型与 FastAPI OpenAPI schema 一致；
8. 测试不会修改代码目录中的数据库和 demo 文件。

本地统一检查命令应覆盖：

```text
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
npm run typecheck
npm run test
npm run build
```

## 12. 暂缓技术及重新评估条件

| 技术 | 暂缓原因 | 重新评估条件 |
| --- | --- | --- |
| PostgreSQL | 第一版不需要额外运维 | SQLite 出现实际写锁瓶颈或需要多系统直连 |
| OpenSearch | 引入集群成本高 | FTS5 + LIKE 回退无法满足检索基准 |
| sqlite-vec / 向量库 | 第一版没有语义检索闭环 | 近重复或语义检索样本证明精确检索不足 |
| simhash | 阈值和中文效果需要真实样本 | 精确去重无法解决转载问题 |
| networkx | 图谱不是第一版闭环 | 图功能进入范围且数据规模经过测量 |
| APScheduler | 与 Windows 调度重复 | 需要应用内部动态调度且外部调度无法满足 |
| Pydantic AI 等 Agent 框架 | 第一版只需要单次结构化调用 | 多步工具调用的复杂度超过自有适配层承受范围 |
| Celery / Redis | 第一版没有分布式执行需求 | 出现多机 worker 或任务吞吐瓶颈 |
