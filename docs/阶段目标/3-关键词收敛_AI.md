## 1. 目标

阶段 2 把关键词从"给人看的标签"改成了"给机器用的检索键"，并把词表摆上了界面。但词表目前只是**被观察**的对象：模型每次加工都从零发明写法（332 个词里 301 个只出现一次），人工只能在事后把已经散开的写法一个个合并。本阶段把词表变成**被使用**的对象：

    每次加工前把现有词表注入提示词（按类型分组）
    → 模型优先复用已有写法，只有确实指新事物时才新建
    → 人工在界面上把词表里残留的同指写法批量收敛（模型给候选，人确认）
    → 词表规模下降、同一事件的消息能被同一批词命中

完成后的可验证行为：同一批消息在词表稳定后重新加工，模型产出的关键词显著偏向复用；词表页能一键标记常驻词、按批生成合并建议并采纳。

### M11 复算的方法（2026-10-14，可复现）

- **固定提示词**：`enrich-v4`（迁移 0021 种子并启用，本阶段唯一一次真实复算用的就是它）。
- **固定模型**：Provider `OpenCode-AM` 的 `deepseek-v4.1-flash`（运行库中唯一启用的候选；每次调用写 `llm_calls`，模型与耗时可按任务回查）。
- **固定样本**：全部来源、满足系统自身加工长度阈值（`llm_enrich_text_threshold = 300`）的**缺加工结果**消息，按发布时间倒序取 100 条；实操覆盖 2026-10-06 → 2026-10-08（这三天是他们订阅里长文最密的区间），并完整覆盖近 7 天的长文缺口。
  - 选样不用 `POST /api/keywords/backfill`（那个入口刻意不套长度阈值，会把十几字的快讯一起补进来）；写入仍走产品的服务路径（`enrichment_service.create_task`，与详情页「生成摘要」同一条），因此任务、审计与结果落库与界面操作完全一致。
  - 短快讯不参与本次样本，原因与后续安排见[关键词覆盖范围与检索索引](../决策记录/2026-10-14-关键词覆盖范围与检索索引.md)。
- **重跑方式**：取样的口径就是下面这段（只读选样 + 产品服务入队 + worker 循环，脚本未入库）：

  ```python
  # 选样：满足长度阈值的缺加工消息，倒序取 N 条（LATEST/CURRENT 与仓储层同一表达式）
  SELECT m.id FROM messages m JOIN message_versions v ON v.id = {LATEST}
  LEFT JOIN message_enrichments e ON e.id = {CURRENT}
  WHERE e.id IS NULL
    AND length(COALESCE(v.summary,'')) + length(COALESCE(v.content,'')) >= 300
  ORDER BY COALESCE(v.published_at, v.collected_at) DESC LIMIT 100;

  # 入队与执行：与详情页「生成摘要」同一条路径
  for message_id in picked:
      container.enrichment_service.create_task(message_id)
  worker = Worker(container)
  while worker.run_once():
      pass
  ```
- **旧提示词结果**：**不重跑**。运行库里已有的 59 条 v1–v3 结果保留为历史；关键词聚合按"最新一次成功结果"取用，因此它们仍参与词表，只是不进入复用率的分母（`reused` 为空的行不参与判定，这条口径在 M3 已定）。是否用 v4 重跑旧结果留到 M12（按词表版本重跑入口）统一处理，避免"半新半旧"的中间态扩散。

**成本与耗时**（`llm_calls` 实测）：101 次调用、**384,249 tokens**（平均 3.8k/条）、累计 1645 秒（16.3 秒/条），其中 1 次调用失败后由候选重试成功，最终 0 条结果失败。按条计价的直接成本很低，真正的约束是**耗时**（100 条约 27 分钟）。

**本次复算得到的四条结论**：

1. **覆盖率上来之后热词才谈得上"有内容"，但门槛口径下热词表依然很小**：近 7 天覆盖率 35% → 62% 才让热词从 2 个变成 5 个，而且这 5 个词全部来自 AI 新闻这一簇（tibo 的系列推文 + 快讯）。要让热词反映全部分类，还需要继续补 10-06 之前的存量，或者把 `keyword_hot_days` 放宽到 14 天（近 14 天已有 993 条消息）。
2. **复用率随样本真实化反而下降**：早期小样本（5 个可判定词位）显示 40%，真实批次是 15.6%。批内趋势也说明问题——前 25 条 13.0%、中 25 条 10.4%、后 50 条 4.0%：越往后越是"跨来源的长文"，新主体（公司、产品、人名）越多，而**注入词表只给窗口内达到门槛的词**，所以模型没有可复用的对象。词表的孤词占比因此稳定在 89% 左右，收敛靠的是人工合并（5 次）与常驻锚点，而不是注入。
3. **门槛口径的取舍需要用户确认**：注入的热词段现在要求"近 7 天 ≥5 次"（这正是审阅指出的不一致，已在 2026-10-14 修复）。代价就是本条第 2 点：能进热词段的词太少。可选的放宽方式有三档——把 `keyword_hot_min_mentions` 降到 2–3、把 `keyword_hot_days` 放宽到 14 天、或让注入的热词段改回"窗口内 Top N（不设门槛）"。「近期新增」段（上限 30、按首见时间）是当前唯一稳定的复用通道。
4. **短快讯永远是关键词体系的盲区**：最新 100 条缺加工消息里 52 条短于自动阈值；缺加工消息里 662 条文本不足 300 字符（其中 273 条标题超过 40 字、本该自动加工却因早期 Key/配置问题没有结果）。这类消息的关键词要么是"标题复述"（实测），要么根本不存在——处理方式见[关键词覆盖范围与检索索引](../决策记录/2026-10-14-关键词覆盖范围与检索索引.md)，其中"273 条本该加工却没有结果"属于**可修复的覆盖缺口**：它们的加工任务一条都没建过（`tasks` 里查不到），原因是自动入队只在**新版本入库那一刻**触发，当时没有可用的模型/Key 就会静默跳过（日志里是 `auto_task_skipped`），之后没人回头补；用回填入口就能补齐，不需要新机制（建议下一轮做）。

**人工复核**：按两个判据取固定样本填在[复核清单](3-关键词收敛_M11复核清单.md)（8 组关键词 + 2 条种子消息的相关消息），结论需要由人填写后再决定是否调整口径；清单同时暴露了几个待判断的点，例如 `gpt-6.1sol` 与 `gpt-6` 是两个词条（合并候选）、`tibo` 作为来源作者名进了词表（它当前是人工常驻词，长期是否保留由复核确认）。

> 2026-10-15 补充：阶段 4 的 P1a 已用隔离只读副本对上述 8 组逐条复核（结论：全部为"主体/主题组"而非"事件组"，`gpt-6.1sol`、`tibo` 等待判断项仍未决），复核证据、S01–S03 事件样本与 B01–B11 边界样本见[阶段 4 固定样本与 M11 复核材料](4-文章聚合_样本与复核.md)。该复核由实现 Agent 完成，仍需用户抽查确认；本小节的原始结论未被改写。

## 2. 范围

### 包含

- 热词注入：加工（`enrich`）提示词支持 `{{vocabulary}}`，运行时注入现有词表（按类型分组、别名已解析、排序确定、条数可配）。
- 常驻词（pin）：人工在词表页标记，永远出现在注入词表里，不受条数上限与频次影响。
- 复用观测：提示词要求模型自报每条关键词是复用还是新建；**服务端以注入集合为准硬判定**，落库并在概览页给出复用率。
- 词表版本：记录"模型这次看到的词表版本"，写入加工结果，用于解释同一版本前后两次加工结果为何不同。
- 合并建议：把词表分批交给模型返回疑似同指组，落库、可忽略、可采纳；采纳复用既有合并流程（含影响面预览与撤销）。

### 不包含

- 按来源或行业分类定制词表：本阶段词表全局一份，不做分层词表。
- 向量检索、语义相似度合并：建议仍由模型给出、人工确认，不引入 embedding 与近似检索。
- 上下位关系（`broader` 分组）：合并只处理同指，粒度关系留待文章生成阶段。
- 时间衰减排序与线索活跃度：属于文章生成阶段，本文只保证注入与统计所需数据可从现有表算出。
- 文章生成与发布。

## 3. 约束和前置条件

- 依赖：可用的 Provider 与 API Key（建议与基线复算都会真实调用模型、消耗额度）；worker 可运行；迁移编号从 `0014` 起（现有最新为 `0013_keyword_aliases.sql`）。
- 分层：注入用的词表查询只能经端口（`ports/repositories.py`）进入服务，SQL 只写在 `adapters/sqlite/`；`domain/` 里的渲染函数必须是纯函数。
- 提示词：注入内容与"复用/新建"字段都属于提示词的数据，不能硬编码在 `adapters/llm/`；新提示词走 `llm_prompts` 种子迁移并启用，版本串改变后阶段 2 的旧基线失效（见第 1 节排期结论）。
- 任务机制：**合并建议每批一个后台任务**（`keyword_merge_suggest`，属 `LLM_TASK_TYPES`、由 worker 认领；迁移 0019 按 `0009` 的先例重建了 `tasks` 表）；**常驻推荐是请求内的一次同步调用**（候选几十个词、几秒返回，规格标为 `assignable=False`，不进 worker 认领集合，因此不触发任务表重建）。两者都不在 API 线程池里跑。
- 确定性：注入文本与批次划分必须可复现（同样的词表输入两次渲染得到完全相同的字符串），否则 `llm_calls.input_hash` 无法解释、建议也无法比对。
- 规模阈值：前端组件默认不超过 200 行。`KeywordVocabulary.tsx` 现为 204 行，加常驻词列前必须先拆分。
- 迁移：只新增编号 SQL，不改历史迁移；旧库升级后 `reused` / `vocab_revision` 为 NULL 的行不参与统计、不得报错。

## 4. 关键决策（已写成决策记录，见[热词注入与合并建议](../决策记录/2026-10-13-热词注入与合并建议.md)）

下表是决策点的摘要；最终口径（含实施细化）以决策记录为准。

| 编号 | 决策点 | 选择 | 理由 |
| --- | --- | --- | --- |
| D1 | 注入内容的形状 | 按类型分组只给词，不给频次与计数；另附"近 7 天新增"一段；**常驻词并入其类型分组并保证出现**（不单列一段，避免同一个词出现两次） | 频次会诱导模型把高频词当成更重要，而注入的目的是复用不是排序；计数还会让同一词表两次渲染产生差异 |
| D2 | 注入条数上限 | 配置项 `llm_vocabulary_limit`（默认 150，`0` 关闭注入）+ `llm_vocabulary_recent_days`（默认 7） | 词表会继续增长，硬编码不可维护；默认值参考现状规模（332 个词）留出增长空间 |
| D3 | 词表版本语义 | `vocabulary_state` 单行表存"注入文本指纹 + 计数"，注入时发现指纹变化则计数 +1，并把当前计数写入 `message_enrichments.vocab_revision`；**只有加工执行推进，编译与试跑不推进** | 无需在写入与合并路径埋钩子（漏一处就会漂移），且语义正好是"模型看到的词表变了"；变更计数无法从事实数据推导，才允许落字段 |
| D4 | 复用率口径 | **纯服务端硬判定**：模型输出归一化后是否落在本次注入集合里即为 `reused`；不要求模型自报"复用/新建"字段 | 自报可以表演性填报，且多一个字段多一条容错路径与一份 token；硬判定下的复用率才是可比较指标 |
| D5 | 合并建议的执行方式 | **每批一个后台任务**（≤100 词，迁移 0019）：入队即返回、worker 执行，排队/重试/耗时与其它模型任务一致；结果落 `keyword_suggestions`，`keyword_suggestion_batches` 做幂等台账，任务幂等键含内容指纹。**2026-10-14 修订**：最初按「请求内同步调用」实现（理由是不重建 `tasks` 表），实测一次扫描要十几批、每批几十秒，同步意味着十几次等待且失败无法重试 | 批量与耗时决定了必须异步；任务化后进度、重试与失败原因都落在既有任务页，台账仍保证同一批不重复付费 |
| D6 | 建议的采纳路径 | 采纳不新增合并实现，直接复用既有 `POST /api/keywords/merge`（dry_run 预览影响面），成功后回填 `merge_id` 并可撤销 | 合并的破坏性与可撤销性已经有一套实现和测试，不复制第二套 |
| D7 | 常驻词与合并的联动 | pin 以规范词为键；合并时把成员上的 pin 移到目标词（目标已 pin 则保持），撤销时按 `pinned_json`/`target_was_pinned` 还原。**2026-10-14 修订**：每次合并把每条别名的先前状态单独记进 `keyword_alias_changes`（迁移 0023），撤销按记录重放，因此链式合并（`A→B` 再把 `B→C`）可以任意顺序解开；若某条别名已被更晚的合并改写，撤销会被拒绝，提示先撤销更新的那次 | pin 表示「这个词必须一直可用」，合并后 pin 留在被合并的写法上等于失去作用；原先按当前位置记账，逆序撤销会丢关系，属于必须修的正确性问题 |

## 7. 风险和取舍

| 风险或取舍 | 影响 | 缓解措施 | 触发重新评估的条件 |
| --- | --- | --- | --- |
| 注入让提示词变长 | 每次加工输入 token 上升，调用成本增加 | 只注入词、不给计数与理由；条数可配；先按默认 150 观察 token 用量 | 单次加工输入 token 明显抬升成本，或前 150 词覆盖率不足 |
| 注入降低多样性（词表被某领域占满） | 模型把不相关的新词硬塞进已有词条 | 提示词明确"只在确实指同一事物时复用"；复用率作为观测指标而非考核指标 | 复用率升高的同时相关消息质量下降 |
| 合并可能回潮 | 模型再次产出被合并掉的写法 | 注入前解析别名，被合并写法不进词表（阶段 2 已定的唯一防线） | 合并记录里出现同一组被反复合并 |
| 建议可能提上下位合并 | 抹平检索粒度（`尊界`/`尊界V800`） | 提示词只判定同指；界面沿用既有"不要合并上下位关系"说明；人工确认 + 可撤销 | 出现把上下位写进建议的批量案例 |
| 词表继续增长导致批次变多 | 人工工作面重新变大 | 建议按频次降序分批，孤词后置；概览给出待处理数量 | 词表超过约 800 词，评估把建议生成改为后台任务类型 |
| 提示词版本变化 | 阶段 2 的旧基线与历史结果不可比 | 排期上把基线复算放到 M11 一次完成；重跑入口单独评审（M12） | 每次改提示词都需要重测基线 |
| 复用率被"表演性填报" | 指标失真 | 服务端以注入集合为准硬判定（D4），自报不落库 | — |
